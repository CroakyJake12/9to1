# Code projects and development workspaces

The Dev source directory supplies the project and workbench domain used for Code in the Develop hub. Develop groups Code, Sites, Data, Stacks, Games, Virtual Device and Terminal. Preserve their appropriate domain models and reuse the common project identity wherever the specification calls for it.

A project begins with a chosen destination and provider. Preview a template and validate its toolchain, paths, source revision and proposed files before creating it. Preserve existing files, draft edits and stable workspace IDs. A selected project or displayed command does not grant the ability to run tests, write files or alter a repository.

The actual task workbench attaches to the current Task/Run and original Files/Home authority. Keep draft recovery, metadata transitions and undo history attached to their owning revisions. For a change in this directory, exercise the normal Create/Open, edit, test, close and resume paths as applicable. The retained table of core capabilities describes limits on individual implementations.

## Current capabilities

- Workspace and project records use stable IDs; workspace files are versioned, atomically saved, and protected from stale writers.
- Project templates can be registered by providers and filtered by language, framework, platform, product surface, search text, and toolchain readiness.
- Providers that own template content can prepare a deterministic multi-file UTF-8 payload after required toolchain readiness is revalidated. Preparation enforces the existing 64-file, 4 MiB per-file and 16 MiB total bounds, rejects path aliases/traversal and records per-file SHA-256 values. The result is still data for the existing original Home/Files setup review; this Dev preparation does not create Files items, authorize publication or replace that setup adapter.
- Task execution validates dependencies, requires workspace trust where declared, requests Home authorization before executing, enforces stage timeouts, and returns stage-level states and diagnostics.
- Code intelligence delegates semantic operations to the existing advanced service. Code actions and semantic rename previews retain immutable proposals for explicit Home-approved application; source/version conflicts refuse stale proposals. The native manual workbench does not call the raw language-server provider: it still needs a genuine read/process admission adapter.
- Structured results carry stable error codes, target IDs, retry metadata, and request IDs.
- A Space can persist a reference to the original workspace/project/root and canonical Task/Run. Fresh reopening reads the existing stores and current task observation; it does not create a workspace, task or attempt. A revision conflict requires an explicit current-reference attachment through the owning service.

## Ownership and integration limits

Dev does not replace Files, Stack, Terminal, Sites, AI Studio, Home, or extension hosting. Providers must connect the domain seams here to those owning services. The native workbench has source editing and reviewed per-pass inverse preparation through the maintained owner. A separate registered Dev App launch, full project wizard, toolchain installer, DAP debugger, Test Explorer, package providers, Stack review UI, full interactive CUI builder, remote environment adapters and exhaustive first-party API/event catalogue remain open implementation requirements.

The generic Task workspace tree/text-search fallback still refuses when its physical owner has no safe per-child traversal port. The native workbench instead uses the genuinely composed Home/Files reader for project folders, file navigation and structured search when available; command output does not establish those capabilities. Source reads and edits retain their actual configured Files identity/read/edit admission and current native fences. Process acceptance is distinct from an observed successful build or test exit.

The source editor and shared UI/runtime are owned by their existing workspace and platform layers. Dev's domain APIs must be wired into those layers through their owners; this project adds no alternate editor runtime or platform-specific dependency. Visual Studio extension provenance remains outside this package.
