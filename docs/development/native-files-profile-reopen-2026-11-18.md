# Haven Files native same-profile reopening smoke — 18 November 2026

## Purpose and precise evidence boundary

This is an **optional, non-deploying, owner-run or CI-run native startup/reopen check** of the **existing** `Haven.Desktop` Linux x64 apphost, not a replacement Files implementation. It launches the identical executable **twice** sequentially with one exclusively created user-private, *disposable* HOME, XDG and `HAVEN_DATA_DIR`, checks the apphost's **own** X11 window in each launch, preserves a smoke-only marker/inode between launches, and terminates only its own new process groups. Both launches use a single verified private directory. There is no Google OAuth and no user Drive data.

The check's process termination is by harness SIGTERM/SIGKILL after window observation — **not** normal user close. Reopening this disposable profile does **not** establish that Drive file identities, credentials, in-app mutations or saved state survived a normal close/reopen. The marker is generated by the harness itself, expressly *not* by Haven. These remain **NOT RUN**. The test prints only bounded JSON, not paths, credentials or its marker. Logs are created mode 0600 inside its exclusive mode-0700 scratch directory. Existing profiles and destinations are rejected, never overwritten. It never reads or uses existing credentials; the child receives an explicit environment allowlist, not `HOME`, Google client-ID, token or account variables from the caller.

## Reproducible command, only after a verified current native build

Use a real Linux x64 `Haven` apphost already built/extracted through the approved candidate route in `docs/development/native-files-source-candidate-2026-11-18.md`. Start a graphical X11 desktop or authorised disposable Xvfb/Openbox session that supports `/usr/bin/xprop`. Prepare an **empty** new private scratch parent; do not select an existing Haven directory. `.NET 10` runtime is needed by the framework-dependent native host.

```bash
cd /absolute/path/to/9to1
# Replace this placeholder with the exact new, admitted native candidate's path.
HAVEN_APPHOST=/absolute/private/candidate/installed/Haven
SCRATCH="$(mktemp -d)"
chmod 700 "$SCRATCH"
python3 -B eng/development/native_files_profile_reopen.py \
  --executable "$HAVEN_APPHOST" --scratch-parent "$SCRATCH"
```

A `PASS` result requires two separately launched *real* native process-owned X11 windows (same test-owned profile, independent process IDs, alive during the stability check). Failure of either launch produces `FAIL` or `BLOCKED`; no fabricated success receipt. The isolated scratch profile remains for the operator to inspect/remove; there is no automatic cleanup touching arbitrary owner paths. Invoke only when no competing SDK/live-instance claim is active. The normal real account OAuth consent and Drive use require separate owner authorisation and security hardening.
