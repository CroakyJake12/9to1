# M3 scope — expressing HUI Prefab/DynamicUI in CUI

Date: 2026-10-14
Directive: `MERGE-DIRECTIVE-2026-10-14.md` (CUI is authoritative; HUI merges into it; spec
takes precedence over framework behaviour)

Status: **M3 is not complete.** This document records what is now established by evidence and
what remains as genuine framework work. It exists so the next increment starts from measured
ground rather than from the assumption that M3 was a rename.

---

## 1. What was assumed, and what is actually true

The staged plan treated M3 as "30 `.hui` files to port". Reading the code, that
understates one part and overstates another.

### 1.1 The declarative bulk is already covered by CUI

CUI's `Repeat` (parser: `Core/CuiRichParser.cs:518`, model: `Core/CuiValues.cs:57`) is a full
reconciliation engine, not a naive re-render:

- resolves an `IEnumerable` source and requires a **non-null stable key** per item (`CUIR051`)
- rejects **duplicate keys** (`CUIR052`)
- `ReplaceRepeatItems` (`Runtime/CuiControlLoader.cs:1026`) diffs and preserves control identity

These are *stricter* than HUI's DynamicUI, which by its own documentation rebuilds an item when
a structural binding changes.

**Evidence.** `Runtime.Tests/CuiTranscriptRepeatCapabilityTests.cs` (new, 3/3 passing) pins the
three properties the Chat transcript actually depends on:

| Property | Test | Result |
|---|---|---|
| Reordering preserves each message's control by canonical id | `Reordering_the_transcript_preserves_each_message_control_by_canonical_id` | pass |
| Removing one message leaves sibling identity intact | `Removing_one_message_leaves_sibling_identity_intact` | pass |
| Duplicate canonical ids are refused, not silently rendered | `Duplicate_canonical_message_ids_are_refused_rather_than_silently_rendered` | pass |

Reorder identity matters because the D04 chronology fix re-ranks the same records by
`CreatedAt`; a rebuild-per-refresh reconciler would discard caret, focus and scroll for every
row on every re-rank.

So the transcript-as-a-list is **not** a rebuild. It is a consolidation.

### 1.2 The imperative surface is smaller than the plan implied

Production use of HUI's imperative DynamicUI API, measured across the workspace:

- `CreateItem` — used in 8 production scene files
- `DeleteItem` — 7 sites
- `Clear` — 5 sites
- `SetVariable` / `SetProperty` — **test-only** (`Haven.UI.Tests/DynamicUiTests.cs`); no
  production caller

Affected production files: `ChatSidebarHavenScene`, `StudyAssignmentsHavenSection`,
`OverlayShellHavenScene`, `ProjectHavenScene`, `StudioProjectHavenView`, `AgentsHavenScene`,
`ChatHavenScene`, `PlanHavenScene`.

### 1.3 The real gap: CUI cannot yet express a mixed-template list

This is the finding that matters, and it was **not** covered by the feasibility test above.

`ChatHavenScene.cs:554` selects the template per message:

```csharp
var template = message.Role == MessageRole.Assistant ? "ChatAssistantMessage" : "ChatUserMessage";
var item = _dynamicUi.CreateItem(template, "Messages", message.Id.ToString("N"), values, index);
```

One container, two templates, chosen per item by role — and positioned by an explicit ordinal
`index`.

CUI's `CuiListDefinition.ItemTemplate` is a **`string`, not a `CuiValue`**
(`Core/CuiValues.cs:57-61`). There is no per-item template resolution anywhere in the parser
or normaliser. So CUI cannot currently reproduce this surface.

There are three candidate resolutions, and they are **not** equivalent in risk:

1. **Per-item template binding in CUI** — make `ItemTemplate` resolvable per item. Genuine new
   CUI capability; the smallest change that matches the existing HUI semantics.
2. **Unify the two templates into one**, with role-conditional content inside. Preferred CUI
   idiom (one template, bindings choose what shows) but **unverified** — `ChatAssistantMessage`
   and `ChatUserMessage` may differ structurally (avatar side, alignment, affordances) in a way
   that conditional visibility cannot express.
3. **Two interleaved repeats.** Rejected: it reintroduces the manual index arithmetic M3 exists
   to remove.

Option 2 is the only one that adds no framework surface, so it must be tried first — but it is
a design question about the chat mockups, not a mechanical port, and it needs the mockups to
answer it.

## 2. What remains

1. Resolve the mixed-template question above against the approved Chat mockups. This is the
   gating decision for M3 and it is **not** yet answered.
2. Port the remaining declarative `.hui` surfaces to CUI markup.
3. Retire `HavenPrefabCatalog.FromAssembly` / `HavenDynamicUITemplateCatalog.FromAssembly`
   reflection discovery only **after** CUI owns the equivalent and callers have moved. These
   are load-bearing; deleting them without a verified successor removes working functionality.

## 3. Explicitly not claimed

- No claim that M3 is complete or that the transcript renders in CUI today. It does not.
- The 3 new tests are **framework capability evidence**, not a migrated surface. They prove CUI
  *can* carry a single-template keyed list; they do not prove it carries Chat.
- The `Duplicate_...` test matches either `CUIR052` or the word "Duplicate", because the
  exception wrapper adds context and the exact string is not a contract.

## 4. Method note

The duplicate-id test needed four iterations to land, and each failure was informative rather
than mysterious:

1. `Text` is not `Avalonia.Controls.Text` — CUI's `Text` element renders as `TextBlock`.
2. `Name=` is not a CUI attribute; elements use `id=`.
3. An `event` alias for the repeat item was a poor choice; `msg` is used.
4. **The decisive one:** the binding resolver expects
   `Dictionary<string, object?>`, not a positional CLR record. Every other CUI repeat test in
   the repo uses dictionaries. An arbitrary record silently fails key resolution.

Point 4 generalises beyond this test: any CUI binding against a typed model needs a projection
to dictionaries. That is a real cost of the consolidation and should be accounted for when the
transcript view model is designed, not discovered at port time.
