### What the port surfaced

The first-party `.cui` sources had **never been compiled**. `ChatSpace.cui` carried 47
diagnostics and `SpacesHome.cui` 30 — invented elements (`Aside`, `AdaptiveSplit`, `Heading`,
`List`, `ScrollView`, `Article`, `Markdown`, `Composer`, `TextArea`, `Row`, `Toolbar`, `Select`)
and invented attributes. `SpacesHome.cui` even contained a comment asserting every element and
attribute was canonical CUI, which is how the drift survived: the claim was never executed.
Nothing loaded either file, so no runtime path could fail either.

That is the failure mode this merge was warned about — a recoloured legacy surface read as a
completed migration — realised in the most literal way available. The permanent gate added here
(`Actual_spaces_and_chat_source_compiles_against_canonical_cui`) is the direct answer.

Three further classes of defect that a compiler **cannot** catch, all found by rendering:

1. **Bindings naming properties that do not exist.** `attachment.Name`, `activity.Name` and
   `RecentSearchQuery` are not on the real records (`MessageAttachment.OriginalName`,
   `ToolActivity.Title`). A document with these compiled cleanly and rendered nothing.
2. **`CuiViewModel` resolves a dotted binding path by its last segment alone**, so
   `Conversation.Title` and `Status.Message` collide with any other `Title` or `Message` in the
   document. `ChatSpaceCuiBindings` therefore resolves authored paths explicitly and refuses
   unknown ones instead of matching partially.
3. **`CUIR007` refuses a two-way binding on `ComboBox`**, so `Input Type="Select"` cannot bind
   its current value. The model and branch pickers became one-way with the selection shown as
   text beside them.

### Known behavioural losses, stated rather than hidden

- `ScrollView` has no canonical CUI equivalent. The transcript is a `Container`, so
  follow-at-end scrolling is lost. This is a real gap, not a stylistic one.
- Select controls cannot display their bound current value.
- Empty states use `If Condition Negate="true"` rather than a dedicated empty template.

## 1. What was assumed, and what is actually true

The staged plan treated M3 as "30 `.hui` files to port". Reading the code, that
understates one part and overstates another.

### 1.1 The declarative bulk is already covered by CUI

CUI's `Repeat` (parser: `Core/CuiRichParser.cs:518`, model: `Core/CuiValues.cs:57`) is a full
reconciliation engine, not a naive re-render:

- resolves an `IEnumerable` source and requires a **non-null stable key** per item (`CUIR051`)
- rejects **duplicate keys** (`CUIR052`)
- `ReplaceRepeatItems` (`Runtime/CuiControlLoader.cs:1026`) diffs and preserves control identity

These are *stricter* than HUI's DynamicUI, which by its own documentation rebuilds an item when
a structural binding changes.

**Evidence.** `Runtime.Tests/CuiTranscriptRepeatCapabilityTests.cs` (new, 3/3 passing) pins the
three properties the Chat transcript actually depends on:

| Property | Test | Result |
|---|---|---|
| Reordering preserves each message's control by canonical id | `Reordering_the_transcript_preserves_each_message_control_by_canonical_id` | pass |
| Removing one message leaves sibling identity intact | `Removing_one_message_leaves_sibling_identity_intact` | pass |
| Duplicate canonical ids are refused, not silently rendered | `Duplicate_canonical_message_ids_are_refused_rather_than_silently_rendered` | pass |

Reorder identity matters because the D04 chronology fix re-ranks the same records by
`CreatedAt`; a rebuild-per-refresh reconciler would discard caret, focus and scroll for every
row on every re-rank.

So the transcript-as-a-list is **not** a rebuild. It is a consolidation.

### 1.2 The imperative surface is smaller than the plan implied

Production use of HUI's imperative DynamicUI API, measured across the workspace:

- `CreateItem` — used in 8 production scene files
- `DeleteItem` — 7 sites
- `Clear` — 5 sites
- `SetVariable` / `SetProperty` — **test-only** (`Haven.UI.Tests/DynamicUiTests.cs`); no
  production caller

Affected production files: `ChatSidebarHavenScene`, `StudyAssignmentsHavenSection`,
`OverlayShellHavenScene`, `ProjectHavenScene`, `StudioProjectHavenView`, `AgentsHavenScene`,
`ChatHavenScene`, `PlanHavenScene`.

### 1.3 The real gap: CUI cannot yet express a mixed-template list

This is the finding that matters, and it was **not** covered by the feasibility test above.

`ChatHavenScene.cs:554` selects the template per message:

```csharp
var template = message.Role == MessageRole.Assistant ? "ChatAssistantMessage" : "ChatUserMessage";
var item = _dynamicUi.CreateItem(template, "Messages", message.Id.ToString("N"), values, index);
```

One container, two templates, chosen per item by role — and positioned by an explicit ordinal
`index`.

CUI's `CuiListDefinition.ItemTemplate` is a **`string`, not a `CuiValue`**
(`Core/CuiValues.cs:57-61`). There is no per-item template resolution anywhere in the parser
or normaliser. So CUI cannot currently reproduce this surface.

### 1.3a The two message roles CAN be unified (resolved)

Comparing `DynamicUI/ChatUserMessage.hui` and `DynamicUI/ChatAssistantMessage.hui` line by line,
**the assistant template is a strict superset of the user template**. Identical: `MessageRoot`
(Horizontal, 100%, gap 10px, padding 8px 4px), `Avatar` (28px, radius 14px, visibility-gated),
`MessageBody` (Vertical, 100%, gap 6px), `Body` (Markdown), `MessageMenu` (icon button, end
aligned).

Only three differences, all already data-driven:

| Difference | User | Assistant | Resolution |
|---|---|---|---|
| Role caption | literal `"You"` | bound `{{AGENT}}` | bind one `ROLE` variable; the scene already computes `AGENT` (`ChatHavenScene.cs:572`) and could compute `"You"` the same way |
| `Thinking` row | absent | present, visibility-gated | add the row; `THINKINGVISIBILITY` already exists (`ChatHavenScene.cs:574`) and resolves to `Collapsed` when there is no thinking text |
| `GeneratedContent` container | absent | present, empty when unused | drive from a list that is empty for user messages, or gate its visibility |

The avatar is **not** a differentiator: `ApplyAvatarValues` (`ChatHavenScene.cs:580`) is shared
by both roles and differs only in which preference and image source it reads, collapsing to zero
width when the avatar is disabled or unavailable.

So options 2 and 3 above are unnecessary for the two message roles. That part of M3 is a
consolidation, not new framework work.

### 1.3b Tool activity is NOT unifiable — the gap stands

`DynamicUI/ChatToolActivity.hui` is inserted into the same `"Messages"` container, at an
explicit index, interleaved with messages (`ChatHavenScene.cs:511`). It is **structurally
distinct**, not a superset or subset:

- `Layout="Grid" Columns="88px 1fr Auto"` versus the message row's `Layout="Horizontal"`
- its own `Background="Surface" Radius="12px"` — it is a card, the message row is not
- no avatar, no Markdown body; a `Status` / `Title` + `Detail` / `Meta` triple instead

Conditionally re-shaping a Horizontal message row into a Grid card inside one template is not a
binding exercise, and splitting tool activity into a separate container would break the
interleaved chronology that D04 exists to get right.

**Conclusion.** Chat's `Messages` list genuinely needs two template shapes in one list. CUI's
`ItemTemplate` is a single `string`. Per-item template resolution in CUI is therefore real,
required work — it is the gating capability for M3.

### 1.4 That gating capability now exists

`<Repeat Template="...">` was added, resolving to one of the Repeat's own
`Definition="true"` children per item — so the template pool is scoped to the list that uses it
rather than being a global name.

- `CuiRepeatDefinition.Template` (`Core/CuiValues.cs`) is a `CuiValue`, so it takes a literal
  name or a per-item binding.
- `CUIR053` — an item whose `Template` resolves to nothing.
- `CUIR054` — a name that matches no `Definition` child. Refused rather than rendering an empty
  row, which would hide a template typo behind an apparently working list.
- `CUI047` (parse) — a `Template` with no `Definition` child to select from.

A stable key is no longer sufficient identity on its own: when an item's template changes, that
row is rebuilt and its superseded scope unsubscribed, detached and unparented. Rows whose
template is unchanged are still reused, so caret/focus/scroll survive as before.

Pinned by `Runtime.Tests/CuiPerItemTemplateTests.cs` (4/4): one list renders a different
template per item; a template change rebuilds only that row; an unknown name is refused; and a
`Repeat` **without** a `Template` is unchanged (backward compatible).

CUI Runtime is 344/344. The 5 `CakeOS.Cui.Compiler.Tests` failures are **baseline** — verified
identical with these changes stashed, and they concern first-party `.cui` sources, not the
parser. Markup 34/34 and Build.Tasks 25/25 pass.

## 2. What remains

1. **Shell wiring** — the largest single item. A native page following `SpaceTaskWidgetPage`
   hosts `CuiSceneHost` and calls `ShowAsync(new CuiNativeScene(...))`;
   `AssistantsNativeCuiSurface` does the same for Assistants. Neither Chat nor Spaces home has
   one. The live Chat surface must not be removed until the CUI one demonstrably covers its
   behaviour, because `ChatHavenScene` carries threading settings, send queueing, dual-model
   selection and attachments that `ChatSpace.cui` does not yet model.
2. Migrate the 21 production `.hui` templates. The two Chat message templates are a strict
   superset relationship and unify (see 1.3a); `ChatToolActivity` stays separate and is exactly
   the per-item `Template` case now supported.
3. Move the 8 scene files off imperative `CreateItem`/`DeleteItem`/`Clear` onto `Repeat`.
4. Retire `HavenPrefabCatalog.FromAssembly` / `HavenDynamicUITemplateCatalog.FromAssembly`
   reflection discovery only **after** CUI owns the equivalent and callers have moved. These are
   load-bearing; deleting them without a verified successor removes working functionality.
5. Two first-party CUI sources outside this delivery still do not compile: `MailWorkspace.cui`
   (111 diagnostics) and `ModelPicker.cui` (7). Same defect class as the two fixed here.
6. Native CUI capture needs repair before it can serve as evidence.
   `NativeAssistantCanonicalVisualCaptureTests.Actual_native_home_saved_configuration_and_canonical_conversation_emit_opt_in_captures`
   is among the pre-existing native failures, so the harness that would prove a CUI surface
   renders natively is itself not green.

## 3. Explicitly not claimed

- No claim that M3 is complete or that the transcript renders in CUI today. It does not.
- The 3 new tests are **framework capability evidence**, not a migrated surface. They prove CUI
  *can* carry a single-template keyed list; they do not prove it carries Chat.
- The `Duplicate_...` test matches either `CUIR052` or the word "Duplicate", because the
  exception wrapper adds context and the exact string is not a contract.

## 4. Method note

The duplicate-id test needed four iterations to land, and each failure was informative rather
than mysterious:

1. `Text` is not `Avalonia.Controls.Text` — CUI's `Text` element renders as `TextBlock`.
2. `Name=` is not a CUI attribute; elements use `id=`.
3. An `event` alias for the repeat item was a poor choice; `msg` is used.
4. **The decisive one:** the binding resolver expects
   `Dictionary<string, object?>`, not a positional CLR record. Every other CUI repeat test in
   the repo uses dictionaries. An arbitrary record silently fails key resolution.

Point 4 generalises beyond this test: any CUI binding against a typed model needs a projection
to dictionaries. That is a real cost of the consolidation and should be accounted for when the
transcript view model is designed, not discovered at port time.
