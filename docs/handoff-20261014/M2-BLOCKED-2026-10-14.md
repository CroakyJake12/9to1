# M2 — attempted, reverted, and blocked on a semantic mismatch

**Date:** 2026-10-14 · **Outcome: NOT LANDED.** Recorded so the next attempt does not repeat it.

## What was attempted

Collapse `SurfacePaletteCatalog` onto CUI as the single semantic palette owner (owner directive:
CUI authoritative, HUI merges into it, spec takes precedence).

The enabling discovery was good news: `CuiPalette` and `SurfacePaletteCatalog.Palette` are
**field-for-field identical** — the same 25 semantic colours plus a theme — so a full collapse is
mechanically possible rather than a hand-copied approximation. The implementation short-circuited
`For(HavenSurface, HavenUiAppearance)` for Chat/Go/Spaces to
`CuiSurfacePaletteCatalog.For(...)`, mapped through a new `FromCui` projection, and skipped the
legacy `Express()` because CUI applies its own per-theme expression.

This also superseded the earlier partial change that routed only the **neutral** surfaces through
CUI while locally deriving text, line, button and focus — a strictly larger win on paper.

## Why it was reverted

It introduced **five real regressions**, not test noise:

| Regression | Cause |
|---|---|
| `HavenUiComponentSystemTests.Accent_switch_mutates_live_gradient_resources_...` | The short-circuit returns **before** the `HavenPersonalisation.OverrideAccent` block, so explicit accent overrides are ignored. `CUI-PREF-203` makes accent override a required mode (None / All Apps / Individual Apps). |
| `HavenUiComponentSystemTests.Scoped_app_accent_changes_nested_components_...` | same cause |
| `HavenUiComponentSystemTests.Every_page_palette_exposes_three_non_flat_gradient_tiers` | accent-derived tiers no longer produced |
| `PersonalisationTests.Non_glow_themes_change_interaction_treatment_without_changing_text_colours` | CUI's internal expression does not reproduce the legacy non-Glow treatment for these surfaces |
| `PersonalisationTests.Every_theme_resolves_for_every_surface_and_appearance` | per-surface/appearance expectations no longer hold |

Shipping that would have broken a **spec-required feature** (accent override modes) to serve the
merge. That is exactly the trade the brief forbids.

## The real blocker: the two accent models are incompatible

The obvious fix is to pass the legacy accent override into CUI's resolver. It does not work,
because the two models are different types:

- **Legacy** `HavenAccentColour` — a **continuous** colour. Accents come from per-surface hue
  anchors (Chat indigo `#3527FF`, Tasks orange, …) plus an arbitrary user override.
- **CUI** `CuiAccentColour` — a **discrete named palette enum** (`Yellow`, `Cyan`, `Lime`, …),
  resolved by `CuiAccentCatalog.Resolve(colour, appearance)` into an anchor set.

There is no faithful conversion between a continuous colour and a named palette entry.
Reconciling them is a **product decision**, not a code change:

1. Does `CUI-PREF-203`'s "expose a per-app colour selector" mean CUI must support continuous
   per-app colours, replacing the discrete enum with a real colour chooser?
2. Or is the discrete named palette the intended spec model, in which case the legacy continuous
   accent pipeline is the thing that must be retired — and every per-surface hue anchor with it?

Until that is answered, any full collapse either drops accent override or silently degrades it to
a nearest named colour.

## What is actually landed for palettes

The **earlier, narrower** change stands and is verified: for Chat/Go/Spaces the **neutral** shell
surfaces (tide, base, panel, panel2, panel3, hover) resolve from `CuiSurfacePaletteCatalog` at the
matching appearance and the live `CuiTheme`. Accent, text, line, button and focus remain owned by
the legacy pipeline, so accent override keeps working.

That is genuinely correct against `CUI-PRO-202` ("restrained accents… not application-local colour
patches") and is the change the rendered evidence validates. It is a **partial** M2, not a merge.

## What M2 needs to proceed

An owner decision on the accent model (question 1 or 2 above). Then:

- M2a — thread the resolved accent model into CUI for in-scope surfaces, keeping override working.
- M2b — delete `SurfacePaletteCatalog` and `HavenUiResourceApplier`'s duplicated palette assembly,
  leaving `Haven*Brush` names as the aliases `CuiThemeResourceApplier.ApplyLegacyScopeAliases`
  already provides.

## Not claimed

No part of the palette merge is complete. M1 (theme authority at the preference boundary) is
landed and verified; M2 is partial; M3 (expressing HUI Prefab/DynamicUI in CUI) is not started and
remains the largest stage.
