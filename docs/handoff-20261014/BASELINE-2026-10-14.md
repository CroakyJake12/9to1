## 5. Defect found and fixed — Gate A restore blocker

**Symptom:** `./eng/9to1.ps1 restore -Component core` failed at `origin/main` `2c4d151b`.

```
error NU1902: Warning As Error: Package 'System.Security.Cryptography.Pkcs' 10.0.0
  has a known moderate severity vulnerability (GHSA-2fmv-rv2c-59x7)
error NU1903: Warning As Error: Package 'System.Security.Cryptography.Pkcs' 10.0.0
  has a known high severity vulnerability (GHSA-846f-f764-76mx)
```

Failing projects: `HavenOS.Home.Tests`, `HavenOS.Mail`, `HavenOS.Files.NativeHost`.

**Root cause (from resolved asset graph, not speculation):**
`MailKit 4.18.0` → `MimeKit 4.18.0` → `System.Security.Cryptography.Pkcs 10.0.0`.
`9to1 Workspace\Directory.Build.props` sets `TreatWarningsAsErrors=true`, so
`NuGetAudit` findings become hard errors. The repository at `2c4d151b` therefore
**cannot restore `core`**, blocking every downstream gate.

**Fix (narrow, at the canonical owner, no audit suppression):**

- `9to1 Workspace\Directory.Packages.props` — added
  `<PackageVersion Include="System.Security.Cryptography.Pkcs" Version="10.0.13" />`
- `9to1 Workspace\Mail\HavenOS.Mail.csproj` — added direct
  `<PackageReference Include="System.Security.Cryptography.Pkcs" />` to lift the
  transitive pin.

`NuGetAudit` / `NuGetAuditLevel` were **not** weakened. Latest published 10.0.x is
`10.0.13`; this is a patch-level lift within the same major/minor.

**Result:** `restore -Component core` now succeeds for all CUI, Home and Spaces
projects. Build status recorded below.

   `Chatbox.hui`, `ChatAddMenu.hui` and `ChatHavenScene` render through

### 9.2 `SpacesHome.cui` was not real CUI — migrated to canonical CUI

**Root cause of the failing Spaces test, established from code:** the document was authored in
a third, invented element vocabulary. It is neither CUI (its `Aside`, `AdaptiveSplit`,
`SearchField`, `Heading`, `List`, `Article`, `Row`, `Main`, `Panel` are not CUI primitives and
not registered Definitions) nor donor AXAML (they are not in `CuiLanguageVocabulary.DonorElements`).
`CuiRichParser` therefore parsed it **without diagnostics**, so the document looked valid and
the surface never rendered through a real CUI host. The failing assertion
(`space-context-items` absent from the parsed tree) was a symptom of that, not a bad expectation.

**Fix — at the owning layer, not by weakening the test.** `9to1 Workspace/Spaces/UI/Home/SpacesHome.cui`
was rewritten in canonical CUI following the repo's own production conventions
(`9to1 Workspace/Home/UI/ModelPicker.cui`, `9to1 Workspace/Spaces/UI/Tasks/SpaceTaskWidget.cui`):

- every element is now `Page` / `Container` / `Text` / `Button` / `Input` / `Theme`;
- all 8 ids, all 7 actions (`spaces.create`, `spaces.open`, `spaces.rename`, `spaces.move`,
  `spaces.fork`, `spaces.archive`, `spaces.clear-search`, `spaces.add-context`) and every
  `accessible-name` preserved;
- `definition="true"` + `items` / `item-template` / `empty-template` replace the invented
  `List`/`Article` + `repeat` + `empty-text`;
- Professional semantic resources (`{Resource CuiPanelBrush}`, `CuiTextBrush`, `CuiTextSoftBrush`,
  `CuiLineBrush`) used instead of nothing, with `SemiBold`/`Bold` weights per `HAVEN_UI_RULES.md`
  Typography USER-UI-0001 (Light/Thin forbidden);
- data contracts preserved verbatim as binding roots (`spaces.query`, `spaces.builtIns`,
  `spaces.customSpaces`, `status.message`, `selection.*`) so no contract was silently renamed.

**Verified:** `eng/cui/migrate_legacy.py` now reports `changed: false` for the file (it
previously reported `state: requires-manual-adapter`, diagnostic naming `AdaptiveSplit`).
`HavenOS.Spaces.Tests` is **70/70 PASS**. The assertion was **not** modified.

**Honest losses, recorded not hidden:**
- `AdaptiveSplit compact-breakpoint="760" compact-mode="drawer"` was dropped — CUI has no
  responsive construct. See `DECISION-2026-10-14-CUI-RESPONSIVE.md`.

- `SearchField clear-action` → the `Input`'s own `action`.
- `variant="primary"` on the create button was dropped: `variant` is not a CUI button property.
- **`touch-target="44"` was dropped: CUI has no touch-target property.** Touch sizing must come

## 10. Root cause of the Chat visual mismatch (found, not fixed)

**The production Chat surface is not CUI-themed at all.** It resolves a separate, static,
teal palette from `9to1 OS/HUI/theme/tokens.json` (`background #0F1A1E`, `accent #3ED598`) via
`CakeTheme` / `HavenDesignTokens`, which is never bridged to `CuiThemeResourceApplier`.
CUI's Professional theme — correct, Montserrat-backed, 8 built-ins + Cinematic legacy — is
implemented and simply does not reach the Chat chrome.

This explains every visual rejection the handoff names (wrong palette, wrong hierarchy, wrong
icon/typography treatment) without needing renderer speculation.

**Not fixed** because `HAVEN_UI_RULES.md`'s Theme Modification Lock plausibly forbids every
obvious remedy and no explicit instruction has lifted it. Raised as
`DECISION-2026-10-14-CHAT-SURFACE-AUTHORITY.md`.

`dotnet --info` reports `RID: win-arm64`, `Host Architecture: arm64`. Only the arm64 .NET

**Required to clear:** install the **x64** .NET runtime/SDK side-by-side on this ARM64 host
(Windows ARM64 runs x64 under emulation, so the existing x64-pinned projects would then run
unchanged). This is an environment install and was **not** performed unilaterally.

not a pass and not proof the product is broken.
