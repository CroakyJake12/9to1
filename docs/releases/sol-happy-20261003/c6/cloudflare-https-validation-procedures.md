# Deployed HTTPS validation procedures

Prepared from canonical Sol Happy SH-01–SH-13, source `/workspace/team-c/spec-native-final-2104.txt` (lines 8180–8335). This is a procedure, not executed acceptance. All outcomes currently NOT_RUN. Authenticated account metadata reads do not establish these gates. Root alone issues deployments and provider mutations; C6 reviews and independently checks authorized reads. No spending, live payments, production routing changes or original user-data modification is authorized by this plan.

Before execution, record immutable repository commit, deployed Worker version/deployment ID and timestamp, hostname, environment, exact issuer/resource audience, public-client callback, configuration SHA256, compatibility date, service binding names and IDs, D1 database identity/schema migration hashes, secret reference names only, frontend artifact hashes, rollback version and schema compatibility. Root must retain provider-reported deployment result separately from source manifests. Re-fetch deployment metadata to bind public HTTPS output to the issued revision; an arbitrary health string is insufficient identity proof. Credentials, cookies, recovery links, passwords, signing material and tokens remain outside Git; public evidence stores only sanitized status/assertion results and hashes. Never print private response bodies to normal diagnostics.

Use dedicated staging state and two fictional accounts with unique `example.test` identifiers, an ordinary public client and isolated browser profiles. No Jacob/reserved owner, organisation grants or paid entitlements are provisioned as test substitutes. Mail delivery tests require an approved real test recipient and configured provider; local D1 capture alone remains unverified delivery. Test registration/session writes are executed only by the root-authorized staging journey runner. Existing user accounts and buckets are excluded.
