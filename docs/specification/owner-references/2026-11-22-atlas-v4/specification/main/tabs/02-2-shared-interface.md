# Shared interface

This chapter defines the interface of Haven, Home, shared CUI components, Settings and the compact model picker. Its visual authority is the [editable Interface Atlas v3.3](https://github.com/CroakyJake12/9to1/blob/1f92cd888f59025cc684f0720163efdbc580f8e3/docs/specification/owner-references/2026-11-18-interface-refactor/design/9to1_Interface_Atlas_v3.3_Editable.html) at repository revision 1f92cd888f59025cc684f0720163efdbc580f8e3. The named screens and the final active refinement layers in that file determine composition. Preview data and preview storage are examples; they do not establish service capability, production schema or completed functionality.

The requirements below are written for the replacement specification. They carry forward Atlas interaction outcomes without incorporating old worker instructions, implementation schedules or provider fixtures. The Atlas’s HTML/CSS/JavaScript is a design reference; it is not an instruction to author application UI in those languages.

## 2.1 Haven shell and navigation

SHELL-001 — One host, one app implementation. Haven hosts native app and web tabs in one tab strip. An app’s standalone presentation, where provided, uses the same product implementation. Hosted app identity is visible in the tab and, where shown, the app sidebar. Do not stack a duplicate app title bar beneath Haven’s tab and address rows. Initial onboarding and explicitly standalone/mobile surfaces keep their own composition. Source: home-apps, host-browser, onboarding; final Atlas shell refinement.

SHELL-002 — Tab anatomy. Normal Haven tabs keep app icon, label and trailing close affordance left aligned. The selected tab has the Atlas’s light surface and readable dark label, resolved appropriately in each theme and accessibility mode. App icons retain their distinctive filled artwork. The equal-width Main/Voice/Vision selector inside the model picker is the deliberate centred-label exception. Active, focused, hovered and close-button states must remain separately identifiable. Source: home-apps, host-model-picker, final suite-consistency and shell layers.

SHELL-003 — Document identity and tools. In hosted editors, the current document title is reflected in the active tab. Saving state is surfaced in the host’s address region with a readable accessible description. Keep one appropriate primary action directly accessible; group remaining document actions into the document-tools disclosure, preserving their original commands and context. Settings uses Settings tools and does not invent a document history or comment thread. Closing a tools popup restores its trigger’s focus. Source: final Haven shell layer, applicable hosted editor screens. This consolidation applies to the eligible common app-header composition; app-specific final Atlas arrangements remain authoritative, including Boards’ sidebar identity, file actions and save state. Do not duplicate those controls in the address row.

SHELL-004 — Address modes. The address control distinguishes 9to1 routes, Files locations and web addresses. Its selected mode and committed location belong to the active tab. An unfinished address draft survives view refresh; Escape restores the committed location, while explicit submission performs navigation. Back/forward availability reflects that tab’s actual history. Local folder search remains a Files operation; it must not appear as a second global address bar. Unknown or unavailable destinations receive an inline state without fabricating a successful navigation. Source: host-browser, files, files-grid, final Haven address refinement.

SHELL-005 — Tab close and recovery. New Tab and Home Dashboard are separate canonical tab destinations. Closing a tab selects the nearest valid tab to the right, otherwise the left; when none remain, create a New Tab, not a Dashboard view. Focus follows the selected tab. Closing either surface does not delete its layout preferences, widget sources, account state, user data or recoverable drafts. The close affordance remains independently operable without activating or dragging the tab. Source: host-newtab, home-dashboard and final shell refinement, except their superseded merger.

SHELL-006 — Canonical destinations. Resolve internal navigation to the requested stable app, object or setting identity. Keep host-newtab, home-dashboard, home-apps and home-explore as distinct destinations even where they use the same sidebar and visual primitives; never alias Dashboard to New Tab. Existing compatible deep links and settings aliases continue to resolve without duplicating stores. The home-events route may resolve to Notifications. Unknown or unavailable destinations display a recoverable failure rather than silently opening another surface.

SHELL-007 — Browser boundary. Web content retains the selected tab’s actual URL, browser profile and engine identity. CUI theme changes affect browser chrome, not the document’s authored page styles. Failure of a browser engine is scoped to dependent web content and must not prevent local native editing. History, bookmarks and inspection use the same active-tab context. Source: host-browser, host-browser-history, host-browser-bookmarks, host-devtools-html, host-devtools-cui.

SHELL-008 — Inspection truth. HTML and CUI inspectors distinguish their target and available information. The Atlas’s inspectors are bounded, read-only snapshots, and its query console does not evaluate JavaScript. Engine selectors and permission controls in that preview are per-origin example preferences. A production inspector or engine switch may claim capability only after the corresponding native operation exists and is verified; the screenshot alone does not authorise arbitrary evaluation or grant an operating-system permission.

SHELL-009 — Atlas default and safe normal customisation. Preserve the current pinned Atlas Haven shell layout as the default, except for explicit owner changes and the separate Home Dashboard/New Tab correction. Normal mode supports reversible repositioning and styling of selected tab-strip, toolbar and sidebar items, density, grouping, widths and similar presentation settings. Keep primary navigation, the account/profile entry, Settings, accessibility and recovery discoverable; ordinary rearrangement cannot hide the final route to those controls. Supply accessible non-drag alternatives, preview, change history and targeted rollback. Normal-mode AI agents can add features via permission-reviewed, update-compatible custom extensions, including new app/hub controls; they cannot silently overwrite, remove or rewrite built-in product features. Preserve the underlying default layout independently of user preferences.

SHELL-010 — Unrestricted customisation mode. Unlock exactly through Settings → account icon → tap username ten times → enter account password → inspect the confirmation popup → Allow. Ten taps only reveal the feature; the password step authenticates and Allow explicitly activates it. Unlike normal mode, unrestricted mode supports much freer rearrangement, direct terminal editing of CUI configuration/source within authorised operating-system rights, and agent-driven additions, modification or removal of existing first-party features. Provide source/configuration revision history, reviewable diffs, backups, compatibility checks and permission review for such changes; warn that arbitrary code edits are not always automatically reversible. Surface a working independent recovery route before enabling dangerous configurations. The unrestricted label never permits bypassing account authentication, permissions, device protection, security boundaries or paid service entitlements. Turning it off restores the protected editing mode without silently discarding compatible saved advanced changes.

SHELL-011 — Controlled configuration history and rollback. Version interface settings and layout changes as recoverable transactions with before/after state, provenance and applicable affected scopes. Support per-change undo/redo where meaningful, labelled checkpoints, previewing a prior revision, comparing changes, targeted rollback of an element or category and full restore of a selected known-good checkpoint. A generic 'Reset' button is insufficient. Isolate theme, chrome position, hub arrangement, extension settings and profile preferences so a layout repair need not erase unrelated personalisation, data or accounts. Guard against corrupted migrations and incompatible extension layouts, preserve the latest usable configuration, and report what will change before commit. Restoration preserves canonical app and user-content identities.

SHELL-012 — Independent Customisation Recovery app. Ship a dedicated recovery application or independently launchable recovery entry point in the installed Haven shared core, able to open even when Haven's main browser/chrome, theme or extension layout fails. Detect and inspect damaged layout/state, offer safe-mode launch with third-party chrome customisations suspended, show recent configuration checkpoints and allow selective restore, rollback or an explicitly confirmed reset to the authoritative default layout. It must not depend on the broken customised Haven interface to run and must not remove browser profiles, saved work, project data or account identity as a side effect of visual recovery. Retain diagnostic records, explain limitations honestly, and test crash loops, invisible account controls, unusable themes, malformed extensions, invalid display geometry, and failed migrations.

SHELL-013 — Firefox donor feature preservation. Use the Firefox browser application as Haven's primary browser donor, adapting/forking the application portion where its chrome or behaviour changes to meet Haven/CUI requirements. Preserve the broad set of compatible Firefox capabilities instead of building a minimal web-view substitute: navigation, profiles, private browsing, history, bookmarks, tabs and groups, downloads, site settings and permissions, tracking protection/privacy, extensions and WebExtension compatibility, developer tools, web standards/media, authentication/password/passkeys where supported, printing, accessibility, relevant sync/import-export features and recovery. Maintain a feature-by-feature donor parity/intentional-replacement matrix; document design adaptations, unsupported features and verified tests. Assess Firefox application code, Gecko and any other upstream components individually: fully include modified forks' source trees in the 9to1 repository, while reproducibly pinning unchanged components when build architecture genuinely permits this. Ship dependencies as part of the Haven installation, subject to licence, attribution, upstream security fixes, reproducible packaging and platform restrictions. Retain shared Dulche integration without duplicating donor AI surfaces. Never describe donor capability as shipping until implemented and tested.

SHELL-014 — Haven default visual layout, transcribed from the final editable Atlas v3.3 source. Reference screen IDs: home-apps, host-newtab, host-browser, host-browser-history, host-browser-bookmarks, host-model-picker, host-notifications, host-devtools-html and host-devtools-cui; include the final atlas-haven-shell-code refinement. The browser host has exactly two persistent horizontal chrome rows above the current page, not a third duplicate application-title row. Top row: 9to1 identity/wordmark on the leading side, a compact Home tab, app and website tabs aligned from the left with distinctive filled app icons, a visible title and separately focusable close control, a New Tab (+) action, and tab search/overflow and host window controls towards the right. Use the Atlas's lightly surfaced selected-tab treatment with dark readable label adjusted for theme, while keeping hover, focus, active and close states independently identifiable. Tab pinning, groups, multiple views and split arrangements preserve canonical tab identities. Second row: Back, Forward and Reload; one rounded typed address/location field with a mode control for native 9to1 routes, Files locations or web addresses, committed versus draft text and specific error/clear status; then the relevant primary/document tools, compact model picker with truthful current model/context information, notifications bell and account/profile avatar. Navigation and address modes belong to the active tab. On hosted document views, the actual document title appears in the selected tab, a genuine save-state indication occupies the host control region, a single relevant primary action remains directly available, and secondary document/Settings operations occupy a labelled tools disclosure. Remove the redundant hosted app-header row rather than recreating duplicate app labels, avatars, model selectors, address bars or commands. Apps and Settings can present their own left sidebar and scrollable content beneath the host chrome. In standalone windows the Haven tab/address rows are absent and the same app exposes the standalone controls it needs. Web content keeps its own site-authored styles; 9to1 themes style the browser chrome. At narrow widths, preserve reachable overflow, keyboard controls, focus, save states and original operations. The Atlas's example tab titles, model names, percentages and web page content are fixtures, not current system measurements.

SHELL-015 — Default-layout acceptance and controlled modifications. Build the ordinary Haven layout from the actual Atlas hierarchy, positioning and control grouping rather than merely approximating its colour palette. Test Home, browser web content, document editors and Settings in hosted and standalone modes. Normal customisation permits rearranging eligible chrome while preserving required account/Settings/recovery access and adding approved extension features only. Unrestricted customisation, following the reauthentication gate in SHELL-010, permits deliberate CUI/terminal editing and agent changes to core features, subject to review, capability gates and source protection. Version UI settings and source edits separately. Test a broken theme or invisible-control configuration, independently launch Customisation Recovery, inspect prior checkpoints and roll back one affected control without erasing work, accounts or the rest of the layout; separately test restore to a known-good checkpoint and the Atlas default. Keep exact integration and edge-case interactions in the interaction volumes.

Acceptance: open native and web tabs; switch repeatedly; edit an address draft while refreshing underlying content; use back/forward; open and dismiss tools with keyboard; close Home/New Tab in the middle and at the end of the strip; restore the session. Confirm correct identity, no duplicate chrome, usable overflow, visible focus and preserved drafts. Check real engine failure separately from Atlas navigation.

### 2.1.1 Tab, resource and view lifecycles

UIX-HOST-001 — A host tab records TabID, content kind, canonical destination, optional artifact/ConversationID, browser ProfileID and engine where applicable, title/icon source, navigation history, pin/group/workspace membership, view-state reference and recovery state. The logical record is independent of the renderer's transient objects. Distinguish an empty New Tab, native app Start view, opened native artifact and web document; opening an app without an artifact must not fabricate a blank saved document merely to populate a tab title.

UIX-HOST-002 — Selecting a tab activates its existing view and focus context. If a view must be remounted, restore the canonical destination and supported view state without repeating its last command. Duplicate tab duplicates navigation/view context and preserves the same referenced artifact unless the user explicitly requests a document copy. Duplicating a browser tab does not copy another profile's credentials. Pin, move and group affect tab organisation; they do not save, publish, delete or change ownership of its content.

UIX-HOST-003 — A close request is delivered to the actual owning view with the tab's current identity. A locally recoverable background document can close its view while saving continues under its owning service. Where unsaved work cannot safely survive closure, offer the relevant Save, Discard and Cancel outcomes and identify the affected document. Discard means the confirmed draft scope, never deletion of the last durable artifact. A failed save leaves the view or recovery draft available. Closing one of two views of the same document must not destroy the remaining view's session.

UIX-HOST-004 — The session manifest records the tab order, selected tab, canonical destinations, applicable profiles/engines, groups/split arrangement and supported view references in one revision. Restore each independently. A removed document produces a missing-target tab with recovery/open-location actions; revoked access produces a denied state without leaking content; an absent browser renderer produces a repair/engine choice scoped to that web tab. Other native tabs must become usable even when one destination cannot restore. Reopening a closed view never resends an admitted message or invokes a stored command.

UIX-HOST-005 — Tab groups and workspaces retain stable identities, labels, ordering and membership. A group is organisation, not an account or permission boundary. Collapse hides the group's visible tabs without cancelling their runs; close-group distinguishes closing views from deleting documents. Move between windows/workspaces preserves TabID or records an explicit equivalent transfer without duplicating active effects. Existing compatible alternate tab placement and Split View remain supported through shared semantics; new geometry absent from the Atlas must be identified as a design extension, not claimed to be illustrated by the existing horizontal reference.

UIX-HOST-006 — Split View contains normal tabs with independent active input and scroll focus. It may combine a native artifact with a web page or tabs from different browser profiles. A pane border/selection identifies the active target. Keyboard commands go to the focused pane, then the appropriate shared host command, with no duplicate dispatch. Closing a split arrangement restores its constituent tabs according to the chosen organisational action; it must not imply deleting content or signing out a profile. Shared dividers preserve minimum usable editor widths and offer a keyboard resizing path.

### 2.1.2 Address resolution, browser engines and profile boundaries

UIX-HOST-007 — Address submission resolves a typed destination before navigation. Ordinary HTTP(S) content, registered native app/resource links, host management pages and custom CUI surfaces have distinct namespace/permission handling. Preserve supported cui://, browse:// and 9to1:// compatibility routes through the central registry where they exist; do not infer privilege from a typed string or install an unregistered route handler. An address that cannot resolve remains editable with a specific reason. Navigation from a web origin to a native route does not transfer the destination's authority back to that origin.

UIX-HOST-008 — BrowserProfile is an identity/privacy/storage boundary for cookies, sessions, site permissions, extension state and credential integration. Profile is attached to the tab, so one workspace can contain multiple profiles. Changing workspace changes organisation; changing profile reopens the document under the destination profile without copying authentication material. The active profile must be discoverable near operations that can act under the wrong account. Existing profile names and pictures are presentation, not authentication identifiers.

UIX-HOST-009 — Firefox/Gecko and Chromium/Blink adapters retain separate private profile databases and renderer memory. Higher-level tabs, bookmarks, history and download records use the canonical host contracts. Switching engine keeps the tab identity, URL and organisational placement, then reconstructs the page through the chosen backend; DOM objects, JavaScript heaps and unsaved web application state are not promised to transfer. Warn about a known active form/upload risk before a reload that would discard it. A failed switch retains a truthful failed/preserved-page state and an explicit retry or return path rather than rewriting the saved preference as though activation succeeded.

UIX-HOST-010 — Per-tab engine choice and per-site default are separate commands. A remembered site rule records its match scope and profile context. Resetting that rule does not erase unrelated site permissions or cookies. Unknown, unavailable or incompatible engines remain visible as unavailable with a repair action. A fallback must identify the resulting engine and profile; no silent fallback may merge their private stores or misrepresent a page as having passed security checks under another backend.

UIX-HOST-011 — Browser capability coverage includes navigation/history, bookmarks, downloads, site permissions, privacy/data clearing, supported credential/passkey integration, developer tools, accessibility and supported extensions/media features. Preserve functioning donor capabilities except an explicit product replacement, including replacement of competing donor AI entry points by the shared Dulche experience. Maintain a capability matrix per engine/profile for features that differ. An unsupported WebExtension API, inspector function or media operation produces a specific limitation rather than an inert control or silent global disablement. Firefox-derived capability parity is evaluated at individual-feature granularity, and removing a donor feature merely because its default Firefox interface is replaced is not an acceptable omission.

UIX-HOST-012 — An engine update stages a new version, verifies integrity and runs relevant compatibility checks before promotion. Keep the prior validated version when rollback is supported. Promotion must account for profile-schema compatibility; rolling back a binary must not reopen an upgraded private database unsafely. Renderer crashes, extension failure and one corrupt private profile are isolated from canonical host data and other profiles/engines. Repair identifies which data is derived/rebuildable and which user data needs preservation.

### 2.1.3 Search, browser extensions and transfers

UIX-HOST-013 — SearchProvider records identity, query construction, optional suggestions, declared capabilities, privacy scope and availability. Ordinary search resolves a URL or provider query without invoking a model. Dual-provider search, where supported, creates two ordinary result tabs for the same query in standard Split View; it is not a second renderer or a blended fabricated answer. Sending a query to a second provider is explicit through the selected search mode/configuration, and a failed provider cannot block the other tab.

UIX-HOST-014 — Extensions declare compatibility with Gecko, Chromium, both, a native CUI surface or a limited subset. Installation, enabled state, engine availability, granted scope and actual execution are separate. Switching one tab's engine does not uninstall the extension or disable it globally. A CUI extension page runs under the extension's registered identity and capability scope, not as a trusted host page merely because it uses the shared visual system. Material extension identity/schema changes invalidate incompatible grants through the shared policy contract.

UIX-HOST-015 — Site Enhancer definitions retain identity, revision, site/profile match rules, enabled state, visual changes, any supported behaviour/script, declared permissions and provenance. Preview is reversible and confined to its selected target. AI-assisted authoring creates a proposed change that can be inspected before installation; it does not silently create a persistent script. Disabling or rolling back an enhancer restores the underlying site presentation where feasible without deleting site content or account state. Unsupported selectors and stale page structures are reported as partial applicability.

UIX-HOST-016 — Downloads progress through admitted, transferring, paused, interrupted, failed, verifying and complete states when supported by the transport. A completed record binds the actual file identity/location, bytes and originating source; a label or partial temporary file is not completion. Resume checks server support and existing partial data. Open/Reveal uses the owning file operation, and retry does not launch an unintended duplicate. Native drag-and-drop carries a typed canonical reference when both surfaces support it; web upload converts that reference into an explicitly permitted file transfer.

UIX-HOST-017 — Browser AI context references use stable tab/group/workspace or artifact identities and a captured source revision/navigation epoch. A title-only mention is insufficient to disambiguate two same-named tabs. Reading a page, controlling one tab, controlling selected tabs and operating Browse for a task have separate scopes. Navigations or profile changes invalidate stale element targets. Use semantic browser/app operations when available; a failed semantic call does not silently grant broader computer control. Consequential external actions retain their exact shared approval boundary.

Worked acceptance — Open a Write document and two web tabs from separate profiles; group them and make a split. Start a download, compose an unsent web draft and switch only one tab's engine. Verify the declared reload consequence, distinct cookies, preserved native document and truthful download state. Close/reopen the group after simulating one unavailable engine. The native document opens, the affected web tab offers recovery and no message, download or AI action is repeated without its actual retry semantics.

Additional acceptance — Test normal drag/reposition and keyboard alternatives with mandatory account access retained; follow the exact ten-tap username/password/Allow unlock; reject incorrect password and cancelled permission; apply an intentionally broken unrestricted layout; launch Customisation Recovery externally; preview and roll back only one changed control and then a whole checkpoint without losing tabs, projects, profiles or hub layouts. Check Firefox-donor parity against the audited capability matrix and verify source/provenance and staged updates independently for forked application and unchanged pinned engine components.

Source basis — Current Atlas host/browser/history/bookmark/inspector screens and final Haven composition; deliberately restated behavioural depth from [browse.complete.md](https://github.com/CroakyJake12/9to1/blob/1f92cd888f59025cc684f0720163efdbc580f8e3/docs/specification/owner-references/2026-11-18-interface-refactor/baseline/retained-pack/modules/browse.complete.md), particularly profile isolation, engine switching, typed browser entities, extensions and recovery. Earlier icon-only New Tab, duplicate-host and dated delivery instructions are excluded.

## 2.2 Home, New Tab and discovery

HOME-001 — Home Dashboard and New Tab are separate, complementary Haven experiences. They both use the full Home/Haven sidebar and the final modern Atlas design system, but have different purposes, route identities, content layouts and separately persisted personalisation. The Dashboard (home-dashboard) provides personal activity, tasks, progress, recent work and notifications requiring attention. New Tab (host-newtab) provides a start/search surface with clock/date, shortcuts and selected widgets. Preserve the final Atlas New Tab sidebar instead of reverting to its early icon-only rail. The later Atlas v3.3 instruction `dashboard.render = () => newTabSurface()` is the specific error to remove in Atlas v4; restore the separately defined Dashboard design. Both destinations remain discoverable in Haven navigation, alongside Apps, Explore, Models, Assistants, Specialists, Library and Mesh.

HOME-002 — Search and AI. Search is the default New Tab action. Ask AI is an explicit separate action leading to Spaces; selecting or entering a normal address does not silently invoke a model. Preserve the query and explain unsupported or invalid input. The prototype resolves only supported app/page examples; production must use the actual navigation/search service and must not pretend that an offline route example retrieved a web page. Source: host-newtab.

HOME-003 — New Tab customisation. Preserve the final Atlas visual presets Focus, Balanced and More widgets; backgrounds Neutral, Horizon, Paper or a user image; independent display of clock/date, shortcuts and each widget; and ordering, pinning and compact/wide sizes where supported. The New Tab layout and personalisation persist independently from the Dashboard's arrangement, even though both may reuse the same underlying widget providers, data sources and CUI theme. Changing either layout never silently changes the other, copies an artifact or deletes widget source material. Expose previews, versioned changes and targeted rollback consistent with Haven's recovery contract. Source: host-newtab-customise, host-newtab-widgets and final New Tab design, excluding the Dashboard-render alias.

HOME-004 — Equivalent move controls. Drag handles, visible move buttons and Alt+arrow keyboard actions update the same ordering. Reordering preserves identity and returns focus to the moved item. A first or last item exposes the correct unavailable direction. Hidden widgets retain their identity and valid preferences. Removing a shortcut or widget removes its presentation, not the target artifact. Source: final New Tab reorder implementation.

HOME-005 — Widget ownership and freshness. Widgets identify their owning app or source. Pins reference canonical content, including a Boards note, instead of copying it into an independent Home record. Loading, unavailable access, offline and failed refresh states are explicit. Live values carry source/freshness information where relevant. Sample calendar entries, task counts, study totals and the Atlas timer are fixtures; they must not become seeded user content or be presented as measured activity. Source: home-dashboard, host-newtab-widgets.

HOME-006 — Scrolling and narrow layouts. Home content scrolls natively within the available surface, with theme-aware scrollbar thumb and transparent track. Do not hide root overflow to conceal clipped content. Customisation dialogs and pickers keep their close controls, labels and actions reachable at narrow widths. Keyboard navigation reveals focused items without losing the user’s chosen scroll position unnecessarily.

HOME-007 — Haven Apps catalogue. App discovery uses search, package-state filters, pinned icon tiles and a compact all-app list consistent with the pinned Atlas visual layout. Atlas v4 overlays the seven approved hubs and connected project/resource views without losing search, favourites or the same canonical package identities. Train appears in Coordinate; AI Studio remains in Experiment. Distinguish Launch, not installed, downloading, installing, installed, update available, repairing, failed and unavailable when supported. Uninstalling an app does not silently delete its documents. Settings, Haven and Launcher consume one package/update service. Verify signatures, integrity, dependencies and compatibility before atomic activation, keep the last validated package when rollback is possible and report actual version/channel and operation state. Apps, hubs, feature shortcuts, Spaces and extensions are distinguishable entries, not duplicate installations.

HOME-008 — Explore. Explore is a conversational route into the app that owns the intended deliverable. Distinguish creating a game from writing a document about a game. If a request asks for different deliverables, present a clear choice rather than silently discarding one. Continue opens the destination with the original brief visible and dismissible; Back to Explore retains the conversation. Navigation alone does not create or mutate an artifact. The Atlas’s local intent matcher is an interaction example, not an inference implementation. Source: home-explore.

HOME-009 — Library and Mesh. Library indexes canonical artifacts across apps and opens their owning app at the exact identity; it is not a second storage authority. Mesh states belong to a specific device and distinguish connection, capability and granted scope. Viewing a device, controlling input, forwarding clipboard, forwarding files and shutting down that device are different actions. Source: home-library, home-mesh.

HOME-010 — Notifications. Notifications is the single owner-facing entry for activity updates formerly labelled Events. Each item preserves origin, timestamp, state and a link to the actual object or run. Mark read changes reading state only: it does not approve a permission, complete work or suppress a pending decision. Notifications opens its dedicated Settings destination. Source: host-notifications, settings-notifications.

HOME-011 — First run. Welcome, optional sign-in and model discovery are separate steps in a standalone pre-host window, without tabs, browser address controls or the loaded host shell. Local mode is a visible, first-class path. Ordinary local editing remains usable without an account, model, browser renderer or Files connection. Returning to a step preserves valid prior choices; incomplete optional setup is not reported as a connected or loaded capability. Source: onboarding.

HOME-012 — Haven/Home sidebar and Apps visual inventory, taken from the pinned Atlas v3.3. Screen IDs: home-apps, home-dashboard, home-models, home-assistants, home-specialists, home-library, home-mesh and final Haven shell layers. Below Haven's two-row chrome, the Home management region has a full-height left navigation sidebar identified by the 9to1/Home branding, with labelled core destinations Apps, Dashboard, Models, Assistants, Specialists, Library and Mesh & devices, plus the appropriate Explore, New Tab and other registered destinations; a workspace/local availability section; and footer Settings/account access. Selecting a destination highlights its actual page; the sidebar is not a separate Home application or a third host title bar. The Apps main panel is a scrollable workspace: a compact top context line and large Apps heading with Manage apps action; an app search field and installed/package filter; a Pinned section showing large app-icon tiles in a regular grid; and an All apps section of denser icon, name, concise description and launch affordance entries. Use consistent accent, spacing, card borders, typography, icon artwork and sidebar widths from the Atlas. Do not reproduce sample app counts or mock package statuses as live data. Atlas v4 incorporates the approved seven hubs, cross-hub project views, app renames and Train while preserving this modern discovery/management visual language. Hubs organise authorised references, not duplicate files or alter package ownership.

HOME-013 — Home Dashboard, distinctly retained from the originally registered Atlas design. Screen ID: home-dashboard; use its own pre-override page composition, not the later call to newTabSurface. The same full Home sidebar borders a scrolling dashboard main area. The upper content area has a date/context heading, personal greeting, a brief description and Customise action. Beneath is a responsive card grid with a wider Today/Planner agenda panel showing time-labelled upcoming activities, a narrower Study this week/progress tile with source and measured-versus-target values, then a Continue working heading and cards linking to recently used canonical documents/projects; an attention/approval strip leads to the actual pending action, and any contextual AI control remains an explicit separate destination. Maintain the original Atlas card layout and source attribution, but update any sample fixture labels, dates or percentages with real permission-scoped data in production. The Dashboard has its own widget arrangement, placement and saved revisions, not a clone of the browser's New Tab. Its cards may reuse New Tab widget components and existing providers without sharing a single layout state.

HOME-014 — Modern New Tab visual inventory, taken from the final Atlas v3.3 refinement. Screen IDs: host-newtab, host-newtab-customise, host-newtab-widgets. Use Haven's two-row browser chrome and the full Home navigation sidebar, not the earlier icon-only rail. A scrollable main canvas begins with a concise Home heading and a trailing Customise action. The start area centres the clock/time and date above a wide rounded search/address field with search icon, input and Go action. Below the field are explicit Ask AI and All apps buttons; entering an ordinary address/search never silently invokes a model. A Shortcuts heading precedes a row/grid of recognisable app-icon tiles and an Add shortcut affordance. A Widgets heading precedes individually owned cards with small source identifiers, concise titles, current contents and source-specific actions; examples include Planner Up next and a pinned Boards note, with additional focus timer, recent work, tasks and Study progress options. New Tab editing reveals visual preset choices Focus, Balanced and More widgets; Neutral/Horizon/Paper or uploaded-image backgrounds; visibility controls; separate Add widget and Add shortcut searchable pickers; drag handles, up/down or other move buttons and keyboard alternatives; widget size controls; remove controls; and Done to exit editing. Widgets retain canonical sources, real availability/freshness and layout identity through moves. Fixture dates, note text and static timers illustrate placement rather than guaranteed live information. The New Tab arrangement is persisted independently from Dashboard.

HOME-015 — Home customisation, extension and recovery policy. UIX-INPUT-003 — Touch, pointer and keyboard paths share semantics while using appropriate gestures. Dragging has an explicit threshold and capture; text selection and ink tools do not accidentally start object drag. A visible move/open/menu action covers operations otherwise dependent on long press, hover or drag. Timed destructive holds have an equally explicit single-activation review route. Motion, colour and exact pointer timing are never the only ways to discover state or complete an operation.

UIX-INPUT-004 — Async command state records accepted, pending, working, waiting, completed, failed, cancelled and uncertain outcome only where they represent real phases. Disable duplicate commit while the same operation is in flight, while retaining meaningful navigation/cancellation that is safe. After an uncertain acknowledgement, first reconcile the actual result instead of automatically executing a second effect. A failed overlay does not replace the recoverable underlying document with a generic empty screen.

UIX-INPUT-005 — Contextual AI follows the active artifact/range through a clear binding. Merely selecting another document does not silently continue an old approved action against the new one. A proposal retains its original target and can be reopened for review even after navigation. Access mode, human edit mode, layout lock, source permissions and exact approval remain independent. Hiding/repositioning the bar retains its draft and task; closing the host view follows the owning runtime and recovery contracts.

Worked acceptance — Open a context menu on a two-object selection, revoke one object and activate a permitted-looking action. Verify revalidation and explicit partial/blocked outcome. Then start a scoped AI proposal, change the active document and return. It still identifies the original target, and its action cannot be applied to the new document. Repeat with keyboard, IME composition, touch-sized controls, reduced motion and a narrow viewport; focus and cancellation remain usable.

Source basis — Current components/states/contextual chat/editor popup references and shared-ai.complete.md. These are common implementation contracts; application chapters define specialised text, ink, formula, graph and media interactions.

## 2.7 Mobile, foldables and external displays

<a id="h.f5gcc5o8b6gt"></a>

### 2.7.1 One product across mobile and desktop

MOB-001 — Mobile is a supported form of the same 9to1 product. Haven-hosted applications, separately installed applications and a hybrid installation share canonical app identities, artifact formats, commands, permission authority and supported runtime services. An app can be available through both entry points without creating duplicate documents or competing preference stores. Shared contracts remain subject to the operating system's real process and storage boundaries; a platform integration must document the broker/reference mechanism instead of assuming that separate packages can read one another's private data.

MOB-002 — The installation registry distinguishes a hosted feature, installed standalone package, shared dependency and shortcut. Opening an existing artifact selects the eligible owning implementation and preserves ArtifactID, revision and navigation context. Installing an additional entry point does not silently migrate or copy every artifact. Uninstalling one entry point explains its actual data scope and preserves independently owned shared data and surviving entry points. A schema upgrade coordinates compatible hosted/standalone versions before they write shared content.

MOB-003 — Phone, unfolded/tablet and external-display layouts are responsive compositions over shared state. Orientation, folding, resizing, connecting a display and moving a window do not create new conversations, restart an admitted operation, resubmit an assessment or discard an unsaved document. Persist canonical data independently of the transient view. Reconstruct only the visual surface and supported view state when the platform requires recreation. Preserve a meaningful focus or reading anchor and the current selection where possible.

<a id="h.rhq2f52f9ajx"></a>

### 2.7.2 Floating navigation bar, pins and More

MOB-004 — Use the owner's specified mobile layout: a persistent floating bottom bar with customisable, pinnable icon tiles and a More control exposing the complete eligible navigation catalogue. The bar is the primary mobile navigation system. The existing desktop visual language, theme, accent and canonical destinations carry across, with touch-appropriate grouping and spacing. The owner's 21 November direction supersedes older Atlas mobile navigation geometry where they conflict; it does not replace the desktop host with a bottom bar.

MOB-005 — A mobile bar configuration stores an ordered list of stable destination/action references, icon/label metadata, supported context and visibility preferences. Pins can target eligible apps, Spaces-owned destinations or registered commands; their identity is independent of their current label. Pinning Study, Translate or Actions does not turn that Space into an app package. Missing or unavailable targets remain identifiable with an explanation or repair path and do not silently retarget to a same-named result.

MOB-006 — Pin, unpin and reorder have visible and accessible controls. Dragging previews a change; cancellation restores the original order; commitment records one preference revision. More remains reachable and cannot be removed by pinning every slot. Its catalogue includes unpinned eligible destinations, useful search/filtering and clear installed, installable or unavailable states. Removing a pin changes navigation only. It does not uninstall an app, delete a Space or revoke an integration. Opening More preserves the current editor/composer draft and closes through standard Back/Escape and focus-return behaviour.

MOB-007 — The floating bar respects safe areas, gesture regions, cutouts, text scaling, orientation and the on-screen keyboard. It never covers the active composer, answer field, document selection, primary commit control or a permission decision. When the keyboard reduces available space, use a deliberate adaptive bar placement/compact treatment while retaining a reachable navigation affordance. Persistent means navigation remains consistently available during ordinary work; it must not force overlapping controls into an unusable viewport. Full-screen content has an explicit, discoverable path back to host navigation.

MOB-008 — Each tile has a useful accessible name and current/selected state. Touch, switch access, keyboard and assistive navigation invoke the same target as pointer activation. Icon-only appearance does not remove semantic labels or a way to discover the destination. Badge counts identify actual eligible events and cannot reveal protected content. Pin synchronisation, if enabled, preserves compatible canonical references while treating display arrangement and unavailable device-specific destinations explicitly.

<a id="h.f0buyn8p5tv9"></a>

### 2.7.3 Responsive editing and larger-screen assistance

MOB-009 — Preserve substantive app workflows on mobile through sheets, drawers, contextual toolbars and progressive disclosure. A desktop inspector can become a sheet; its commands and revision checks remain the same. Do not replace a rich editor with a read-only preview merely because the primary screen is narrow. Selection, undo, save/recovery, source inspection, permission review and access to the app's central operation remain usable. Responsive layouts reduce simultaneously visible controls before removing capabilities.

MOB-010 — Build has full supported editing and project workflows on mobile, including the corresponding Code, Sites and Stacks contracts. A nonblocking, dismissible hint may explain that a workflow is easier on an external display or an unfolded device when that advice applies. It must not prevent work, repeatedly interrupt the same session or assume that the current phone is foldable. The hint reports available options without pretending a display, keyboard, remote worker or compatible runtime is already connected.

MOB-011 — Games and Mini Computer are available on mobile. Their implementations adapt to lower processing capacity and memory through measured budgets, bounded caches, responsive rendering, virtualisation and supported quality/resolution or remote-execution choices. They preserve canonical game/project/guest identity and checkpoints. The device's actual runtime support determines which local guest or executable can run; a mobile product entry is not proof that every architecture or desktop binary is executable. Remote execution is identified and permissioned explicitly rather than disguised as local execution.

MOB-012 — Memory pressure and application suspension have declared recovery paths. Persist drafts/checkpoints at valid boundaries; release reconstructable views/caches before losing canonical work. Resume checks whether the service or remote task continued, stopped or became unknown. Recreating a view cannot blindly repeat a save, tool effect, model admission or paid request. A killed mobile process is represented as an interruption until durable evidence establishes the outcome. Foreground responsiveness has priority over optional background indexing, training or preload work.

MOB-013 — A platform capability matrix records each meaningful feature as supported, adapted, unavailable because of a specific dependency/platform limit, or deliberately omitted. Prefer feature preservation. A lower-value feature may be omitted when the porting cost is disproportionate, provided its user impact, alternative access path and scope are documented in the product decision and acceptance record. Do not use a general 'mobile version' label to omit central workflows, Build support, Games or Mini Computer after they have been expressly required. Reassess omissions when platform support changes.

<a id="h.kbg6ma77ylt8"></a>

### 2.7.4 Automations, mobile features and platform scope

MOB-014 — Automations exposes separate desktop and mobile controls that reflect the actual eligible triggers, targets, actions and execution conditions on each device. An automation's logical identity and task definition may be shared; its device binding, permissions, scheduler availability and operational restrictions are explicit. Editing the mobile binding does not silently change a desktop trigger. A capability unavailable on the phone can offer a clearly identified authorised remote-device binding where supported, rather than registering a local trigger that will never fire.

MOB-015 — Each device-specific automation records the relevant execution location, foreground/background eligibility, connectivity, power or other configured constraints, last observed availability and missed-trigger policy. The interface distinguishes Disabled, Waiting for eligible conditions, Unsupported and Failed. Scheduling intent is not evidence that the operating system accepted or executed the schedule. Source events and operation identities deduplicate a reconnect or handover. A shared automation running on more than one eligible device must have a declared ownership/lease or intentional fan-out policy.

MOB-016 — Home Launcher and Projector are mobile-origin features. Home Launcher provides the device home/launcher experience through supported platform integration and remains distinct from Home, the shared 9to1 control centre. Projector is the external-display/activity platform described in section 7.8, including its gallery and Desktop experience. A receiver or companion on a desktop/display supports the phone's Projector session; that does not rename the feature as desktop 9to1OS or collapse it into ordinary mirroring. Preserve compatible existing Launcher routes and Projector session records through the current canonical names.

<a id="h.dlpq1vpqb8hh"></a>

### 2.7.5 Atlas additions and acceptance

MOB-017 — The Atlas must include both desktop and mobile designs for the relevant journeys, plus unfolded and external-display states where their structure differs materially. Add the mobile floating bar, pin/customise/More, keyboard interaction, app editing, installation choices, desktop/mobile Automation controls, Home Launcher and Projector gallery/session/phone-controller/recovery designs. Retain the established shared style while making each form factor usable. Register new screen identities only with actual designs; do not assert that the pinned 251-screen snapshot already contains these newly directed states.

MOB-018 — Each added design pairs its ordinary state with the material empty, loading, unavailable, failed and recovery states. A mobile screenshot alone does not prove input ergonomics, runtime support or process recovery. Connect designs to the same functional requirements as desktop and record intentional adaptations or approved omissions. New owner requirements remain active while the corresponding Atlas additions are pending; a worker cannot dismiss them solely because the older screenshot has no matching control.

MOB-019 — Acceptance: pin Study, Translate, Actions and a standalone app; reorder them; remove a pin; open More and the same canonical document through both hosted and standalone entry points. Edit with the keyboard visible, rotate/fold and simulate view recreation. Verify the floating bar remains usable, the document and draft retain identity, one action is submitted, and pin changes do not install or delete content. Repeat with accessibility scaling and keyboard navigation.

MOB-020 — Acceptance: edit and save a Build project on a narrow screen, dismiss its larger-screen hint, then resume the same project on an eligible Projector display. Exercise a mobile Games workload and a supported Mini Computer workload under declared low-memory conditions; recover a checkpoint after interruption without inventing continued execution. Configure distinct desktop/mobile Automation bindings, deny one required mobile capability and verify an explicit blocked state without a false execution receipt or a duplicate desktop action.

Source basis — Owner clarification of 21 November 2026 supplies the floating mobile bar, pin/More model, installation choices, form-factor coverage, required mobile apps, device-specific Automation controls and mobile feature identities. Existing Atlas mobile screens and shared app/runtime contracts supply compatible foundations. These are newly adopted product requirements; no claim is made that the older Atlas or current code already implements the complete redesign.

## 2.8 Sounds and event feedback

<a id="h.swtf2alwp0se"></a>

### 2.8.1 Bank identity and unrestricted event assignments

SOUND-001 — Provide one shared sound-effect bank for 9to1 event feedback. It contains polished short effects with recognisable character and a useful variety of quiet, playful, electronic and more prominent choices. The shipped selection is original or appropriately licensed, with source/licence provenance retained outside ordinary playback UI. A bank entry is an actual playable asset with a stable SoundID, name, optional category/tags, duration, asset/version reference, supported format and availability. A category helps discovery; it does not restrict which event may use the sound.

SOUND-002 — The user can assign any available bank sound to each supported event independently. Initial event types include Message finished, Error, Question awaiting your input, Goal completed and Goal checkpoint reached. Use stable EventTypeIDs so visible labels can evolve without losing preferences. The same sound may be assigned to several events and different sounds to each; the product must not reserve a completion sound for completion events or an error sound for errors. Each mapping can also be muted without removing its saved SoundID or affecting other mappings.

SOUND-003 — SoundMapping records the event type, selected SoundID/revision policy, enabled state and the relevant preference scope. Settings exposes the event and its current selection together, with an accessible preview control, bank picker, search/filter and reset. Changing selection updates that mapping only. Preview plays the selected asset and causes no synthetic application event, task completion, notification read change or permission action. Stopping a preview is immediate through the supported playback controller.

SOUND-004 — The bank distinguishes installed/cached, downloadable and unavailable assets where those states exist. A missing asset retains the saved selection and offers repair or replacement; it must not silently overwrite the preference with a new sound. Built-in event sounds needed for ordinary local use are available offline. Optional additional packs, where supported, use the normal verified package/asset lifecycle and do not acquire access to conversations or notifications merely by supplying audio files. Asset replacement preserves identity only when it is a declared compatible version of the same sound.

<a id="h.le1p9wnv4rvc"></a>

### 2.8.2 Real events, delivery and interruption

SOUND-005 — Playback subscribes to the canonical event service, using EventID, EventTypeID, source identity, actual transition, scope, timestamp and delivery state. A message-finished event means the relevant response actually finished under the run/message lifecycle; a streamed fragment or paused tool operation is not completion. Question playback is for a genuine request awaiting the user's input, not every sentence ending with a question mark. An error identifies a real failure state; a retrying background attempt must not fabricate a new final failure simply to repeat the sound.

SOUND-006 — Goal completion and checkpoint sounds originate from the owning goal/plan state transition and evidence rules. A proposed plan, unchecked checklist item, model assertion of success or opened progress panel does not satisfy the event. Checkpoints have stable identities and revisions; report a newly reached checkpoint once for the relevant transition. Reopening or synchronising a completed goal cannot produce a second completion event. A materially new completion after an explicit reopen uses the goal owner's genuine new transition identity.

SOUND-007 — Deduplicate playback by eligible event/delivery identity across UI rerenders, retries and reconnects. The notification and sound services coordinate whether an event is delivered on one active device, selected devices or an explicitly configured broadcast. A historical event imported during sync is not automatically a fresh audible alert. An event suppressed by quiet settings retains its actual application state and follows a documented catch-up policy rather than replaying a burst of stale sounds when audio resumes.

SOUND-008 — Provide a global event-sound volume/mute and useful per-event enable/volume controls. Respect the user's effective device audio and quiet/focus settings through the real platform integration. Foreground speech, media, recording and accessibility output have a declared mixing/ducking policy; a notification must not secretly change the user's system volume. Important outcomes remain visible when sound is disabled or inaudible. Choosing the same effect for every event is allowed, so visual labels remain the authoritative way to distinguish them.

SOUND-009 — Simultaneous events use a bounded playback queue and a declared priority/coalescing policy that avoids a pile-up of overlapping clips. Preserve each underlying event and its visible notification even if several sounds are coalesced. A long preview can be stopped independently of event playback. Sounds cannot block the UI thread, inference completion or durable state commit; a playback error reports a scoped audio problem without converting successful work into a failed task.

<a id="h.6dzwis5febqc"></a>

### 2.8.3 Accessibility, state and acceptance

SOUND-010 — Controls expose sound name, duration, selected state, volume and mute semantically. Preview is user-initiated and clearly stoppable. The bank does not require hearing to identify an asset or configure a mapping. Optional haptic feedback, where supported, has its own choice and actual device availability; it is not treated as an audio asset or required as the only alternative. Shared themes can style the picker, but cannot silently replace a user's chosen mappings.

SOUND-011 — Mapping changes persist through the shared settings service with their actual scope. Account-level preferences may synchronise compatible SoundIDs, while device volume, audio route and platform-specific availability remain explicit. An unavailable sound on another device is shown as unavailable, with the original selection preserved. Reset identifies whether it resets one event, every event mapping or audio levels, and does not delete goal history, messages or the sound library.

SOUND-012 — Acceptance: assign the same sound to Message finished and Error and different sounds to Question, Goal completed and Goal checkpoint. Preview and stop each; mute one event; restart offline and verify saved choices. Trigger genuine events, retry/reconnect, reopen a completed goal and simulate a missing sound. Confirm only eligible new transitions produce audio, previews cause no product mutation, visual outcomes remain available and unavailable assets do not erase preferences. Exercise quiet settings, overlapping events, recording/speech, accessibility controls and playback failure.

Source basis — The owner's 21 November 2026 clarification requires a sound-effect bank and unrestricted per-event sound selection. The existing canonical event/notification, goal/plan and scoped preference contracts provide the integration boundaries. The bank assets and Settings/preview designs require creation and Atlas registration; this specification does not claim that those assets or screens already exist.
