## 1.1 Purpose

9to1 is a modular, highly customisable AI ecosystem built around user control, independent extensibility and cross-app continuity. Haven is the 9to1 browser and shared host: an application may run inside Haven, in its own standalone window, or in a hybrid arrangement. Haven must remain installed because it supplies essential shared components even when no Haven browser window is in use. The application and Haven coordinate their chrome so hosted views do not duplicate the host tab bar, profile controls or other shared UI; standalone views expose the controls they need. Home manages shared resources and preferences; Spaces owns conversations and agent work. Agents, documents, settings and other canonical resources retain their identities and work across compatible apps, placements and devices.

User control is a first-class product requirement within security, consent, hardware, service capability and paid-entitlement boundaries. Configuration should cover meaningful behaviour as well as appearance: for example, a user may keep an agent available in the background while having it suspend or release local compute resources during gaming. When the desired setting or feature is missing, 9to1 AI may help create a custom extension rather than require a core application change. User extensions persist across product updates with compatibility validation, controlled migrations and rollback, and require appropriate review and permission grants. Extensions cannot bypass security boundaries, make unauthorised payment requests or assign unpaid cloud-service entitlements. Local work, optional network services and AI assistance must expose truthful availability and state.

This is the active 9to1 Product Specification, maintained through the owner's section-by-section approvals. Its approved product and behavioural requirements are self-contained, including compatible feature coverage, persistence and technical contracts. The editable Interface Atlas defines visual and demonstrated interaction designs within the scope of the latest approved decisions. Implement approved requirements directly from this document and its linked active design and interaction contracts. Existing compatible capabilities and user data retain the preservation guarantees below.

This is a specification baseline, not a declaration that the application is complete. Design coverage, source implementation, tests and live operation are separate facts. The decision register identifies the limited policy questions that remain open; a question blocks only the operation whose correctness depends on its answer.

## 1.2 Authority and conflict resolution

AUTH-001 — Apply the latest explicit owner direction within its stated scope. This approved Product Specification governs required product behaviour; the currently adopted editable Interface Atlas governs visual composition and demonstrated interactions wherever consistent with later approved decisions. Atlas v3.3 is the pinned input snapshot. Atlas v4 is the editable review candidate produced from that snapshot and the owner-approved changes; it is not automatic design acceptance. The owner will edit and return v4.1 for the next pass. Capture, compare and reconcile that exact returned file before adopting it as the design input for that pass. Until then, the latest approved requirements govern conflicting, missing or superseded Atlas designs. Earlier renderers, discarded refinements, fixture limitations and implementation defects do not establish product requirements.

AUTH-002 — This document supplies the product behaviour, state transitions, data ownership, recovery and acceptance that the Atlas does not fully demonstrate. Its engineering clauses are explicit reconstruction decisions, not claims that the owner previously approved every technical detail. Where a clause conflicts with an authoritative Atlas interaction, preserve the Atlas contract unless later explicit owner direction supersedes that interaction, record the precise discrepancy and correct this document. Where the Atlas is internally contradictory or silent on a consequential policy, record a bounded decision rather than importing an old instruction silently.

AUTH-003 — The active source of product requirements is this specification together with its adopted interaction volumes, the applicable Atlas design, and explicit subsequent owner decisions. Existing implementation artefacts, prior dates, old requirement IDs, descriptive source ledgers and claims of being 'canonical' do not establish competing product authority. Historical operating prompts, model allocations, deadlines, quotas, process IDs and completed-work claims are not live instructions. Preserve compatible capabilities and data through explicit requirements and migrations rather than assuming historical claims are binding.

AUTH-004 — Repository source and tests establish implementation facts at a named revision. They cannot redefine the product merely because a legacy path currently works. Conversely, an Atlas screen cannot establish that a provider call, local save, permission check, model load or hardware configuration works. Change only the conflicting aspect of a capability and preserve its compatible behaviour, data and access paths.

AUTH-005 — Record a conflict with the exact source path or document section, source revision, disputed claim, affected requirement ID, Atlas Screen ID and proposed resolution. Distinguish a visual mismatch, missing behaviour, stale documentation, implementation defect and unresolved policy. Resolve by scoped authority; do not select whichever file has the newest modification time or the longest instruction block.

AUTH-006 — Preserve compatible existing capabilities even when the Atlas does not illustrate them. Before changing a feature, inventory its workflows, commands, shortcuts, integrations, supported formats, API behaviour, preferences and recovery paths. Classify each as conforming, needing adaptation, explicitly conflicting, additional compatible capability or incomplete. Omission from a condensed screen or chapter is not permission to remove functionality, discard data, substitute a stub or hide the remaining access path.

AUTH-007 — A historical technical schema can be useful implementation evidence without becoming a second product authority. Preserve existing serialized data and protocol compatibility through deliberate migrations. When a required detail is missing here, inspect the existing contract, choose a compatible reversible implementation where possible and record the choice. Changes to permissions, destructive semantics, external effects or irreversible formats require the corresponding explicit contract; hold that affected operation if the decision is genuinely unresolved.

AUTH-008 — The owner’s 21 November clarifications adopt automatic Chat/Agentic Chat/Worker/Design response presentation, optional Dreaming and preference-driven training, the mobile floating navigation bar, hosted/standalone/hybrid mobile installation, mobile Games/Mini Computer/Build support, separate desktop/mobile Automation controls, Home Launcher, Projector, Cumulative Context Compaction by default, an Assumptions Bank, a shared freely assignable sound-effect bank, and source-bound Specialist knowledge workspaces with independent web, general-knowledge and memory policies. Action logs, plans, goals and checkpoints must be retained as product features as well as preserved through compaction. These requirements supersede conflicting older notes within that scope. The corresponding new Atlas designs must be added and verified; their absence from the pinned snapshot does not defer the clarified product requirement. Existing code and historical design proposals remain evidence with their actual limits.

AUTH-010 — AI developers and other implementation workers may independently make routine, reversible technical decisions within approved requirements, including internal architecture, implementation detail, refactoring, tests and performance optimisation. Record consequential choices and supporting evidence. They must not silently alter approved product behaviour, remove or weaken a required capability, redefine the Atlas/specification authority, expand permissions or service entitlements, or make irreversible or materially risky changes without the owner's explicit approval. Where a proposed change affects fundamental product behaviour or conflicts with an approved requirement, present the difference, impact and options for owner review; continue unrelated safe work while awaiting that decision.

AUTH-011 — Markdown authority reconciliation. Treat .md files, including AGENTS.md, README.md, local design notes, generated specifications and working instructions, as subordinate to the approved product specification and the currently authoritative Atlas within their respective scopes. When an .md instruction conflicts with either, disregard only the conflicting instruction; do not blindly execute stale rules merely because the file is nearby, strongly worded, or labelled authoritative. Check the source revision and intent, identify whether it is outdated, partially compatible, a current operational safety rule, or an actual unresolved discrepancy, and document or clarify material ambiguity before proceeding. Preserve compatible and independently useful content. Remove authored .md instruction files whose substantive product directions conflict entirely with the approved specification, after checking for unique valid technical or operational information and migrating that information to the correct surviving owner as needed; remove/update links that would otherwise point to the obsolete files. Do not delete donor/upstream documentation, licence notices, historical evidence, source files or applicable operational safety instructions merely because they are Markdown. Carry out repository cleanup through the authorised source-management workflow with reviewable changes, not as an untracked destructive side effect of interpreting this document.

## 1.3 What constitutes a requirement

SPEC-001 — Stable IDs identify requirements, not paragraphs' positions. Do not reuse an ID for a different meaning. A later change records the old ID, its replacement and the scope of supersession. Screen IDs remain the Atlas identifiers, even if the visible title changes. Historical requirement IDs may be mapped to new IDs during repository reconciliation; their appearance in source code or an old audit does not make their old wording active.

SPEC-002 — Write product requirements as direct, affirmative instructions describing what to implement or how the feature behaves, without a separate 'must' versus 'may' obligation hierarchy. Replace permissive or mandatory modal wording with precise commands such as 'Implement', 'Support', 'Preserve' or 'Provide'. For genuinely experimental or technically uncertain capabilities, use 'Investigate and implement', requiring feasibility findings, an implementation where viable, and documented obstacles or fallback decisions where it is not. An expressly labelled proposal, example, fixture or source snapshot remains distinguishable from an approved requirement; an investigation instruction does not permit silently dropping the outcome. Apply this editorial rule throughout the specification without weakening the intended scope or safety requirements.

SPEC-003 — Define and ultimately verify complete feature behaviour: target identity, trigger, preconditions, visible outcome, canonical mutation or read, permission scope, persistence, cancellation/recovery, and applicable keyboard/touch access. Cover relevant empty, loading, denied, failed, offline, stale and conflict states; a visual mock-up, happy-path button or success toast alone is not feature completion. Achieve completeness through an efficient build-and-review pipeline rather than blocking the initial implementation on exhaustive polishing: a rapid, competent implementor produces a working integrated feature, then a separate careful auditor/tester checks code and requirements, exercises edge cases, reports defects and drives fixes. When parallel workers are available, organise these roles as a continuous pipeline, including the Sunday development pass. When only one worker is available, complete the rapid implementation pass first and then conduct a distinct extensive review and test pass. Neither speed nor review status excuses knowingly unsafe or destructive changes; distinguish implemented, audited and accepted states.

SPEC-004 — Requirements are independent of worker branding and temporary machine allocations. Qwen, Astra or another worker can implement or review them using the current repository operating contract. The product does not depend on a particular coding assistant remaining available, a dated model alias, an assistant quota or a specific local process ID.

SPEC-005 — Existing operational instructions still govern safe source custody, resource constraints and build coordination where applicable to the actual environment. Product precedence does not authorize a worker to overwrite another worker's files, stop a resident inference process or deploy a service. Qwen's later documentation pass must separate product authority from current operational procedures and historical evidence.

SPEC-006 — Donor-first implementation. Avoid building mature applications and engines from scratch where established source code can deliver required capability. Identify the upstream donor, licence, version/revision and applicable source components for each app or subsystem, and evaluate separately whether each component must be modified. For a component used unchanged, pin an exact upstream revision using a reproducible source dependency such as a Git submodule or equivalent fetch/lock mechanism; integrate its build and packaging into 9to1 so end users never need to install the donor separately. Pinning source does not mean silently using moving branches or relying on a user-installed dependency. For a donor component requiring source modification, including replacement of its app UI with CUI, maintain a fork with its complete source tree present inside the 9to1 repository, preserving original notices, provenance and a workable upstream-update process. Do not treat a patch-only overlay or linked external repository as satisfying this full-tree fork rule. Evaluate separately coupled parts such as Firefox application code and Gecko engine: modify/fork the portion that needs modification and pin the portions that truly remain unchanged, after verifying the architecture and build can support that separation. Track licence compliance, source integrity, vulnerabilities, upstream security fixes, build reproducibility, compatibility and feature parity for both pinned and forked donors.

SPEC-007 — Implementation-language priority. Deliver the full approved 9to1 feature specification before attempting broad language migrations. Prefer C# as the eventual common implementation language, while retaining C++, Rust, JavaScript or other existing donor/backend languages whenever migration would require rewriting a whole backend or substantial unnecessary effort. This permission does not weaken the requirement that first-party app UI and orchestration use CUI where applicable, or change the donor source-modification policy. Language uniformity cannot block feature completeness, reliability or performance.

SPEC-008 — Post-completion C## roadmap (future scope, not a current implementation dependency). After 9to1 reaches feature completion, investigate and implement C## ('C-Sharp-Sharp'), a fork-based evolution of the C# language/compiler ecosystem. Keep syntax recognisably close to C#; improve language quirks and provide lower-level control, with Rust-class performance as a measurable target rather than an assumed result. Preserve straightforward upstream C# source compatibility and a maintainable process for integrating later compiler/language/runtime changes. Include Dulche as a built-in library. Treat compiler, runtime, standard libraries and tooling as distinguishable components, changing only what is necessary. After C## itself is ready and validated, plan and execute a staged port of the entire 9to1 ecosystem to C## with compatibility tests, donor considerations and rollback. Both C## development and ecosystem migration remain out of scope for the present feature-completion phase and cannot delay it.

## 1.4 Product boundaries and canonical ownership

PROD-001 — Haven is the 9to1 browser, shared host and central management experience. Home is a set of management views within Haven, not a separate application or hub. Home Dashboard and browser New Tab are distinct destinations: Dashboard is a personal activity/briefing workspace; New Tab is the browser's start/search page. They reuse the Haven sidebar, CUI components, widget providers and canonical resources without sharing one layout identity. Haven remains installed to supply shared components even when all applications run standalone. Browse provides the browser's web-content functions. The late Atlas v3.3 runtime override that makes Dashboard render the New Tab screen is specifically superseded by the owner's decision; correct that in Atlas v4 while preserving the remainder of the approved default design.

PROD-002 — CUI is the unified first-party interface, theme engine, application interaction and orchestration system. Owned app UI uses CUI contracts across hosted, standalone and hybrid compositions. Typed platform, renderer, persistence, native integration and donor-engine code remains infrastructure behind explicit boundaries, not a competing UI language or separate permission authority. The editable HTML Atlas is a design reference, not a production technology mandate. Rendering, computation and engine adapters can be implemented in appropriate source languages under the donor-first and implementation-language policies, but cannot replace CUI as the first-party interface contract. User-authored code, sites, games and imported content are not restricted to CUI.

PROD-003 — Dulche owns the shared AI/runtime boundary, including model catalogue, routing, admission, TaskRuns, memory, tools, actions and agent integration. It consumes Haven's canonical permission authority, while owning apps and the runtime enforce grants and protected-action checks. UI surfaces request and display these operations rather than fabricating state or creating competing brokers, grants or retry policies. Provider and engine adapters can hide their implementation and transport details from everyday user workflows.

PROD-004 — Spaces owns conversational work and its durable activity. Editors own their documents and their native editing models. Contextual AI targets the open artifact and revision, using the same shared runtime and grants as Spaces. An AI-generated file remains the same canonical artifact when previewed, opened in an editor, revised, referenced in conversation or exported.

PROD-005 — Hubs are discoverability and workspace structures, not separate data stores or automatic shared-engine boundaries. Develop groups Code, Sites, Data, Stacks, Games, Virtual Device and Terminal, with Prototype as a feature within Develop rather than a separate app. Code, Sites and Stacks can share a deeper project engine/interface while other hub members retain appropriate independent models. Experiment contains AI Studio, Play and Story Sequences. Assistants and Specialists remain shared resources whose conversations are owned by Spaces; AI Studio creates and tests their definitions. Shared settings, permissions, files and projects have one canonical owner, even when they appear in several hub or app views.

PROD-006 — Hosted, standalone and hybrid modes use the same canonical app, commands, data, persistence and runtime contracts. Haven and the app coordinate window chrome: hosted views omit duplicate tabs, top profile controls, model selection and other Haven-provided elements; standalone views expose what they need. Hybrid apps can operate both inside Haven and independently while preserving state, identity and active work.

PROD-007 — Local-first work means supported local reading, editing, saving and recovery remain usable when optional network or AI services are unavailable. It does not mean every cloud-only integration is secretly available offline. Display actual availability, queue only operations that support it and preserve local results independently of sync or publish status.

PROD-008 — The suite includes every family in the Atlas coverage index. Delivery through increments does not reduce the final scope. More detailed application contracts take precedence over generic editor defaults within their own scope. A narrower mobile view retains essential operations and identities through deliberate drawers, sheets and navigation; it does not become an unrelated product.

PROD-009 — Space taxonomy. Study, Translate and Actions are specialised Spaces within Spaces, sharing conversation, configuration, permissions and runtime lifecycle; they are not standalone app/package identities. Actions supersedes the older Space label Tasks without changing saved identities. Planner tasks, TaskIDs/TaskRuns and Present's Actions graph remain distinct concepts. Study reuses Decks (formerly Cards), Forms, Write and Planner through their owning-app contracts.

PROD-010 — Standard hub catalogue. Coordinate contains Spaces, Voice & Vision and Train. Create contains Frame (formerly Picture), Wave, Motion and Sculpt. Develop contains Code, Sites, Data, Stacks, Games, Virtual Device (formerly Mini Computer) and Terminal, plus the embedded Prototype feature. Organise contains Connect, Planner, Files, Automations, Maps, Projector, Launcher and Collection (formerly Shelf). Work contains Write, Present, Boards, Canvas, Flow, Decks (formerly Cards) and Forms. Experiment contains Play, AI Studio and Story Sequences (formerly Paths). Sculpt is the full Blender-derived application, implemented as the Blender fork under SPEC-006; its scope is not limited to a Games asset workspace. Connect is the canonical app/package name; Mail is its email surface and compatible alias, not another application or data owner. Train is a distinct application whose approved initial scope is fine-tuning, Dreaming, evaluation and checkpoint management; general pretraining and arbitrary direct manual weight editing are deferred beyond that initial scope. LEARN-001–012 remain required, including real supported parameter updates. Within Coordinate and Experiment respectively, Train owns those training workflows while AI Studio concentrates on experimenting with, defining, testing and evaluating AI agents, tools and integrations, without becoming Train's substitute. Admin is its own dedicated hub for Admin and system-management interfaces. The OS is platform infrastructure, not a hub app. Replay is a shared cross-app history, checkpoint and reconstruction feature, not a standalone app. Preserve existing names as compatible routes and migration aliases where appropriate, while the new names govern user-facing navigation.

PROD-011 — Hub integration and cross-hub continuity. Hubs provide a shared visual navigation surface and useful combined project/resource views, not merely lists of app shortcuts. A project can present its Sites, Stacks, code, tasks, images, audio and other authorised resources together with their real owning-app identities and exact revisions. A resource or app can appear in more than one hub or project view without copying its underlying content or fragmenting its data. Some hub apps are independent, some share components/frameworks, and tightly integrated suites may share an overall editor or engine. Hubs never force unrelated apps to use a common internal engine, nor may hub membership restrict a resource that the user is otherwise authorised to find or open.

PROD-012 — Opt-in hub customisation and safe defaults. Ship the standard hub catalogue and app placements enabled by default, with user hub editing disabled until the user explicitly enables 'Customise hubs' in settings or a deliberate equivalent configuration action. Only in that mode may the user create, rename, arrange or remove custom hubs, or reassign and cross-list apps, using discoverable editing controls and accessible non-drag alternatives. Routine navigation, tab dragging or app usage must not accidentally change hub membership. Disabling hub customisation immediately returns the normal standard hubs and placements in the interface without deleting, resetting or overwriting the user's custom layout, custom hub identities or app placements. Re-enabling restores the previously saved custom arrangement, including its order, subject to truthful compatibility recovery if installed apps or capabilities have changed. Offer reset-to-defaults as a separate explicit, appropriately confirmed action; resetting hub presentation must never delete app installations, user projects, data, shortcuts or settings outside hub arrangement. Persist custom layouts with versioned migration/recovery so app updates do not silently discard them.

PROD-013 — Shared extensions and hub capabilities. Custom extensions can add compatible commands, components and integration points across one or several apps and hubs through explicit grants and versioned extension contracts. Hubs can host optional shared search, recent projects, project activity, pinned views and cross-app actions while delegating mutations to canonical owners. Hiding, removing or rearranging a hub entry affects presentation and membership only; it does not uninstall the app or delete the resource. Changes remain reversible and do not bypass permissions, source integrity or service entitlements.

## 1.5 Shared product principles

UX-001 — Use concise, familiar, functional UI labels. Prefer the shortest clear action or object name ('Play', 'Open', 'Save', 'Stop') over a descriptive sentence. Put supplementary explanation in an optional tooltip, help panel or contextual disclosure when needed; for important permission, payment, destructive-action or recovery consequences, show the essential information at the point of decision rather than hiding it on hover. Do not use AI-generated-sounding marketing slogans, filler, needless metaphors, ornamental prose or overengineered interface copy (for example, 'Spaces, chat your way'). Clear, natural product language takes precedence over branding flourish. Keep tooltips brief and accessible on keyboard and touch as well as mouse.

UX-002 — One control has one primary operation. Opening a disclosure, moving focus, changing tabs or dismissing a menu does not commit an unrelated mutation. Draft, pending, applying and active values remain distinct where configuration requires an explicit commit. Navigation, theme changes and panel placement must preserve identities, active work, user content and valid preferences.

UX-003 — The interface reports actual state. Saved locally, syncing, synced, pending apply, loading a model, running, stopped, failed and awaiting approval are distinct. Show useful progress only when it is grounded in real work. Unknown totals or estimated time remain labelled. A preview, cached result or historical success cannot masquerade as the current result.

UX-004 — Recovery preserves the user's effort. Failed admission retains drafts and attachments; failed export retains the native artifact; failed reload retains or restores the last usable configuration where possible; conflicts preserve recoverable versions. Retry must reconcile an uncertain operation before performing a duplicate external effect.

UX-005 — Keyboard, pointer and touch access share the same command semantics. Focus and selection are not execution. An accessible visible alternative exists for operations otherwise requiring drag, hover or a timed hold. State remains understandable without colour, motion or a tooltip alone.

UX-006 — The selected theme and accent style the interface. They do not rewrite authored document typography, paint colours, media, chart semantics or imported content. A quieter layout does not remove features. Adapt placement and grouping while preserving discoverability and accessible names.

UX-007 — User agency and configurable defaults. Provide sensible, safe defaults without treating them as compulsory. Give users meaningful control over interface, workflows, automation and resource usage through explicit, discoverable settings, and support permission-reviewed custom extensions where the standard feature set does not meet a need. Preserve reversible configuration, recovery and cross-app continuity. User agency operates within enforced security, privacy, technical compatibility, provider availability, and purchased-service entitlement limits; a preference or extension cannot grant itself protected permissions, unauthorised payments or unpaid service capacity.

## 1.6 How to use this document

Start with authority and product boundaries, then the relevant shared interface/runtime contract, the owning app section and its Atlas Screen IDs. Read the applicable acceptance scenarios before changing code. The full screen index records every one of the 251 registered screens exactly once; other sections may reference a screen repeatedly without creating another identity.

For ongoing implementation, load the relevant specification sections, shared/global rules, applicable Atlas screens, interaction references and dependencies for the task instead of repeatedly inserting the entire specification into each agent's context. Keep a verified index of requirement IDs, ownership and cross-section dependencies; retrieve deeper or adjacent sections whenever the operation crosses their boundaries. A focused context is not permission to overlook global authority, access, safety, data-preservation, integration or acceptance obligations. Full-document audits and initial reference-reconciliation passes still inspect complete coverage when required.

Open the editable Atlas file locally and use its screen navigation or #Screen-ID route. The source hyperlink identifies the exact repository artifact; a GitHub file page is not a running hosted Atlas. Preserve existing route aliases when a title or navigation label changes. A new required visual surface must receive a registered ID and an explicit design before it is reported as Atlas-covered.

The decision register distinguishes open product policy from ordinary engineering choices. Continue independent implementation when a decision blocks one capability. The acceptance chapter defines what evidence establishes completion. The adoption chapter supplies Qwen's later reference-reconciliation task; it does not claim that the repository has already been updated.

AUTH-009 — The detailed interaction chapters and the three native Spaces, Editor and App interaction volumes linked from the Interaction control index are normative parts of this specification. Their IX identifiers define each control's mouse, keyboard, touch, drag, state and integration behaviour; product and runtime requirements remain in force. The Comic owner mockup supersedes the Cinematic design. Atlas v4 must register approved design changes and update affected interactions, screen mapping and identifiers without discarding still-valid controls. Repository Markdown instructions remain subordinate under AUTH-011.
