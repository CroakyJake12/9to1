## 9.1 Reading the register

COVER-001 — The register below contains all 251 unique Screen IDs from the [pinned editable Atlas](https://github.com/CroakyJake12/9to1/blob/1f92cd888f59025cc684f0720163efdbc580f8e3/docs/specification/owner-references/2026-11-18-interface-refactor/design/9to1_Interface_Atlas_v3.3_Editable.html) exactly once, with source titles preserved and later owner-directed names identified explicitly. Each row identifies its owning chapter, explicit requirements and an acceptance focus. Shared CUI/accessibility/state, runtime and permission rules apply where relevant, even when a row names only its primary contract. A row records design traceability, not implemented or verified status.

COVER-002 — Product surfaces, design-system reference screens and theme-reference imagery have different purposes. The 251 records comprise 233 product surfaces, eight design-system references and ten theme-reference image pages. Reference entries guide components, materials and original assets; they do not require shipping the Atlas editor or reference images as app pages. Compatibility IDs may intentionally resolve to the same canonical experience.

COVER-003 — Use the Screen ID to open the local Atlas. Use the owning chapter to read the full behaviour and acceptance, then verify the final active screen composition. Older source labels embedded in a manifest row are provenance and do not override the final Atlas refinements or this document’s authority rules.

COVER-004 — When implementation begins, attach code owner, canonical command/state, permission boundary, persistence, responsive/keyboard/failure coverage and actual evidence to the relevant requirement and screen. Newly required product screens receive registered IDs; until designed, label them explicitly as design pending. Do not claim the existing register illustrates a new topology or scheduler panel that is absent from the Atlas.
