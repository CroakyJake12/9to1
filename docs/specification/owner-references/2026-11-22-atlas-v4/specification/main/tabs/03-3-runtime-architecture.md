This chapter specifies production behaviour. The [Atlas](https://github.com/CroakyJake12/9to1/blob/1f92cd888f59025cc684f0720163efdbc580f8e3/docs/specification/owner-references/2026-11-18-interface-refactor/design/9to1_Interface_Atlas_v3.3_Editable.html) supplies the authoritative interface and interaction model; its fixture values and local preview handlers do not demonstrate a production service. ## 3.1 Shared architecture and canonical ownership

RT-001 — CUI is the public interface system for 9to1 application surfaces, including generated interfaces. Shared components expose typed state, semantic roles, accessible names and actions. Haven hosts the interface; Home manages shared services and user-facing configuration; Dulche brokers model execution, requests, tools and coordinated agents, using Home’s canonical permission authority and the owning app’s protected-action enforcement. An app must use these shared contracts instead of silently introducing another model catalogue, permission broker or document store.

RT-002 — Every app and resource has stable identity. Keep AppID, artifact identity, revision, conversation/thread identity, AgentID, TaskID, RunID and action identity distinct. Human-readable titles, usernames, file paths, tab labels and display names are mutable presentation or location data, not identity. A reference from Home, Files, Spaces or an embedded preview resolves to the same owning artifact and revision. Opening a different view does not duplicate the artifact.

RT-003 — The owning app exposes typed operations for its supported create, open, edit, import, export and navigation actions. An operation declares its input, target, expected revision, permission needs, result and failure states. Manual local authoring and saving remain available when optional AI, cloud accounts, remote storage or browser services are unavailable, except for operations that actually require those dependencies. Unavailable capabilities have a scoped explanation and recovery path.

RT-004 — View state, unsaved authoring state, committed artifact revisions, runtime work and published output have separate lifecycles. Closing a view neither approves a queued action nor stops a background run. A view that reopens reconnects to an existing task or artifact; it does not submit the previous command again. Switching theme or layout cannot alter authored content, grants or runtime configuration.

RT-005 — Shared services advertise version, compatibility, capabilities and actual health. Dulche reports Starting, Ready, Degraded, Restarting and Stopped where those states apply. Failed optional services leave unrelated local work intact. A compatibility failure cannot be disguised by launching an untracked private service or silently resetting durable configuration.

RT-006 — Donor engines and platform adapters may provide internal infrastructure behind typed boundaries. They do not establish a second public application language or a second permission authority. Existing compatible functionality and formats remain available until a specifically identified requirement supersedes them. Migrations preserve canonical IDs, content, author choices and recoverable prior data. A successful code conversion alone does not establish feature parity.

Acceptance: open one artifact through its app, Home, Files and a conversation reference; confirm one identity and revision. Disable AI and network services, edit and save locally, then restore the host. Confirm the same artifact and run records return without duplicate requests. Deliberately introduce a service compatibility mismatch and verify a scoped repair state with preserved documents.

### 3.1.1 Service ownership and application boundaries

ARC-001 — Home Core owns discovery and lifecycle of the shared local services, including the permission authority and the managed Dulche broker. CUI owns first-party application structure, styling, app-facing state, interaction behaviour and orchestration. Dulche executes admitted model and tool work through the same Home permission authority and owning-app enforcement. Owning apps maintain their canonical artifacts and domain operations. A shared infrastructure process may implement several of these responsibilities, but the contracts remain separate: a UI subscription cannot become an execution grant, a model result cannot become a storage commit, and a component registry cannot become an account authority.

An implementation boundary must identify its owner, allowed callers, input/output contracts, lifetime, authoritative state, derived state and failure boundary. Typed infrastructure may implement rendering, storage, computation, native integration, inference and retained donor engines. Moving app-specific presentation or interaction orchestration into C#, AXAML, HUI, HTML, CSS, JavaScript or a generic Object wrapper does not become compliant by calling it an adapter. This restriction concerns 9to1's own UI; it does not forbid supported languages inside the user's code, websites, games or imported content. CUI and its low-level renderer must preserve authentic document, media and browser capabilities rather than replacing them with screenshots or text-box approximations.

ARC-002 — Use one canonical app registry. An AppRegistration contains AppID, package/version, supported artifact types and schema ranges, launch/open/create routes, typed action catalogue, required service/capability versions, optional capabilities and supported host compositions. Its name, icon and preferred navigation label are presentation metadata. Installation and registration do not launch the app or grant every action. A route resolves the app and target before a view opens; if the owner is missing, the original target, requested mode and draft remain recoverable during installation or repair.

An OpenArtifact request distinguishes Original, Reference and IndependentCopy intent. It identifies ArtifactID or a provider-qualified resource reference, desired revision or current-revision policy, owner, requested edit/view mode and navigation return context. A stale thumbnail is never the resolved artifact. An embed uses the same canonical open contract and an explicit host-composition contract; it may restrict available actions but cannot expand source permission. Hosted and standalone forms attach to the same service/state interfaces. App-level headers must not reintroduce host controls already owned by Haven.

### 3.1.2 Logical operation and result envelopes

ARC-003 — Every mutation-capable action exposes a typed command contract. The following logical fields are required where applicable; a field may be absent only when the action schema declares why it does not apply.

| Column 1 | Column 2 |
| --- | --- |
| Field | Meaning and invariant |
| ContractVersion, ActionID, ActionVersion | Select the exact schema and semantic operation; a renamed label does not change ActionID. |
| OperationID | Stable identity for this intended effect across transport retries; a different effect requires a different identity. |
| CallerIdentity, Principal, Scope | Authenticated caller and acting account/namespace; caller-supplied text is not authentication. |
| TargetReferences | Canonical resource/object IDs and owning app/provider; paths and titles are supplementary. |
| ExpectedRevisions | Preconditions for every mutable target or an explicitly declared snapshot/query condition. |
| Arguments | Validated typed input; preserve user-entered drafts separately from successfully converted values. |
| RequestID, RunID, ParentOperationID | Optional causality linking the action to AI work, automation or another command. |
| ApprovalReference | Broker-issued decision for this action where required; possession alone does not bypass current revalidation. |
| CancellationScope, Deadline | The requested cancellation identity and applicable expiry; not a persisted process-local token. |
| IdempotencyPolicy | Declares whether repeated delivery is safely deduplicated, reconciled remotely or unsupported. |

The result envelope contains OperationID, status, target identities, resulting revisions, confirmed effects, warnings, per-target outcomes and a structured error or blocker when relevant. A long operation returns JobID plus observable state and cancellation support rather than a premature success result. Created references are returned only after their authoritative owner accepts creation. A preview or proposed diff returns proposed references explicitly and does not occupy the successful mutation-result field.

ARC-004 — Distinguish transport success, command acceptance and effect completion. Expected operational failures return stable categories such as InvalidArgument, UnsupportedCapability, DependencyRequired, PermissionRequired, PermissionDenied, RevisionConflict, ResourceUnavailable, QuotaExceeded, Cancelled or OutcomeUnknown. Include the failed stage, safe target metadata, retryability, preserved source state and any completed effects. A UI must not infer success from HTTP success, a non-null object, an exit-free callback or a message containing the word saved. Preserve provider-specific error details behind a safe diagnostic reference without requiring consumers to parse prose.

Read/list operations declare snapshot or live semantics, pagination and stable cursor behaviour. A cursor binds to the relevant query, ordering and scope; it is invalidated or revalidated if that scope changes. Empty is a confirmed result with zero eligible records. Denied, disconnected and unsupported are different results. Filters and search must not leak inaccessible names, counts or cached previews. A UI refresh subscribes to the same records rather than appending duplicate entities after each page or reconnect.

### 3.1.3 CUI syntax, declarations and component identity

ARC-005 — The CUI visual/structural primitive vocabulary is Page, Container, Text, Image, Audio, Video, Object, Button, Input and Layer. Type selects registered behaviours such as Container Grid, Vertical Stack, Horizontal Stack or Absolute and Input Text, Checkbox or Slider. Themes, Styles, Property regions, Variables, Definitions, Prefabs, ActionEvents, conditions, repeats, imports, keyframes and anchors are declarative constructs, not a second native-control vocabulary. The public parser must reject donor tags such as StackPanel or TextBlock, donor namespace escape routes and attached-property syntax masquerading as CUI. A migration utility may read legacy markup to emit CUI; normal compilation/loading must not silently fall back to the legacy language.

CUI uses strict XML-like nesting. Built-in keywords are case-insensitive; user-defined identifiers, component names and symbols are case-sensitive. Quoted values retain their literal content. Colon assignment shorthand is equivalent to the corresponding long attribute form when unambiguous; unquoted underscore-to-space shorthand may resolve only when exactly one registered symbol matches. If both Vertical_Stack and Vertical Stack exist, the shorthand is an error. Comments use the declared CUI comment delimiters and do not nest or create runtime nodes. Formatting whitespace is discarded outside text-bearing content; Text exposes an explicit preserve-whitespace mode. Escaping and formatting round-trip significant punctuation deterministically.

ARC-006 — Definitions create reusable elements or registered Types without rendering an instance at declaration. A Definition cannot silently shadow a built-in primitive or export a forbidden donor taxonomy as aliases. Imports identify package/version and resolve symbols deterministically; ambiguous imports require explicit qualification. Cyclic Definition, Prefab or required import dependencies fail before activation. Compiled output records source locations, language version, component registry/ABI requirements and required capabilities. Missing required capabilities are compatibility failures; unknown optional metadata may be preserved without pretending it is implemented.

Page establishes an addressing scope. ID and Name are aliases for one identity field; an instance has at most one. IDs are unique within their scope. Groups deliberately address multiple members, but an ID and Group cannot use the same identifier in the same scope. A dynamic Prefab/Definition instance has its own internal scope; access to another scope must explicitly identify the containing instance. Node handles refer to that instance and lifetime generation, so a destroyed-and-recreated node cannot inherit a stale event target or mutation simply because its textual ID was reused.

ARC-007 — A dynamic Prefab shares implementation but has independent mutable state per instance. A static Prefab shares declared internal runtime state within its documented runtime namespace; placement, parent, size and host activation remain instance-specific. Static sharing is not automatic disk persistence or cross-process synchronisation. Shared account preferences and canonical documents still belong to their services, not an accidental static variable. Conflicting per-instance mutable inputs must be rejected for static Prefabs or represented as independent dynamic instances. Inputs, outputs/events and optional content slots are declared typed contracts; no implicit capture of arbitrary caller state is permitted.

Text is literal content. Assigning markup-looking characters to Text displays those characters. Children is intentional structured CUI content parsed within the host's permitted component/property/action set. Replacement is staged and validated before it replaces the live tree. Failed parsing, missing capabilities or invalid action bindings retain the prior valid tree, input, selection and focus and return a typed failure. Appending valid Children has an explicit insertion boundary and new stable identities. A model response or imported file must not enter Children merely because it contains angle brackets.

### 3.1.4 Property resolution, reactivity and input

ARC-008 — Resolve every effective presentation property through one typed CUI cascade, from lowest to highest: built-in default, inherited Theme, Type/Definition default, explicit instance value, scoped Property region, active Style/event overlay. Direct runtime assignment changes the stored explicit value; it does not create a secret precedence level above overlays. Equal-specificity declarations resolve by documented CUI scope/source order. Renderer selectors, donor themes, resource loading order and native local-value priorities cannot defeat this cascade. The inspector exposes the effective value, winning source and masked stored values.

A hovered control illustrates the invariant: while a hover Style supplies a blue background, a valid command changes the stored background to green. It remains blue until hover ends, then resolves to green rather than restoring an obsolete snapshot. Group mutations validate the entire intended target set before a persistent change; a required incompatible member causes a typed error rather than silent partial application. Active group Styles also apply to subsequently materialised compatible members. Theme changes invalidate presentation dependencies without rewriting authored content, canonical document revisions or application permissions.

ARC-009 — A live binding subscribes to a CUI-visible value and invalidates only affected expressions/properties/subtrees. A static reference is evaluated on load or explicit refresh and retains that result when an unrelated live binding updates the same element. Compiler/build tooling supplies change notification for supported fields, properties and collections; ordinary binding must not poll every frame. A short-lived local variable cannot silently become durable observable state. Derived values declare their recomputation and dependencies; dependency cycles are rejected statically where possible and become recoverable typed errors otherwise.

Display bindings are one-way by default. Writable Input value properties may write back only when the binding is writable and conversion succeeds. During invalid numeric input, keep the entered string and validation message while the canonical typed value remains unchanged. Explicit write-back-disabled or static bindings cannot mutate their source. IME composition is not final input: validation and shortcuts must not prematurely commit an intermediate composition. The context-limit field adds its existing pending/apply transaction on top of this binding behaviour; successful integer conversion alone is not permission to reload a model.

ARC-010 — Conditional composition instantiates the selected branch and removes the other structural branch. Identity-preserving Repeat requires a stable item key; it must not associate a row's draft, focus or selection with another object because the collection order changed. Virtualisation may recycle visual objects only through an explicit rebind/reset that clears stale event, validation and accessibility state. Unmaterialised items remain canonical records and remain discoverable through semantic navigation. App state that must survive branch removal belongs to a declared owning state record, not an assumption that invisible nodes still exist.

Active, Hidden and Interactive are independent. Active controls lifecycle/layout/input participation while retaining declared stored state for reactivation; Hidden controls visual rendering; Interactive controls user-originated interaction/focus. Deactivation does not overwrite stored visibility or interaction preferences. Independently active descendants can break only the activation dependency, not their ownership, theme, scope or permission boundaries; removal of the owning conditional branch still removes them. Hidden-but-interactive constructs are technically distinct, but first-party accessibility checks reject invisible focus targets without a documented accessibility purpose. No concealed control may receive consequential user input merely because it remains in a logical tree.

ARC-011 — Events identify Source, Target, event kind, applicable typed value and cancellation state. They target the originating component; propagation is explicit and stops when consumed. Group rules retain the actual member as Source. Stateful event Styles last only while their condition holds; the declared Once variants commit their supported property result rather than reverting when the state ends. Once means persistent effect semantics, not an implicit promise of one lifetime invocation. Async actions expose Running, Completed, Failed and Cancelled events and never block input while awaiting network, storage or inference.

One gesture must not dispatch through both a popup/editor handler and a global host shortcut. An event can request a typed domain operation but cannot declare that its effects succeeded. Store a cancellation or navigation token with asynchronous UI work and check target lifetime and result generation before projecting its result. If a user opens artifact B while artifact A's metadata request is pending, A's late result must not populate B's title, permissions or preview.

### 3.1.5 Layout, specialised surfaces and tooling

ARC-012 — Layout is property-driven. Required families include dimensions/minimums/maximums, padding/margins, alignment, wrapping/overflow, independent horizontal/vertical scrolling, Grid rows/columns/sizes/spans, stack spacing and Absolute positioning. Fixed dimensions use logical DPI-aware units; percentage, Auto and fractional/fill sizes retain their typed meanings. Invalid combinations fail clearly. Off-screen content is virtualised rather than removed from the document. Focus navigation can hydrate and reveal a target without constructing every previous page, row or object.

For Absolute placement, proportional X/Y use the declared centre-origin surface: left/right are −1000/+1000 and bottom/top are −1000/+1000; decimals and intentional off-surface positions are permitted. Pixel and percentage alternatives are explicit per axis and cannot be combined ambiguously with proportional values. X/Y inheritance recalibrates each axis against the nearest declaring container, which may differ by axis. Relative anchor/above/below/grid placement tracks the target's movement; raw coordinates remain fixed within the selected coordinate space. Popup positioning additionally respects the usable viewport and input-method insets.

ARC-013 — Layer is signed rendering/hit-test depth with deterministic source order at equal depth; it does not imply modality. Modal focus/input containment is a separate property scoped to the surface. Opening a modal remembers a valid return target; closing it restores focus or the nearest surviving owner. Nonmodal inspectors remain usable without trapping the entire app. Input/focus semantics must correspond to the actual rendered geometry after scaling, transforms and scrolling.

Registered Object Types host authentic specialised engines and expose content identity/revision, selection, focus/input ownership, accessible navigation, supported commands, state events, disposal and failures. Their internal document styles and media are authored content. CUI styles their surrounding chrome and declared chrome properties without recolouring pages, ink, charts or video. Engine failures remain inside the declared boundary and preserve the canonical artifact. A single generic Object wrapping a complete legacy application is not a compliant CUI migration.

ARC-014 — Effect modifies an element's rendered appearance; Background processing samples content behind its background region. Background blur/refraction/colour/transform chains never change the underlying elements' content, bounds, hitboxes, event routing or accessibility tree. Sampling stays live when the source scrolls, animates or plays video. Cache invalidation follows those dependencies. Unsupported effects produce an explicit capability/fallback result rather than a misleading frozen screenshot. Gradient stops, transform units and animation times are typed and validated. Reduced Motion suppresses ornamental movement while retaining the operation's final meaningful state.

ARC-015 — CUI controls provide semantic role, accessible name, description, value/range, selected/expanded/disabled/busy state and focusability. The framework owns keyboard semantics, scaling, high contrast, localisation and directionality. User content is not translated or restyled by changing interface locale. Reading order follows meaningful structure; absolute canvases provide their domain's semantic navigation. Screen-reader and keyboard behaviour must be tested in actual native/web adapters. Having an AccessibleName property in source is insufficient evidence.

The toolchain includes deterministic parsing/formatting, typed validation, accessibility lint, dependency generation, source maps, component preview, hot reload and semantic inspection. Invalid hot reload preserves the last valid tree. Valid compatible changes preserve state by stable identity; incompatible replacement reports its scope. Tests can address IDs, roles and names, render at declared dimensions/themes/scales, drive semantic input and inspect both stored and effective state. Native renderer adaptation must not silently introduce an additional public grammar or cascade.

ARC-016 — Architecture/CUI conformance requires negative and positive cases against real app composition: reject donor syntax, ambiguous shorthand, duplicate identities, import cycles and invalid property types; exercise dynamic/static Prefabs, group mutation atomicity, overlay restoration, live/static bindings, conversion failures, keyed reorder, conditional removal and invalid Children rollback. Validate one hosted and one standalone editing journey using the same commands and data. Test theme changes in two running apps, menus/dialogs/Object chrome, offline preference fallback, IME, keyboard-only use and stale async results. Preserve a source/engine parity inventory so passing a small parser sample cannot hide an unchanged legacy shipping host.

## 3.2 Model, route and context lifecycle

RT-010 — Use one canonical catalogue for discovery, installed-model management, the compact picker and routing. A model record identifies its provider/source, version or artifact, supported modalities and capabilities, known context limits, installation state and requirements. A friendly model name is insufficient to establish equivalence. Unknown or unverified metadata remains explicitly unknown. Atlas names, usage values and device requirements are fixtures unless confirmed from actual manifests and runtime checks.

RT-011 — Distinguish available, saved/bookmarked, downloading, verifying, installed, loaded, updating, failed and removal-pending states. Selecting an eligible installed model changes the intended selection; it does not itself load the model. Sending a request performs the necessary eligible loading transition. Download, selection, loading, credential configuration and tool permission are separate operations. Removal of weights must not delete conversations or their provenance.

RT-012 — Main, Voice and Vision are picker roles. Each role retains its selected model, reasoning value and Assistant/Specialist choice while the picker remains open. Role selection is not a grant to use a microphone, camera or screen. Actual invocation checks the capabilities required by the operation, including the distinction between speech recognition, synthesis and visual understanding where the selected route supports them. Do not infer these capabilities from a role label.

RT-013 — Route eligibility is evaluated before route preference: capability, current privacy rules, permission, entitlement, health and resource availability determine which routes can run. Active and Background routes remain distinct. Local only excludes cloud execution. A configured cloud fallback or a successful connection test is not permission to disclose every artifact, memory or source. The admitted request records the selected route and effective configuration.

RT-014 — Keep supported context capacity, requested context allocation, active allocation, actual usage, reasoning effort, provider allowance and device resources separate. Percentage or token displays identify what they measure. Never substitute CPU load, quota consumption or context occupancy for a reasoning setting. No capacity or maximum is inferred from the Atlas's sample numbers.

RT-015 — Context edits produce a pending value. Typing, Enter, section dismissal and role switching do not apply it. Apply and reload is offered only while the pending value differs from the active value. Validation checks the selected route's genuine capability and available resources. Invalid input keeps the working value unchanged and supplies a useful inline reason. The picker and host popup share one conversation/request policy; RUN-104/105 and resolved DEC-003 define persistence, actual per-session allocations, partial application and admission of unloaded roles.

RT-016 — A real context reload identifies the affected runtime session and other work that would be interrupted. It preserves the conversation, drafts, committed outputs and recoverable run state. Mark the configuration Applying until the actual runtime confirms the requested allocation. On failure, keep a still-usable previous configuration where available; otherwise show Unavailable or recovery-required honestly. Retain the attempted value for correction. Never report a rejected context as active, restart unrelated sessions, or promise that an unloaded engine can always remain ready after failure.

RT-017 — Reasoning remains visible in the compact picker, as in the Atlas. Store both the user's requested setting and the effective provider setting when an adapter maps between them. Only advertised provider capabilities may be invoked. Unsupported or inapplicable reasoning is explained without inventing extra model levels. RUN-103 and resolved DEC-002 define the versioned binding and fallback rule while preserving the Atlas 0–100, step-10 control. Existing discrete clients retain an explicit compatibility mapping; neither scale fabricates provider capabilities.

RT-018 — Provider setup separates a draft connection from authenticated, tested and available service states. Endpoint identity, account identity, credential reference, declared capability, discovery result and last test outcome remain inspectable. Tests report actual errors and capabilities; a saved credential draft never appears verified. Credentials are held in secure storage and are absent from model context, UI exports and ordinary logs. Revocation stops future use without deleting unrelated local work.

RT-019 — Logical sessions, run identities and provider endpoints are distinct. Several private sessions may share one endpoint without sharing context or grants. A session-scoped Stop targets only that session/run. An endpoint-wide reload identifies every affected session and preserves their recoverable state before it proceeds. Test concurrent sessions with different private inputs, cancellation of one, and reconnect without cross-session disclosure or broadcast cancellation.

Acceptance: select a model without loading it; send and observe the real load outcome. Fail download verification, exhaust available space, expire authentication and attempt removal while a model is in use. Confirm truthful states and recovery. Exercise context edit, dismissal, invalid value, success, reload failure and interrupted run recovery. Compare each displayed requested/effective setting with the actual adapter request and response.

Atlas anchors: home-models, home-models-installed, home-model-details, host-model-picker, settings-models, settings-provider, settings-providers, settings-voice. Implementation evidence: [ReasoningScale.cs](https://github.com/CroakyJake12/9to1/blob/1f92cd888f59025cc684f0720163efdbc580f8e3/9to1%20Workspace/shared/src/Haven.Core/DomainLogic/ReasoningScale.cs) at the pinned repository revision defines the competing discrete scale; its existence is a migration fact, not authority over the Atlas.

### 3.2.1 Catalogue records, role selection and routing

RUN-101 — A ModelRecord separates a logical model identity from its immutable artifact/provider revision and installation location. It contains provider/source identity, display name and aliases, family, format, quantisation where meaningful, modalities, tool/structured-output support, context/output limits, reasoning capability metadata, installation references, source provenance and replacement history. Metadata carries its origin and verification state. Name lookup returns all matches; an alias resolves within a namespace. A local file path or repeated human-readable name cannot collapse different models into one identity.

A CapabilityClaim distinguishes model ability, adapter implementation, host integration and current permission. A model may understand images while the adapter cannot transmit them; an adapter may support audio while microphone access is denied. The eligible operation is the intersection. Discovery can display a declared claim as unverified; admission requires sufficient verified compatibility for the requested operation. Unsupported parameters cannot be ignored silently. A provider response that omitted a requested feature must not be reported as full conformance merely because it produced text.

RUN-102 — A RouteDefinition has RouteID, revision, ordered candidate references, enabled state, per-candidate constraints, fallback policy and applicable foreground/background scope. Resolve a request's explicit override first, then applicable Agent/task and app/surface overrides, then the relevant role/capability route and authorised background/default inheritance. Record the winning source; locked policy explains its origin. Main/Voice/Vision remain the Atlas picker roles. Additional modality distinctions belong in capability records and advanced management, not in a replacement compact-picker layout.

Before considering order, filter capability, input/output size, model/adapter compatibility, privacy, provider account scope, entitlement, current health and resource availability. A cloud candidate remains ineligible when disclosure is not granted. Fallback requires a classified model/provider condition such as outage, genuine rate limit or incompatible context; a denied tool mutation, missing file or pending approval is not a reason to switch models. A pinned selection with fallback disabled fails transparently. Each actual fallback records the skipped candidate, reason and model/configuration used; it cannot inherit another model's completion or usage receipt.

### 3.2.2 Requested reasoning and effective provider settings

RUN-103 — Keep the Atlas's requested Reasoning range of 0–100 in ten-point steps. A role stores RequestedEffort separately from EffectiveEffort. An adapter may advertise an explicit mapping to supported stable LevelIDs; that semantic mapping takes precedence. Its version, level IDs and supported conditions are part of capability metadata. If the provider declares only a semantically ordered set, use one shared deterministic fallback: assign normalised anchors 100 × (ordinal + 1) / levelCount and select the closest anchor, resolving equal distance to the lower declared effort. These anchors are mapping labels, not measured compute percentages.

Only declared semantic ordering permits that fallback; lexical order, enum integer accidents or a count alone do not. With no usable mapping, reasoning is unavailable for that route until the adapter supplies it. With one level, show that fixed effective level rather than inventing a range of provider settings. Requested zero never invents an Off parameter: it selects the lowest supported level unless an actual Off level is declared. The normal UI can preserve the requested slider value; the current summary/details reveal the effective provider level when different. All entry points call the same versioned mapper. Changing a model revalidates the mapping rather than carrying an incompatible provider enum across adapters.

Validation includes every permitted slider position, all advertised levels, ties, missing ordering, unsupported reasoning, a fixed single level, an actual Off level and model change. Capture the actual adapter arguments. The old four-step product scale can remain a compatibility mapping for clients that explicitly use it; it does not replace the Atlas interaction or become a fabricated capability of every provider.

This is an adopted engineering binding, not a claim that the Atlas implements provider mapping. The current ReasoningScale.cs contains a general tier-label expression based on 100 × (ordinal + 1) / count, but also special three/four/five-level labels and separate four-step rounding. RUN-103 deliberately requires semantic ordering, gives advertised mappings precedence, and specifies nearest-anchor/lower-tie resolution for the new requested slider. Those differences require a versioned mapper and compatibility tests; historical count-only or upward-tie behaviour is not silently inherited.

### 3.2.3 Context scope, persistence and the apply transaction

RUN-104 — The picker and host context popup project one shared context policy for the current conversation/request scope. Per-role model, reasoning and participant choices remain independent. A saved conversation stores the versioned selected policy and role references; a Temporary conversation keeps them within its permitted session lifetime. Home defaults initialise new scopes; changing a default does not silently mutate every active conversation. A legacy global setting migrates as a default while already admitted requests retain their captured effective configuration.

The shared policy is a requested budget, not evidence that Main, Voice and Vision have the same physical context window. Resolve its applicable model sessions at admission/apply and record each ActualContextAllocation, capacity, usage basis and binding. A non-token Voice adapter declares NotApplicable rather than displaying a fabricated token count. An unsupported setting is distinguished from an unknown capacity. The context usage indicator identifies the active session/role whose usage it shows; unrelated sessions are not added into an unexplained percentage.

Conversation scope and default migration are deliberate production design choices: the Atlas establishes shared pending/applied interaction but stores prototype state in uiPreferences.modelContextTokens. The inspected preference service exposes a global ContextLimit setter; neither source demonstrates the new per-conversation transaction. Implement that mapping without treating the prototype preference or current setter as a production reload acknowledgment.

RUN-105 — Context editing follows Draft → Validating → Applying → Applied, with Invalid, ApplyFailed or OutcomeUnknown branches. Keep PreviousAppliedRevision, DraftValue and ApplicationOperationID. Validation checks positive whole-number syntax, genuine route capacity, resource fit and current policy without unloading anything. A successful validation authorises no external effect by itself. Apply snapshots the intended value, affected sessions, routes and current revisions, then rechecks them immediately before configuration changes. If model selection changes during validation, invalidate the old validation instead of applying it to the new route.

Reconfigure only affected active sessions. Unloaded roles retain the requested policy and validate it when loaded/admitted; applying context does not load every role or start inference. Reject an unsupported requested budget for an affected session with its specific limit/reason rather than silently clamping it. A newly selected lower-capacity route remains unavailable for that request until the user supplies an eligible budget or selects a supported alternative. NotApplicable sessions do not block application and do not receive invented token parameters.

Do not overwrite active configuration before runtime acknowledgment. For a hot-reload-capable adapter, apply through its supported transaction and verify effective allocation. For an adapter requiring unload/reload, checkpoint affected work, identify the interruption scope and perform controlled replacement. If a provider exposes only a fixed physical window, enforce a supported request budget and label that distinction; do not claim a physical reload occurred. Commit the shared applied-policy revision only after applicable sessions confirm their result. Partial application is explicit and recoverable, with old/new allocation recorded per session; it must never appear as universal success.

RUN-106 — Installing and loading use separate state machines and ownership. A download has JobID, immutable source revision, expected integrity/size where available, staged destination, observed bytes, resume token and cancellation state. Verify before marking Installed. A load has EndpointID, target artifact/configuration, reserved resources, actual adapter state and health check. Model selection and catalogue browsing do not start either operation. Sending may trigger an eligible load; it cannot silently download unapproved bytes or connect an account merely because a model name was selected.

Temporary acquisition has explicit consuming owners; persistent installation has a durable ownership record. Removing one consumer releases its reference, not bytes still used by another endpoint or installation. Replacement stages and verifies the new artifact, recalculates model-derived limits and retains only compatible declared settings. Alias continuity does not reuse the old immutable artifact identity. Keep a rollback reference until the replacement has passed its required checks; failure preserves the old usable route when possible and clearly reports when resources prevent both from remaining resident.

## 3.3 Durable work and coordinated agents

RT-020 — Admission, execution and completion are separate events. A draft has not been submitted; a queued request has not necessarily started; completed preparation is not a committed action. Assign durable request/run identities before work enters a queue. Record the task relationship, admitted configuration, effective permission/policy revision, status events, checkpoints, output references and action receipts needed for recovery.

RT-021 — Expose meaningful states such as Queued, Starting, Working, Waiting for input, Waiting for approval, Paused, Cancelling, Cancelled, Completed and Failed. A state transition follows an actual event. A tool result, saved artifact or external action is completed only when its owning service confirms the corresponding outcome. Activity summaries describe work and tool events; private internal reasoning is not a user-interface contract.

RT-022 — Steer, queue, pause, stop and resume have explicit supported semantics. Steering is associated with the current task and becomes part of its durable history. Queueing does not approve effects. Stop prevents future work at the boundary the runtime can actually reach; show Cancelling while that boundary is pending. Preserve committed effects and completed outputs. Cancelled work must not automatically resume after a restart.

RT-023 — Recovery attaches to the same task/run/checkpoint when continuation is valid. A retry that begins a new attempt has a new RunID and records its lineage. Distinguish safe computational retries from file writes, external sends and other effects. An uncertain acknowledgment requires receipt reconciliation or explicit review before a potentially duplicate external action. Reopening a tab, reconnecting a provider or restarting a runtime cannot replay completed effects automatically.

RT-024 — A coordinator and every child agent are real runs with stable parentage, delegated brief, granted inputs, allowed outputs, budget, state and public activity. Delegated authority is the intersection of the parent's current grant, the delegated scope, the child's capability and applicable policy. It cannot widen access or bypass mandatory approval by changing agents.

RT-025 — Independent children may progress in parallel. Cancel/retry/review for one child is scoped to that child; completed sibling output remains intact. Parent cancellation, grant revocation and budget changes propagate to affected descendants. A replacement child cannot evade exhausted limits or reclaim another agent's write scope silently. Merge/join records identify which outputs were accepted and which remain proposals or conflicts.

RT-026 — Durable history, canonical plans, action logs, goals/checkpoints and the Assumptions Bank remain the source records; compacted context is a derived execution view. Cumulative is the default compaction strategy, alongside Summary and Disabled. Cumulative builds during the response cycle, then an audit agent repairs and validates it before the boundary switch defined in this chapter. Compaction preserves outstanding obligations, canonical IDs and revisions, permissions, completed-action receipts, evidence references and unresolved conflicts. A summary never grants access that the original scope lacked. Cloud-based summarisation requires the same disclosure permission as other cloud processing. Capacity failure leaves the history and draft recoverable.

RT-027 — A persistent task's completion depends on its explicit completion conditions and confirmed outputs, not merely a progress message, a context-window boundary or a tool returning successfully. Continue independent permitted work when another branch is blocked. A genuine input/approval blocker is represented explicitly. Background and scheduled work obey their own authorisation and retention rules; a conversation's presence alone is not a recurring-job instruction.

Acceptance: restart while queued, active, awaiting approval and after a mutation whose acknowledgment is lost. Confirm stable identities, recoverable input and no duplicate effect. Stop one child while siblings complete. Revoke an inherited source, exhaust a child budget, compact context, and verify the same constraints remain effective on continuation.

### 3.3.1 Broker handshake and execution identity

RUN-201 — On attachment, a client and Home-managed service exchange supported contract versions, required capabilities, authenticated principal/scope, service instance identity and current health. A reconnect negotiates again; an old transport socket or process ID is not proof of continuity. Required incompatibility produces a typed degraded state and preserves local work. Clients subscribe to restored state from a cursor/snapshot instead of starting duplicate brokers or replaying submissions. Home's visible window lifetime remains separate from the shared service lifetime.

RequestID identifies an admitted intent; request revision identifies a deliberate change to that intent; AttemptID/RunID identify executions and retries; SessionID owns conversation/context continuity; EndpointID identifies a logical runtime target; transport URL/port is merely a locator. A replacement process may serve the same logical endpoint after recovery, but it has a new service-instance identity and must prove compatibility with stored checkpoints. A provider handle does not confer control of the provider's whole server. Request-scoped controls never broadcast to every session sharing an endpoint.

RUN-202 — Submission creates a durable receipt before the client clears a draft. The submission envelope contains stable submission/operation identity, conversation/session target, input snapshot and attachment references, requested route/role policy, tool scope, output contract, streaming choice, limits, completion conditions and current context/configuration revisions. Admission validates schema, identity, permissions, attachment availability, dependencies and capacity policy. Return Accepted with RequestID and receipt or Rejected with the original recoverable draft and structured reasons. A timeout waiting for admission is OutcomeUnknown until the client looks up the same submission identity.

Identical retry of a submission identity returns the existing receipt. The same identity with materially different normalised input returns Conflict rather than silently creating a second request or changing the first. Content is immutable once admitted; later steering or replacement is a new recorded event/revision under the applicable conversation policy. Restoring the composer must not resubmit its last sent text. Attachment hydration and network failure cannot leave an invisible accepted request with the UI insisting that nothing was sent; reconciliation must expose the actual state.

### 3.3.2 State transitions, queues and cancellation

RUN-203 — Maintain separate admission, execution and effect state. The principal run path is Queued → Starting → Working → Completed, with explicit WaitingForInput, WaitingForApproval, Pausing/Paused, Cancelling/Cancelled, Failed and recovery states. A terminal state is never inferred from stream closure alone. Each transition records actor/source, reason, prior state, new state and durable event sequence. Illegal transitions return InvalidState without corrupting the prior record. Completed requires the completion contract and confirmed outputs; a model's final sentence is not sufficient.

Queue records identify dependency, session ordering, priority class, position/admission estimate where knowable and capacity/expiry policy. Independent sessions may run concurrently when the adapter and resource policy support it. Dependent turns in one conversation commit context in order unless the product explicitly creates separate branches. A parent waiting for a child on the same constrained endpoint yields the necessary execution slot instead of deadlocking the queue. Background work uses bounded fair scheduling and cannot starve active input or an already permitted cancellation request.

RUN-204 — Stop is an idempotent request to stop future dispatch and reach an actual cancellation boundary. Queued work can become Cancelled without executing. Running generation/tool work becomes Cancelling until the adapter reports stopped or a documented best-effort limit. Preserve completed effects, partial output and the receipt history. A remote effect that completes despite cancellation is recorded as completed; do not rewrite it as undone. Stop of a persistent root cancels unfinished dependent work and must survive restart as a terminal cancellation intent, never as an instruction to auto-resume.

Pause differs from Stop and from hiding output. Pause prevents subsequent steps and reaches Paused only at a supported safe boundary. If a provider cannot pause generation, declare that limitation; buffering unseen output is not an exact pause. Resume validates grants, configuration and checkpoint compatibility. Exact resume is claimed only when the adapter can restore the required state; otherwise offer the supported continuation/restart mode with preserved lineage and no replay of completed effects. A manually paused run stays paused until a valid resume/stop action.

RUN-205 — Steering appends an ordered, attributable instruction event to the active task; queueing creates a separately admitted dependent request. A steering event does not delete the current prompt, revoke valid completed work or silently approve an action. Apply steering at a safe planning boundary and record which attempt consumed it. A user change that invalidates planned work updates those nodes and their approvals before dispatch. Earlier-message editing and conversation branching retain their separately specified product policy; neither a transport retry nor ordinary steering may implement destructive history replacement by accident.

### 3.3.3 Event delivery, result records and measured facts

RUN-206 — Every event carries RequestID, request revision, AttemptID/RunID, sequence within its stream, event kind, timestamp, causal parent and safe payload/reference. Use monotonic sequence for replay within a stream; timestamps alone do not establish total ordering between concurrent children. Distinguish text deltas, proposed tool arguments, tool dispatch/result, approved effects, generated-UI updates, metrics, state changes and errors. Incomplete tool arguments or partial generated markup are never executed.

Clients resume from an event cursor or receive a current snapshot with an explicit gap indicator. Bound buffers and apply backpressure. Loss of a view connection does not cancel the underlying run unless an explicit policy says so. Stale deltas from a superseded revision/attempt are ignored in the active display but remain attributable in history. Streaming and non-streaming paths converge on the same final result record. The Action Graph is a projection of these events and receipts; Actions Space must not maintain a second execution history.

RUN-207 — A RunResult records status/finish reason, identifiers, actual model invocations and route changes, user-facing output, artifact/export references, tool invocation references, authorised source provenance, structured blockers/errors and final configuration. Visible activity summaries are distinct from model output and unavailable private reasoning. A cited source is not marked retrieved unless a real source receipt supports it. Offered tools are not counted as used; proposed files are not counted as saved.

Each metric has value, unit, availability, scope, observation time, basis and provenance. Availability distinguishes measured, estimated, pending, unsupported/unavailable and redacted. A measured zero differs from unknown or unlimited. Aggregate only the declared scope and avoid counting a child invocation again through its parent's total. If some contributors withhold a quantity, show a known subtotal with coverage rather than an invented complete total. Queue time, execution time and pause time remain separate; overlapping spans need not add to wall time. Model-weight residency, KV allocation, utilisation, disk storage and architectural parameter counts are different measurements.

### 3.3.4 Journal, recovery and bounded orchestration

RUN-208 — Persist a journal sufficient to recover admitted work: input/configuration snapshot, dependency graph, completed node receipts, pending action/approval references, steering events, budgets, checkpoints, active package versions, blockers and attempt lineage. Journal persistence precedes dispatch of a consequential operation. After a crash, rebuild the last consistent state and reconcile any Dispatched-without-result action with its owning service before retrying. Do not claim distributed exactly-once execution when the remote service lacks that guarantee; represent an uncertain result as a reconciliation blocker.

Checkpoint records declare supported model/backend/schema versions and whether they contain portable conversation state, execution plans or adapter-specific cache state. Restoring conversation history is not restoration of GPU memory. A stale or incompatible cache may be discarded and recomputed while preserving the task and receipts. Sensitive checkpoints follow the same encryption, retention and permission rules as their source context. A recovery worker receives no additional grants merely because the original worker is unavailable.

RUN-209 — The work graph contains stable node IDs, dependency edges, required inputs, allowed outputs, owner, state, completion evidence and retry policy. Child agents inherit only the intersection of current parent scope, explicit delegation, capability and policy. They receive bounded token/time/action/cost/resource budgets where those can be measured and enforced. Budget-unavailable metrics remain unavailable; the scheduler must not treat that as permission for unlimited consumption. Cancellation, narrowing and revocation propagate to affected unfinished descendants. Replacing a child cannot reset the parent's budget or acquire a sibling's scope.

The coordinator joins confirmed outputs by identity/revision. Conflicts preserve alternatives rather than last-writer overwrite. Completed siblings survive another child's error. A blocked node marks only its dependants blocked; independent permitted work may continue. Completion conditions identify required artifacts, approved effects and validation evidence. Persistent work continues across recoverable execution slices until those conditions are satisfied, explicit Stop occurs or a genuine policy/input/resource blocker remains; persistence is not authority to exceed limits or silently change the requested deliverable.

RUN-210 — Detect repeated failing tool calls, oscillating edits and no-progress planning using actual state/event evidence. A recovery intervention is a runtime-authored event, never a forged user instruction. It identifies the pattern, evidence and intended correction, preserves completed work and remains bounded so reviewer/model loops cannot continue indefinitely. A false positive can be dismissed or superseded with an audit record. Unsupported completion claims are checked against canonical receipts before becoming user-visible success. Quality interventions do not invent a new permission or automatically switch to an unauthorised provider.

Validation: lose the admission response; replay the same submission; submit different content with its ID; disconnect/reconnect streaming; stop queued/running/approval-held work; pause an adapter without exact resume; crash immediately before and after external dispatch; fail one child while another completes; revoke a source before resume; restore an incompatible cache; compact history with a pending approval. Verify stable IDs, honest uncertainty, no duplicated effect and preserved drafts/outputs.

### 3.3.5 Cumulative Context Compaction

RUN-211 — Context Compaction has exactly three selectable strategies: Cumulative, Summary and Disabled. Cumulative is the default. The strategy belongs to the applicable conversation/task policy and is captured by each response cycle; changing it does not rewrite canonical history or silently switch the context of an active model call. ResponseCycleID identifies an admitted response and its associated planning/tool activity through the supported end-of-cycle boundary. A long-running task may contain several cycles while retaining the same TaskID, plan and completed effects.

In Cumulative mode, construct and update the candidate during the response cycle, while work continues. Seed it from the current valid compacted state and authoritative events, then incorporate new decisions, results, corrections and obligations incrementally. Do not wait until the response finishes and then call an ordinary snapshot summary Cumulative. The staged candidate is not the active execution context. Existing generation and tools continue against their admitted configuration and canonical state until an authorised switch occurs.

RUN-212 — A CompactionCandidate records CandidateID, strategy/version, ConversationID/TaskID, ResponseCycleID, parent active-context revision, source history revision, source event high-water mark or causal watermark vector, processed ranges/gaps, candidate revision, incremental change journal, source-policy revision, component references and status. The candidate journal makes building recoverable after interruption and deduplicates replayed source events. An incomplete streamed response or tool argument remains provisional; it cannot be converted into a confirmed decision/effect merely because it entered the candidate.

The required audit manifest preserves the following logical information, with execution-critical detail in the compacted context and exact references to complete canonical records:

| Column 1 | Column 2 |
| --- | --- |
| Manifest component | Required retained meaning |
| Goal and obligations | Current user intent, completion criteria, unresolved commitments, constraints, blockers and checkpoint obligations; preserve later steering and corrections. |
| Plan | Canonical PlanID/revision, all relevant step identities/statuses, dependencies, owners, accepted outputs, pending branches and the reason a step is blocked or superseded. |
| Action log | Ordered/causal action identities, target IDs/revisions, safe input summaries, confirmed results, errors, decisions, tool receipts and uncertainty; distinguish proposed, dispatched, completed and cancelled effects. |
| Pending interaction | Exact pending approval/question IDs, target/proposal revisions, waiting scope and available continuation; a summary cannot answer a question or renew an approval. |
| Assumptions | Canonical Assumptions Bank identity/version and relevant entry revisions, accepted facts, uncertainty, corrections, supersession and dependencies. |
| Artifacts and evidence | Saved artifact/revision/export identities, source provenance, meaningful observations and evidence references that justify completed work. |
| Execution checkpoint | Active/dependent RunIDs, current phase, captured configuration, supported checkpoint references, budget consumption and cancellation/pause intent. |
| Authority | Source scopes, grants/policy references, disclosure constraints and revocations; copied prose is not replacement authority. |

Full plans, detailed action logs, source history, receipts and Assumptions Bank records remain retained and retrievable under their current permissions. Compaction reduces the model-facing representation, not the canonical record. It must not reset plan progress, turn an uncertain effect into a successful one, forget a completed mutation and repeat it, or revive a corrected assumption from an older summary. Large logs can use referenced ranges plus execution-critical extracts; a reference must resolve to the exact record/revision instead of an ambiguous title.

RUN-213 — Immediately before a proposed cycle-end switch, a separately identified audit-agent invocation compares the candidate with the authoritative source cut and required manifest. It checks omissions and contradictions, fills missing relevant detail, preserves corrected assumptions and verifies open obligations/action outcomes. Its output is a proposed repaired candidate plus an AuditReceipt identifying auditor model/configuration, inspected ranges, repairs, unresolved concerns and the source/candidate revisions reviewed. The auditor cannot edit canonical history, grant permission, execute queued tools or declare a failed action successful.

Combine the model audit with deterministic validation. Verify referential integrity, plan/step identities and statuses, required unresolved items, action receipt links, pending approval/question IDs, source/Assumptions Bank revisions, permission constraints and consumed source ranges. Reject a candidate with missing mandatory records, unresolved sequence gaps, invalid references or contradictory execution state. Semantic auditing is fallible; do not guarantee that a model catches every omitted nuance. Record audit coverage and preserve recoverability even when the candidate passes.

RUN-214 — Establish a final consistent cut before activation. Tool results, child completions, user steering or assumption corrections arriving while the candidate is built/audited advance the source watermark and mark affected candidate sections dirty. Incorporate those late events and audit the changed tail before switching. Use a bounded admission barrier for only the affected continuation and a compare-and-swap against the active-context revision, final source cut and relevant policy/Assumptions Bank revisions. A stale audit cannot activate a candidate merely because its text looks complete.

An event committed before the final cut must be represented or correctly referenced. An event legitimately committed after that cut remains in the durable suffix and is supplied to the next context before the dependent continuation consumes it. Maintain per-stream/causal boundaries when children have independent sequences; timestamps alone cannot prove a complete cut. Atomically publish the validated candidate, its AuditReceipt and source cutoff as the new active-context revision. A crash yields the old valid context or the new validated one, never a half-replaced context with an advanced cursor and missing events.

RUN-215 — Auditor and compactor are scoped agents under the same grant, privacy, locality, resource admission and bounded budget rules as the task. They receive no extra access merely to improve a summary. A local-only context cannot be sent to a remote auditor without an already eligible disclosure route. If audit is unavailable, fails validation or cannot fit resources, retain the previous valid context and candidate for repair. Continue independent permitted work when possible; hold only continuation that cannot safely proceed within its actual context limit. Never silently drop required records to force a fit or report an unaudited candidate as active.

Retain previous compacted versions and source-cut lineage under the task's retention policy. Rollback restores a previous valid context representation plus all authoritative later events and current corrections; it does not roll back real-world actions, resurrect old approvals or erase later plan progress. A candidate may be discarded and rebuilt from history without repeating completed work. Compaction status distinguishes Building, AwaitingBoundary, Auditing, Repairing, Validated, Active, Held and Failed, with the relevant phase/reason inspectable.

RUN-216 — Summary mode creates a conventional snapshot representation at a bounded safe boundary from a specified source cut, then validates the same critical manifest/references and commits through the same revision-safe switch. It does not promise incremental construction during the response. Disabled stops automatic context compaction; canonical history remains intact and no hidden truncation substitutes for the disabled feature. If the active route cannot admit the required context, preserve the draft/task and offer a truthful supported choice such as explicitly compacting, selecting an eligible larger-context route, changing the requested scope or saving a continuation. A larger context or remote route is still subject to capability, resources and disclosure policy.

RUN-217 — Acceptance observes the candidate changing during an active response while the active context revision remains unchanged. Deliver a late tool receipt and a corrected Assumptions Bank entry during audit; verify both reach the final cut and the auditor repairs the candidate before a single atomic switch. Interrupt building, audit and activation; recover without losing source events or replaying actions. Deliberately omit a completed mutation, pending question, blocked dependency and corrected assumption; deterministic checks/audit must reject or repair the fixture. Test unavailable local audit, insufficient budget, Summary and Disabled at a real context limit. Verify full action logs/plans remain retrievable and that a restored context retains all later effects and obligations.

## 3.4 Tools, integrations and generated interfaces

RT-030 — Maintain a canonical, versioned capability registry. Each executable capability exposes stable identity, owning package/app/provider, typed input/output schemas, prerequisites, permission scope, side effects, health, timeout/cancellation behaviour and result/receipt semantics. Per-request discovery distinguishes executable, unavailable, unconfigured, approval-required and denied capabilities. Semantic discovery can resolve the requested operation even when the user's words differ from a function name.

RT-031 — Installed, enabled, authenticated, assigned and authorised are separate package states. An Assistant/Space assignment references a package identity and version; it does not create a private copy of the tool or credentials. Validate compatibility, provenance and dependencies before activation. Imported instructions or assets do not automatically execute code. A material identity/schema change requires re-evaluation before invoking an old grant.

RT-032 — Provider connections preserve their account identity, scope, resource mappings, revision/sync tokens, pending operation identity and confirmed receipts. RT-033 — Generated interfaces use registered typed CUI components and actions. RT-034 — An inline interactive proposal is distinct from a durable artifact and from an approved action. Changing generated controls updates the proposal only. RT-035 — CUI primitives and extensions have explicit types, identity, properties, actions, content and child relationships. Literal text is distinct from parsed child content. ### 3.4.1 Registry and feasible plans

RUN-301 — A CapabilityRegistration identifies CapabilityID, owner and package/server/app revision, action schema, semantic intents, typed inputs/outputs, prerequisites, platform requirements, permission scopes, effect/risk class, cancellation support, idempotency behaviour and health. Registration requires authenticated authority for that owner. A description, retrieved page or tool result cannot self-register capabilities or alter trust. Updating registration invalidates derived plans and schemas whose assumptions changed; a stable display name never proves unchanged execution semantics.

Build an EffectiveCapabilitySet for the authenticated request scope. Preserve distinct readiness reasons: Executable, ApprovalRequired, AuthenticationRequired, ScopeRequired, MissingInput, AppUnavailable, ProviderUnavailable, PolicyDenied and UnsupportedPlatform. Discovery is neither approval nor execution. A large registry can be surfaced progressively through summaries and search, but the model can inspect deeper schemas throughout the request and receives material invalidation events. Negative discovery results are versioned too; a cached unavailable conclusion must not survive installation or authorisation of the missing capability.

RUN-302 — Resolve requested outcomes against semantic capabilities and typed dependencies. A plan step names the selected capability/version, arguments, canonical targets, expected outputs, dependencies and current permission state. Explicit user invocation constrains or prioritises the named source; otherwise choose by canonical ownership, capability fit, privacy, permissions, reliability and applicable preferences. A similar function name is not sufficient justification for a lower-fidelity or unrelated operation. A missing prerequisite is different from no matching capability. Before claiming inability, inspect the currently eligible tools unless a current authoritative hard constraint already establishes it.

Resolution must be bounded and cycle-aware. Reject plans with missing required inputs, impossible type conversions, uncontrolled dependency cycles or unbounded recursive delegation. Do not invent an output from a previous step to make a plan type-check. An image-generation step followed by Present insertion passes a confirmed image artifact reference, not a filename guessed before generation. A plan to email a file remains staged until the file exists, recipients/attachments are resolved and the send action satisfies its own approval. Plan acceptance cannot silently approve later changed scope.

### 3.4.2 Package and MCP lifecycle

RUN-303 — A package manifest declares PackageID, kind, version, supported runtime/schema ranges, origin/integrity, dependencies, entry points/resources, requested capabilities and requested scopes. Inspecting/importing the manifest cannot execute it. Installation, enablement, assignment, connection and authorisation remain separate states. Stage and verify updates before activation; preserve a usable previous version where rollback is possible. New requested permissions are not inherited automatically. An integrity or incompatible required-schema failure quarantines the candidate with inspectable diagnostics rather than enabling it partially.

Skills provide declarative workflow/instructions/resources and authorised dependencies. Plugins can provide executable capabilities and CUI surfaces under their declared sandbox/capability environment. An integration is a durable authenticated service/account relationship. MCP is a negotiated capability transport. Composition preserves each identity and authority boundary: a Skill cannot obtain shell execution merely by containing a command; a Plugin cannot borrow another connection's token; an MCP bridge cannot remove the owning app's protected-action check. Record package/Skill versions used by every run so later changes do not rewrite the provenance of completed work.

RUN-304 — An MCP connection has stable ServerID, client/server role, transport/process definition, protocol version, credential reference, owner/scope, trust state and a versioned capability snapshot. Names may collide between servers; canonical tool identity remains server-qualified. Connecting/Ready/Degraded/Reconnecting/Failed/Stopped follow actual transport and discovery results. Tools, resources and prompts are exposed only when supported by the negotiated version/server. Unsupported capability is not an empty successful response.

Validate complete tool arguments before dispatch and returned values before binding them to typed app operations. Cancellation reports whether the transport/server confirmed it, whether it was best-effort or whether the effect had already completed. Reconnect re-establishes identity/schema and reconciles pending operations; it does not replay a completed send. Browser-exposed capabilities preserve the actual origin/document identity; a website-hosted remote MCP endpoint preserves its ServerID and transport/authentication identity. A normal webpage URL is not assumed to be an MCP endpoint. Support for one surface does not prove the other.

<a id="h.l6znl9ygpspc"></a>

### 3.4.3 Provider connections and remote state

RUN-305 — One Connection represents an authenticated provider/account relationship independent of the app that created it. ProviderID, ConnectionID, ExternalAccountID, credential reference, scopes/version, allowed consumers and health are distinct fields. Multiple accounts remain separate. Consumers obtain scoped capabilities from the shared integration layer, not reusable raw credentials. Authentication, refresh, expiry, revocation and additional-scope requests are managed centrally and report the exact affected connection. A failed refresh cannot silently select another account with a similar name.

RemoteEntityReference includes provider, connection/account, object ID, revision token when supplied, remote location and any canonical local mapping. Live remote, cached metadata, cached content, imported copy and synchronised mirror have explicit different states. A remote move updates location without changing object identity. A local imported copy survives disconnection under its own storage/permission contract. A linked item becomes unavailable when its source grant disappears; do not turn the old cache into a newly owned copy to evade revocation.

RUN-306 — Centralise pagination, provider limits, retry-after/backoff, cancellation, webhook/change-feed validation and sync cursors. Consumers share health and quota observations rather than each polling the same account independently. A cursor belongs to its provider/account/query/schema scope. Remote writes use stable operation identity and provider idempotency where supported. For uncertain effects, query the remote outcome or require scoped reconciliation before retry. Partial batches retain per-item completion and resume only eligible unfinished items. A queued write has not succeeded remotely; its UI distinguishes Pending, Revalidating, Dispatched, Confirmed, Conflicted, Failed and OutcomeUnknown.

### 3.4.4 Generated interfaces and action bindings

RUN-307 — A generated-UI envelope contains SchemaVersion, source RequestID/revision/RunID, view identity, component tree or validated patch, state schema, canonical data references and declared action bindings. The host advertises its accepted component/property/action set. Validate type, size/resource bounds, reference access, duplicate IDs and command scopes before activation. No arbitrary script or unreviewed application code executes from a generated view. Unsupported rich output retains a useful text/data fallback and identifies the unsupported representation without falsely declaring the whole result lost.

Generated patches are applied against an expected view generation. Invalid or stale patches keep the last valid UI and user input. A local slider can edit a proposal but cannot commit its destination merely because the model attached an action name. Actions carry the exact current proposal revision and canonical target to the owning app; approval and revision checks occur there and through Home. Promoting the proposal creates or updates one real artifact and returns a durable receipt. Reopening the response reconstructs that same binding, not a fresh hidden copy or a repeated mutation.

Validation: import an invalid package without executing it; update with an additional scope; reconnect an MCP server with a changed schema; isolate duplicate tool names and two provider accounts; lose acknowledgment after a remote mutation; stream invalid/stale UI patches; promote a valid proposal, reopen and confirm identical artifact/revision. Test semantic multi-tool planning and truthful no-feasible-path results, including actual provider/permission blockers.

## 3.5 Inference topology and resource lifecycle

INF-001 — Resource admission uses actual device and adapter capabilities and current availability. Model weights, context/KV allocation, concurrent requests and other resident processes consume different resources. Do not infer feasibility by simply adding device-memory totals. Admission can queue, decline with a reason, or offer an explicitly permitted alternative. Silent eviction of an unrelated user's active engine or worker is not an acceptable resource-management strategy.

INF-002 — Distinguish three modes: parallel task orchestration, independent concurrent inference endpoints, and one inference workload distributed across devices. Success in one mode does not prove another. The selected dual-inference acceptance topology must name which mode is intended, the endpoints/devices involved and their isolation expectations. A model can serve several agent runs through a scheduler without multiple engines; conversely, multiple engines do not prove correct agent coordination.

INF-003 — A controller validating engine unload/reload or GPU reclamation must survive the operation it tests. Use a controller outside the affected inference process/device, or an independently verified recovery supervisor. Record the controller, tested endpoints, protected resident workloads and cleanup ownership before the test. Never kill or unload the sole local worker controlling the test without an independent continuation path. Cloud-directed validation is suitable only when its tools/control channel actually remain available after the local endpoint stops.

INF-004 — V100 parity is demonstrated by an explicit capability matrix for the intended backend and model configuration, not by an engine starting or answering one prompt. Required checks include real generation, supported tool-call transport where used, streaming, context admission/reload, cancellation, session isolation, sustained concurrent work, memory pressure and recovery. If distributed inference is intended, additionally verify its real device-placement/splitting mode and failure behaviour. Compatibility-specific limitations remain visible rather than being reported as full parity.

INF-005 — Keep an independently recoverable known-good configuration and a surviving process-level timeout/watchdog for model-host experiments. Preserve enforced thermal/resource guards and verify that telemetry is fresh. Do not adopt a new driver, topology, quantisation or concurrency setting as the baseline until its declared capabilities, cancellation, session isolation and rollback have been demonstrated. Record the actual limitation if recovery cannot complete.

Acceptance: run two concurrent sessions with different private inputs; cancel one without affecting the other. Declare the hardware topology and expected proof before GPU work. Observe actual endpoint/device execution, controller survival, resource pressure, failure and restoration of the known-good configuration. A working preview, two enumerated GPUs or two unrelated prompts cannot prove distributed execution of one request.

Atlas anchors: home-model-details, home-models-installed, settings-models, home-mesh, spaces-running, states. This section formalises the owner’s requirement that validation must not depend on the inference session being unloaded. It does not claim that V100 parity or any dual-inference mode has been achieved.

### 3.5.1 Scheduler and resource reservations

RUN-401 — The scheduler distinguishes task concurrency, model-instance concurrency and device topology. A ResourcePlan identifies model artifact/configuration, intended endpoints/sessions, devices, weight placement, context/KV requirements, concurrency, workspace/activation requirements where measurable and current protected reservations. Admission uses current observations and adapter-specific compatibility. Two devices' memory totals cannot be treated as one allocatable pool unless the selected backend demonstrably supports the required placement. Device enumeration alone is not a capability test.

ResourceReservation has identity, owner, intended resources, observed actual allocation, acquisition/expiry policy and release state. Recheck fit when material conditions change between planning and loading. Observed free memory is not a durable reservation against unrelated processes. If load fails after a reservation, release only owned resources and reconcile partial allocations. Explicit eviction/reclamation targets a named owned workload and declared recovery path. Do not kill unknown processes, drop another user's context or stop a worker's serving model to meet an estimated budget.

RUN-402 — Foreground requests, background work, downloads and cache/index activity have separate scheduling classes with bounded queues and cancellation. A parent waiting for a dependent child yields resources needed by that child. Resource pressure can reduce derived preview/cache buffers, defer optional background work or present an eligible alternative. It must not silently reduce canonical content, switch model identity, lower precision, truncate context or route private data remotely. A proposed lower-context or different-model mode is a changed configuration whose tradeoff must be visible.

An endpoint lifecycle distinguishes Starting, Loading, Ready, Busy, Pausing, Paused, Stopping, Stopped and Failed, alongside the broker's broader health states. Reachable is not Ready; Ready requires the declared model/configuration and adapter health checks. Pause does not promise memory release if weights/context remain resident. Stop releases owned execution resources without deleting installed artifacts or Den records. Remote lifecycle control is limited to capabilities actually exposed and authorised; a remote model endpoint never implies permission to stop its host.

<a id="h.70ieo9l2ki8u"></a>

### 3.5.2 Context reload and controlled GPU experiments

RUN-403 — Configuration changes record requested, validated and actual effective state. Snapshot model/adapter/configuration per attempt. Changes normally affect future work; in-flight changes require a supported explicit transaction. A context reload identifies affected sessions and checkpoint compatibility, pauses/finishes/cancels affected work according to its declared transition and invalidates stale generation events. A failed replacement cannot report Ready on the strength of the old health observation. Where rollback requires unloading the candidate first, recovery truthfully distinguishes Restoring from Restored.

For V100 or other hardware parity, define a capability matrix for the exact intended backend, artifact/quantisation, context size, offload/topology and concurrency. Required rows cover genuine generation, streaming, tool-call schema/transport when used, structured output where required, cancellation, session isolation, context changes, sustained operation, memory pressure and restart recovery. Report unsupported rows. A backend that answers text but fails actual tool calls is not agent-runtime parity. Changed precision or workload must be disclosed in performance comparisons.

RUN-404 — Every GPU-clearing experiment has an independent ExperimentID and run record naming the controller, control channel, target endpoint/service instance, protected workloads, known-good configuration, checkpoint locations, timeout/watchdog, telemetry source and cleanup ownership. The controller must remain available after the targeted inference process/device is unloaded. Validate that survival before destructive lifecycle steps. Cloud orchestration is suitable only when its authenticated local control/recovery channel survives the tested failure; a cloud chat label does not prove that property.

Preserve existing enforced thermal/resource guards. Confirm telemetry timestamps are fresh rather than accepting a cached safe reading. Before unloading, record the current admitted work and recoverable configuration; after loading, verify actual endpoint identity and configuration rather than merely an open port. On timeout, stop further admissions, record uncertainty, release only experiment-owned resources and attempt the documented restoration. If restoration fails, show a concrete blocker and retain diagnostic evidence. Never repeatedly restart the same failed configuration without new evidence or a changed hypothesis.

RUN-405 — Acceptance distinguishes three claims. Parallel orchestration is demonstrated by correctly scoped independent agent runs. Independent dual inference is demonstrated by two simultaneous isolated endpoint workloads, including cancellation/failure of one while the other remains correct. Distributed inference is demonstrated by one request actually using the declared devices/placement, with attributable backend/device evidence and defined failure handling. Run two sessions with deliberately different private inputs and verify no context crossover. Measure resource use and cancellation under concurrent load; do not extrapolate from two sequential prompts.

Source basis: INF-001–005, home-model-details, home-models-installed, settings-advanced and spaces-subagents; technical/dulche-02.md/04.md and modules/models.complete.md. The controller-survival contract incorporates the owner's reported local-worker failure. No model alias, PID, port, quota, driver version or fixed machine allocation is prescribed as permanent product policy.

## 3.6 Dreaming and improvement-driven training

<a id="h.j3zvgpj4nlh0"></a>

### 3.6.1 Required capability, optional activation and truthful support

LEARN-001 — Train owns the approved initial fine-tuning, Dreaming, evaluation and checkpoint-management workflows. General pretraining and arbitrary direct manual weight editing are deferred; this does not defer the real training updates required below. Dreaming is a required product capability that the user optionally enables in Settings. It is disabled until enabled. It performs scenario practice with a main model and a review agent while both the AI and the computer are idle, then uses reinforcement learning to update real trainable parameters. Recording reflections, changing prompts, saving memory or ranking outputs alone does not satisfy this requirement. A supported result is a new full-weight checkpoint or a trained weight adapter attached to its exact compatible base; the interface states which was changed. Successful training does not imply improved quality until evaluation supports that claim.

A DreamingPolicy records enabled state, policy revision, selected trainable model/base, main/reviewer roles, eligible scenario/data scopes, feedback-learning inclusion, locality, resource/idle rules, bounded training plan, retention and candidate promotion policy. Saving an enabled policy authorises its eligible scheduled work and the chosen promotion mode; do not ask for fresh approval for each ordinary practice batch already within that scope. Broader data, remote processing or external actions still require their own applicable authority. Dreaming, Persistent Memory and Background Learning remain independently controlled. Disabling Dreaming stops new training admissions and requests checkpoint-and-stop of its current job without deleting the user's existing model or artifacts.

LEARN-002 — TrainingCapability is per model/backend, not inferred from an inference endpoint. It records exact base artifact/hash, architecture, tokenizer/template, supported trainable tensors or adapter method, precision/quantisation, trainer/runtime versions, optimiser/checkpoint support, compatible serving formats, hardware requirements and data/licence eligibility. An inference-only hosted model is Unsupported for local weight updates; no service is allowed to pretend it changed inaccessible provider weights. A provider training API is usable only when its actual capability, output identity, privacy and configured remote scope are established. No silent cloud fallback is permitted.

The required initial implementation provides at least one end-to-end compatible local RL training path with actual parameter-update evidence. GRPO with a declared reward function/model and compatible PEFT adapter is a concrete supported design pattern; another verified policy-optimisation backend may meet the same contract. Pin the implemented dependency versions rather than relying on rolling documentation defaults. A quantised inference file is not automatically a trainable checkpoint. Obtain an explicitly compatible source representation/adapter path and account for all training resources before admitting work. Preserve the original base artifact unchanged when training adapters.

<a id="h.qsslcg2repmh"></a>

### 3.6.2 Idle scheduling and a surviving control plane

LEARN-003 — Both idle conditions must hold at admission and remain monitored. AI idle means no queued or active foreground/user-directed AI work in the configured runtime scope, and no protected task requiring the selected shared resources; Dreaming's own work does not make that predicate recursively false. Computer idle uses fresh host observations for configured user-inactivity duration, protected foreground activities, resource pressure, power policy and thermal limits. Absence of keyboard events alone does not prove an idle computer. An unknown required observation is not a safe reading. Idle intervals, resource ceilings, thermal guards and interruption deadlines are explicit configurable policy values with validated device-specific defaults, not invented universal constants.

The scheduler reserves resources for rollout generation, reviewer inference, trainable/base weights, gradients, optimiser state, activations, checkpoints and evaluation separately. These phases can run sequentially when simultaneous residency is unsupported. Distinct main/review agent roles do not imply two simultaneous GPU engines. Foreground work has priority: new user activity or a protected job requests preemption, stops new rollout/update admissions, reaches a supported safe boundary and releases the resources needed by foreground execution. A training configuration without a bounded, tested interruption path is ineligible for automatic idle execution.

LEARN-004 — A lightweight controller outside the replaceable model/trainer process owns JobID, leases, phase transitions, cancellation, durable checkpoints and recovery. Its availability must survive unloading both main and reviewer inference engines. Reuse RUN-404's independent control-channel and protected-workload rules. A trainer that crashes cannot erase its controller's operation journal. Do not kill an unrelated engine or the session hosting the controller to create training capacity.

The job distinguishes WaitingForIdle, Preparing, Generating, Reviewing, Training, Checkpointing, Evaluating, CandidateReady, Promoting, Paused, Failed and Cancelled. Activity/resource changes can interrupt any expensive phase. Checkpoint at a backend-supported consistent boundary; if emergency termination is necessary, discard the incomplete update and resume from the last verified checkpoint. Resume checks policy, dataset eligibility, base/reviewer/reward versions and backend compatibility. Disabling the setting or revoking source scope remains effective after restart. The UI reports actual pause reason and whether the checkpoint supports exact training continuation or restart of the unfinished phase.

<a id="h.df3a628cok4i"></a>

### 3.6.3 Scenarios, review and reward

LEARN-005 — A Scenario records ScenarioID/version, origin, skill/objective, permitted inputs, environment/tool fixtures, success verifier, difficulty/category, expected output contract and train/evaluation partition. Scenarios can be generated from permitted objectives or curated examples; any use of user history must fall within the enabled data scope. Practice tools execute in isolated test environments with resettable state. A simulated send/delete/purchase must not invoke its live external counterpart. Test outcomes are evidence from the environment, not assertions made by the practicing model.

The main role generates candidate trajectories using a pinned rollout policy version. The review agent receives the scenario, relevant authorised output and verifier results, then returns structured findings, rubric scores, uncertainty, failure categories and suggested follow-up scenarios. Reviewer instructions and model/version are fixed for the admitted batch. Its critique is not ground truth, an execution grant or a gradient update. If main and reviewer use the same underlying family, record that dependence; do not present agreement as independent confirmation.

LEARN-006 — A RewardDefinition specifies version, applicable task categories, component scores, weights/normalisation, verifier/reward-model versions, rejection rules and missing-signal handling. Prefer reliable task outcome checks where available; use reviewer judgements and learned preference rewards only within their declared roles. Keep objective success, preference, formatting and policy compliance visible separately before combining them. A missing verifier or failed review cannot become a high reward or default zero with no explanation. Fixed rules reject disallowed practice actions even if a model judge praises them.

Freeze the reward definition and any learned reward-model checkpoint for a training segment. Review-generated data, human preference labels and objective test results retain distinct provenance. Detect degenerate constant rewards, repetition, verbosity/format exploitation, contradictory judgements and improving training reward with worsening independent results. Quarantine suspect segments and retain diagnostics; reward score alone cannot authorise promotion. Do not train the candidate to alter its own scorer, test fixtures or held-out answers.

<a id="h.qm11bp7tanrg"></a>

### 3.6.4 Pairwise preference feedback and dataset lineage

LEARN-007 — The product supports a meaningful Which response do you prefer comparison. A FeedbackRecord binds FeedbackID, user/scope, prompt/context revision, exact displayed ResponseA/ResponseB content hashes and run/model/configuration identities, presentation order, selection, optional reason, creation time and training eligibility. A/B selection creates an ordered preference pair; Tie, Neither and Skip remain distinct outcomes and must not be manufactured into a winner. The record evaluates the responses actually shown, not later regenerated text. Correcting a choice creates a superseding revision and invalidates unconsumed stale labels.

When feedback learning is enabled for that scope, eligible pairs feed a versioned preference dataset and reward-learning pipeline that contributes to subsequent RL policy updates. The chosen response is preferred for that example; it is not automatically an objective fact or universally correct style. Separate preference evidence from scenario correctness. Randomised presentation and withheld model labels where appropriate reduce presentation bias, while provenance remains inspectable. Feedback collection, eligibility, inclusion in a training snapshot and promotion of a resulting candidate have separate visible statuses. Lack of enough usable preference evidence is a truthful waiting state, not a claim that learning already occurred.

LEARN-008 — A TrainingDatasetSnapshot is immutable and contains source/feedback/scenario revisions, permitted transformations, deduplication keys, split assignment, label provenance, exclusion reasons and consent/scope revision. Separate train, validation and held-out evaluation by source family or equivalent leakage-aware grouping; near-duplicate variants of one scenario must not make memorisation look like generalisation. User preference and synthetic review labels cannot silently become interchangeable. Use only the minimum authorised excerpts. Exclude credentials, keys, Temporary conversation content and disallowed private sources from all training and reward-model datasets.

Revocation removes future eligibility, invalidates unconsumed snapshots and marks dependent candidates for review/quarantine under the declared retention policy. Deleting a source or feedback row does not mathematically undo a completed weight update. Track affected checkpoint lineage and use a clean prior checkpoint/retraining or a separately validated removal mechanism when that removal is required. Do not claim erasure from weights merely because the dataset entry disappeared. Training exports and remote jobs retain the same disclosure controls as other protected data.

<a id="h.gec5s7j90i6o"></a>

### 3.6.5 Actual RL updates, checkpoints and evaluation

LEARN-009 — The initial preference-driven RL path trains a reward model from eligible chosen/rejected comparisons, validates it on held-out comparisons, freezes an accepted reward version, then uses that reward with scenario/verifier components in policy optimisation. A compatible GRPO implementation can use grouped rollouts and a versioned reward model/function; other verified RL algorithms must record their own objective and required state. Pairwise data are not arbitrarily relabelled as per-token rewards without the defined mapping. Supervised fine-tuning or Direct Preference Optimisation may be additional labelled methods, but neither an evaluation-only loop nor DPO alone fulfils this explicit RL contract.

Each update records TrainingRunID, immutable parent checkpoint, trainable parameter set, dataset/reward/reviewer versions, rollout policy, optimiser/scheduler configuration, random-state information, completed update count, measured losses/rewards and actual parameter-change evidence. Define trainable token/action masks so prompts and tool-returned text are not accidentally treated as policy-generated actions. The pinned algorithm defines clipping, reference-policy/KL treatment, reward normalisation and stale-rollout handling; do not copy changing library defaults as permanent product policy. Reject nonfinite losses/gradients, incompatible tensor shapes and stale base/adapter combinations before a candidate becomes usable.

A checkpoint manifest distinguishes serving weights/adapters from full resumable training state. The latter includes required optimiser/scheduler/random-state and sampler/progress information where supported. Write and verify checkpoints atomically. Adapter checkpoints retain the exact base dependency and application configuration; an adapter alone is not a standalone complete model. Training completion means a verified candidate was produced, not that it was deployed or improved the live assistant.

LEARN-010 — Compare each candidate with its declared parent/current baseline using an immutable EvaluationPlan. Include held-out target scenarios, held-out user preferences where available, general capability/regression tasks, instruction/tool schema compliance, permission-boundary behaviour, privacy leakage checks and serving performance/resource compatibility. Keep training reward and evaluation outcomes separate. Record sample counts, failures, variability/uncertainty and the limits of the tested distribution. A candidate cannot pass by repeating the same examples that produced its updates or by receiving approval solely from its training reviewer.

The plan declares promotion gates and tolerated regressions before evaluating the candidate. Gains in one measured task do not justify an unsupported claim of universal improvement. Insufficient evidence, failed tests, resource incompatibility or worsened protected behaviour leave the baseline active. At least one independent executable verifier or evaluation source beyond the training review is required for supported automated promotion; an unverified model consensus alone is insufficient.

<a id="h.83sv5u9g0we0"></a>

### 3.6.6 Promotion, rollback and acceptance

LEARN-011 — CandidateReady contains the checkpoint manifest, evaluation report, eligibility result and applicable promotion policy. The enabled policy can permit automatic promotion of candidates that meet its predeclared gates or retain candidates for manual selection; implementation must support the chosen mode without inventing recurring approval prompts. Promotion creates a new model/configuration revision and atomically updates only the selected eligible route after serving validation. Existing runs remain pinned to their admitted model version until a supported transition boundary. Do not overwrite the base artifact or hot-mutate weights beneath active unrelated sessions.

Retain a verified prior serving configuration and a functional rollback operation. Rollback changes the active route/checkpoint reference and invalidates incompatible caches; it does not erase user conversations or replay their tools. Monitor the promoted candidate against its declared operational gates and restore the prior version when the selected policy requires it. Settings shows last practice/training/evaluation, active candidate/base/adapter identity, observed results, pending feedback, resource usage, pause/failure reasons and rollback availability. A rejected candidate may still be a valid completed experiment.

LEARN-012 — Acceptance proves all essential stages on a supported small trainable fixture: main-agent practice, reviewer output, verified reward computation, a real RL parameter update, persisted reloadable candidate, independent evaluation and policy-governed promotion/rollback. Trace one pairwise preference from displayed responses through dataset and reward-model versions to an actual policy update. Also test unsupported hosted weights, insufficient resources, revoked/Temporary data, contradictory or constant rewards, a failed evaluation, foreground activity during an optimiser step, controller survival after model unload, restart from checkpoint and rollback after failed serving validation. No quality-gain guarantee or completion claim is established by this specification alone.

### 3.6.7 Primary technical basis and scope of the design

These are required 9to1 engineering contracts, not claims that the current repository already trains models. Ouyang et al. describe collecting response comparisons, training a reward model and using reinforcement learning to update a policy; current TRL Reward Modeling documents chosen/rejected datasets, and its GRPO documentation supports reward functions/models and PEFT configuration. These establish the feasibility of the stated algorithmic path, not compatibility with every installed model: [https://arxiv.org/abs/2203.02155](https://arxiv.org/abs/2203.02155) ; [https://huggingface.co/docs/trl/reward_trainer](https://huggingface.co/docs/trl/reward_trainer) ; [https://huggingface.co/docs/trl/grpo_trainer](https://huggingface.co/docs/trl/grpo_trainer) .

PEFT's quantisation and checkpoint documentation distinguishes training added adapter parameters from replacing all base weights and explains the retained base dependency. TRL's vLLM integration documents generation/training resource arrangements; that does not itself implement the required idle scheduler or independent controller. Those are deliberate product architecture requirements here: [https://huggingface.co/docs/peft/developer_guides/quantization](https://huggingface.co/docs/peft/developer_guides/quantization) ; [https://huggingface.co/docs/peft/developer_guides/checkpoint](https://huggingface.co/docs/peft/developer_guides/checkpoint) ; [https://huggingface.co/docs/trl/vllm_integration](https://huggingface.co/docs/trl/vllm_integration) .

The DPO paper explicitly proposes preference optimisation without the conventional reinforcement-learning training loop, supporting the method distinction above. The DeepSeek-R1 report describes RL with task rewards and discusses limits of learned reward signals, supporting independent evaluation rather than guaranteed gains: [https://arxiv.org/abs/2305.18290](https://arxiv.org/abs/2305.18290) ; [https://arxiv.org/abs/2501.12948](https://arxiv.org/abs/2501.12948) . Primary documentation was checked on 21 November 2026; implementation pins and validates its actual versions. The owner approved fine-tuning, Dreaming, evaluation and checkpoint management as Train's initial scope on 22 November 2026. General pretraining and arbitrary direct manual weight editing are deferred beyond that scope and require their own later feature contract; they are not prerequisites for the required Dreaming capability.
