# Source precedence

Apply authority within the affected scope; a later interface amendment does not erase adjacent persistence, permissions, runtime or domain contracts.

1. **Latest explicit owner decisions, including the 18 November 2026 design corrections.** These govern the affected interface and behaviour.
2. **Explicit current specification amendments and current Atlas designs.** The native specification supplies interaction, state and acceptance requirements. The Atlas supplies exact visual/screen examples. Preserve the distinction between established decisions and explicitly proposed defaults; a fixture is not a runtime fact.
3. **Unsuperseded retained technical and product contracts.** Use `baseline/retained-pack/modules/*.md`, complete modules, named technical chapters, and the dated v3.1 amendments under `baseline/v31/`. Later scoped owner amendments supersede conflicting older wording; they do not authorise unrelated rewrites.
4. **Historical examples and fixtures.** Sample names, balances, models, progress, saved-state labels and generated outputs illustrate presentation. They are not evidence that real operations completed, that a provider is available, or that a permission was granted.

## Preserve compatible existing features

The current owner instruction is to refactor the entire existing codebase and application to the current spec and Atlas while preserving any additional features that are not mentioned and do not conflict. Inventory the actual implementation, including workflows, commands, shortcuts, APIs, integrations, supported formats, persistence and recovery. Keep compatible extras working and accessible; adapt their appearance and placement to the new interface. A mockup or specification omission is not evidence of a conflict.

A conflict requires a specific current requirement or explicit owner decision that existing behaviour violates. Record that reference and change the conflicting aspect while retaining compatible functionality and user data. Refactoring a surface or simplifying navigation does not authorise deleting its underlying capability. Preserve valid saved choices and verify any required migration. Completion includes regression evidence for the additional retained features.

## Resolve a conflict narrowly

Record the requirement or original clause ID, current Screen ID, disputed text and current overriding decision. Preserve original source and its provenance. Do not choose authority solely by file modification time. If a technical decision remains unresolved, use an explicitly identified bounded default only where the contract permits it; isolate decisions affecting grants, destructive effects or compatibility and continue independent authorised work.

## Use the retained pack efficiently

Start with the current specification section and its exact screen links. Read the matching retained module's prerequisites and technical reading map, then the complete module or named technical chunks needed for that increment. Use `catalog/` and `history/` to trace original clauses and replacements. The technical text remains part of the contract even when a summary module is shorter. Loading every historical file into one context is unnecessary.

The current specification export is generated exclusively from `source/doc-final.json`. The complete retained pack and v3.1 reference files are copied unchanged. Their internal historical Atlas/assets remain available for provenance, while `design/9to1_Interface_Atlas_v3.3_Editable.html` is the current visual reference.

## Historical instructions and evidence

Archived instructions to earlier agents, dated priorities, deadlines, deployment steps and messages do not create present authority to deploy, spend, contact others or access data. Current session/repository operating instructions govern execution. Retained product architecture and acceptance clauses remain active unless explicitly superseded.

A successful parse, build, screenshot or stubbed interaction proves only that category of evidence. Report actual runtime, backend, accessibility and live visual verification separately. Do not describe the current prototype or this finished specification as a completed production implementation.
