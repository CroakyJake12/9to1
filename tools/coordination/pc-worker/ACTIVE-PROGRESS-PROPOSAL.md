NOT IMPLEMENTED — reviewable proposal only. No active-progress monitoring, steering, pagination or inbox-update behavior has been added to the continuation loop.

The present loop measures git/checkpoint progress at completed inactive session boundaries. A long active turn can repeatedly read sources and compact context without reaching that check. An active process or frequent tool calls establish activity, not useful implementation. Coordinator review remains necessary for quality, specification coverage and acceptance.

A possible bounded extension is a separate opt-in `active_progress` policy with a coordinator-hashed corrective prompt. It would sample no more often than every 30 seconds and require at least ten distinct completed known-read tool IDs over ten minutes, including repeated input/output signatures, while actual product contents and watched evidence remain unchanged. This is a concrete repeated-work criterion, not a silence timeout.

The observed progress signature would include git HEAD, tracked/staged diff, contents of untracked product source, the durable checkpoint and explicitly configured evidence paths. Untracked disposable `work/` files would not count as product dirt, but explicitly watched test evidence there would count as activity. Any genuine source/test/checkpoint change resets qualification. File count/size limits or incomplete message coverage would defer action instead of assuming no progress. Merely changing timestamps would not establish useful progress or acceptance.

Read classification would accept dedicated read/grep/glob operations with known semantics. Generic shell calls would qualify only through coordinator-approved exact command hashes. There would be no heuristic assumption that arbitrary shell, Python, pipelines or a command starting with `cd` is read-only. This limits coverage of the current shell-heavy worker; without reviewed hashes, that workload would not qualify. A write, test, error, unknown operation, running compaction or missing history coverage invalidates the proposed read-only window.

Only at an observed completed read step could the monitor consider one corrective steer. It must find no running or streaming tool, existing pending steer, unknown queued input, unreviewed owner input, permission/form, coordinator marker, active configured peer or unresolved recovery condition. It must retain the exact session/model/workspace and comply with STOP/PAUSE and all policy enable flags. Under the shared dispatch lock it would reread the snapshot and source/evidence signature, persist a deterministic intent, recheck grants, then admit one approved `session.prompt` with `delivery=steer` and `resume=false`. It would neither interrupt the active worker nor start another session or inference request.

If the session becomes idle before consuming that admitted steer, the supported `session.inbox.update(delivery=steer)` operation could wake only the exact owned pending ID after the ordinary safe idle checks. This requires separate implementation and tests. It must never duplicate prompt text or alter another owner's queued item. No second automatic corrective steer would be admitted until actual product/evidence progress or a new approved coordinator input establishes a different boundary. Ambiguous submission would hold for exact-ID reconciliation.

The installed V2 API has no atomic conditional admission operation. Bounded pagination must cover all new relevant messages between samples; short steps can otherwise be missed. Durable steering and ownership checks reduce races but do not guarantee that the worker chooses productive next actions. A completed correction or changed evidence still does not establish independent acceptance.

The separately implemented `current_observation` refresh is diagnostic only. Every complete successful snapshot records fresh user/assistant IDs, model, tool IDs/names/statuses and observation time in a nested field. It excludes tool arguments, outputs and reasoning. Pinned identity and dispatch receipts remain unchanged. If a snapshot fails, the last successful observation retains its old timestamp; readers must not treat it as current health.

Before any future activation, tests should cover repeated-read qualification, substantive/untracked source changes, evidence changes, unknown shell calls, pagination gaps, running tools/compaction, existing steering, STOP/enable revocation, peer ownership, restart deduplication, ambiguous admission and the exact owned pending-item idle race. A harmless isolated canary should confirm supported steering semantics without concurrent production inference. No such active-progress canary has been run this cycle.
