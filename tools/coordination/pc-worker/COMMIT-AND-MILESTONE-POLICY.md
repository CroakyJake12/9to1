Build an exhaustive scoped requirement/donor manifest with the actual entrypoint, CUI source, typed action/service, data ownership, persistence, platforms and evidence for every requirement. The worker owns sequential implementation throughout the plan in its isolated worktree. Finish the current concrete repair before changing surface. Implement missing frameworks before dependent applications claim readiness. Recover useful prior branch changes by exact reviewed commits, preserving unrelated ancestry. Never reset or merge arbitrary prior work.

At every turn boundary read `work/pc-worker/MILESTONE-STATE.json`, `CHECKPOINT.md` and the current milestone. A final reply is a checkpoint, not completion. Immediately perform the next executable engineering action. Do not ask the owner whether to continue or end because a conversational time limit feels due. A genuine provider cutoff is handled by the continuation service; preserve state before it when possible.

## Commits and checkpoints

Commit each coherent implementation slice after focused authentic smoke checks, and checkpoint dirty owned work at least every 30 minutes of active implementation and before moving milestones. If the slice is incomplete, make a clearly labelled local WIP commit with failing/unrun checks and the next action recorded; a WIP commit is never a passing milestone. Do not interrupt an active save/build solely to meet this interval. Never repeat broad tests without a relevant change, new failure or unresolved risk.

Before each commit inspect `git status`, the exact staged diff and the affected files line by line. Stage only explicitly named files owned and changed for this assignment. No `git add -A`, no blanket staging of `work/`, credentials, user profiles, generated build outputs, reviewer artifacts or another worker's changes. Preserve unrelated index changes. Use normal local commits; no push, public deployment, primary-branch modification, force reset or destructive cleanup. Record commit IDs and source/build/artifact hashes. Never manufacture a clean tree by discarding work.

Maintain `CHECKPOINT.md` and the machine ledger with: current milestone; spec hash and exact sections read; owned/changed paths; commit/build identity; actual commands and complete results; evidence paths; all failures, missing requirements and external gates; the next concrete action. Store smoke evidence in your own `work/pc-worker/evidence/`. Use the guarded dotnet entrypoint and existing serial memory controls. Actual native checks use disposable profiles/windows and preserve the owner's preview.

The ledger helper `milestone-ledger.py --root <pc-gateway-directory> ...` provides `status`, `checkpoint`, `finish`, `block` and `next`. Run `--help` for arguments. It records implementation separately from acceptance, checks source identity and preserves history. It does not create product commits, evaluate test truth, or grant acceptance. A finished implementation milestone means all its scoped requirements were reconciled and smoke evidence recorded; independent acceptance remains PENDING_REVIEW. A checkpoint/WIP does not finish a milestone.

## Independent acceptance and progression

For each surface create an acceptance handoff containing its full scoped requirement manifest, exact source/build identity, launch steps, genuine saved artifacts, failure/recovery coverage and remaining risks. Apply all seven criteria: usability, product fit, functionality, integration, separation/authenticity, user fit and refinement. Native, web, emulated, headless and source-only evidence are distinct. Source tests and screenshots alone cannot substitute for independent runtime acceptance. CUI-only authoring and absence of Fluent/donor presentation must be checked through source, generated output, package contents and real runtime.

Advance to the next dependency-ready milestone after engineering work and scoped commits, while independent acceptance is pending. Check the acceptance repair queue at each boundary. Take a precise significant rejection as the next corrective milestone after the active coherent slice, then rerun only affected checks. Minor reviewer fixes require an explicit exact-commit handoff before integration. Do not label your own work VERIFIED or erase failed/unrun checks. If reviewers are unavailable, keep acceptance NOT_RUN/PENDING_REVIEW and continue independent implementation.

If one requirement needs credentials, a public/product/security/commercial decision, unsupported hardware or external approval, record its exact source requirement, impact and evidence and continue another independent eligible item. Routine engineering choices are already authorised. Do not convert the whole programme into a NEEDS_COORDINATOR pause merely because one milestone finished. Create that marker only when every remaining executable item is genuinely blocked, or all implementation is awaiting independent acceptance; explain each remaining gate. All required work must remain in the ledger. Explicit deferred Training Lab/Droid scope must not be silently implemented or exposed as a placeholder.

## Outages and limits

An unavailable PC endpoint is a recoverable availability condition. Keep the saved task and exact session; the loop probes with bounded backoff and resumes only after the authenticated model catalogue confirms the configured model is loaded. Do not switch to a paid provider or bypass a rate limit. Authentication changes need a valid key; no recovery rule grants secrets or access. A deliberate owner cancellation never becomes a crash-restart signal. The PC must regain power and boot its configured services; an inference API cannot power on the machine.

The laptop continuation service is enabled with user lingering. Its own crashes restart without resending an already admitted prompt. STOP/PAUSE, unknown owner input, pending permissions/forms and ambiguous dispatches remain binding. An unavailable reviewer or an unchanged healthy active worker does not justify repeated status-only model requests.

The ledger also supports `show` for only the current milestone and `dependency --record <json>` for a proven existing functional prerequisite. A dependency receipt needs exact target/dependency IDs, spec hash, concrete contract summary, existing evidence and actual PASS checks with command and exit_code:0 against committed source. It grants scoped implementation readiness only; it does not accept the parent framework. Do not read the entire large queue into every model turn; read the current entry plus actual canonical dependency sections.
