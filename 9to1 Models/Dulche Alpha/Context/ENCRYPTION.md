# UCML encryption and canonical storage

`UcmlProtection` protects sealed UCML artifacts using .NET AES-256-GCM and HKDF-SHA256. It is a trusted host API. It does not authenticate a caller or grant context permission. The canonical storage owner also uses it to encrypt UCML record fields and receipts before persistence; this does not encrypt whole databases or unrelated Den content. Authenticate the actual Home actor, enforce current app/scope/purpose/recipient grants, and recheck those grants before disclosing the decrypted document through the canonical context owner.

## Key custody and retained records

Compose `ProviderSecretUcmlKeyCustody` with the existing platform `IProviderSecretStore`. Windows uses Credential Manager. Linux uses the maintained `LinuxProviderSecretStore`: AES-GCM credential records with an euid-private root-key file, descriptor-relative no-follow access and restrictive permissions. Linux custody is not a claim that keys are hardware-backed or safe from full-disk/account compromise. The credential interface uses managed strings internally; the implementation clears mutable key buffers but cannot guarantee erasure of those immutable strings or all runtime copies.

Standalone sealed-export tooling provisions roots through its explicit trusted setup command. Canonical import provisions a per-Home-profile retained root through its already composed credential owner when no canonical key reference exists. Neither route is a model tool. `CreateKeyAsync(authenticatedOwnerId)` creates a new random 256-bit root key under a fresh opaque key ID and verifies storage readback. The returned `UcmlKeyReference` contains only owner and ID; it is not a bearer credential. Never expose the credential owner, provisioning, raw keys or decryption API to a model. A model receives only context approved by the existing broker/policy boundary.

Each envelope derives a data key using HKDF-SHA256 from the retained root key, a fresh random 32-byte salt, and domain-separated owner/key ID/UTC day information. A fresh random 96-bit AES-GCM nonce and a 128-bit authentication tag protect the serialized document. The authenticated header contains version, algorithm, owner, scope identity, document identity/revision, key ID, UTC day and derivation salt. The title, source details, consent metadata and Markdown remain inside ciphertext.

The UTC day changes the derived data key without deleting older roots. Old envelopes retain all nonsecret derivation metadata, so later days and explicit new root provisioning do not make them unreadable. Missing/corrupt root keys fail closed and are never recreated during sealing or opening. Recovery means restoring the original key through the platform's trusted recovery mechanism. This implementation does not provide cross-device key transfer, backup/recovery UI, hardware custody or guaranteed cryptographic erasure. Keep root keys while any legitimately retained artifact still needs them; key deletion intentionally prevents further decryption.

## Scope of protection

New canonical UCML imports are now encrypted **before** binding values to the existing Knowledge SQLite rows. `CanonicalUcmlRecordProtection` encrypts the full `KnowledgeRecord`, including its UCML metadata, title, body, categories, confidence and provenance. SQL retains fixed placeholders and the minimum opaque routing/lifecycle columns needed to select the original Assistant scope: record/store/Assistant/app identifiers, timestamps, status and flags. The encrypted payload is stored under the existing `ucml.v1:sealed:` marker; no second memory database is created. Its authenticated owner is derived from the actual Home profile/account/organisation tuple, independently of the portable file's owner claim, and its scope is bound to the canonical store/Den/namespace/Assistant tuple and payload purpose.

Only an issued, currently authorized original memory read scope hydrates records. Generic memory lookup, correction, deletion, legacy prompt-memory readers and generic retrieval cannot bypass the UCML broker. The generic retrieval index stores no body, chunks, embeddings, source text or content fingerprint for UCML; its title is a fixed placeholder. Canonical corrections create a new encrypted revision; retirement also re-encrypts the old record with authenticated superseded/rejected lifecycle state. SQL projection tampering and envelope substitution fail closed.

Durable create/correction/rejection receipts are encrypted in the same SQLite transaction. Home approval/audit arguments retain only opaque identifiers and digests, while the user's full review candidate lives in memory. UCML access/export/dispatch observations are stored in the existing Home permission audit with opaque record IDs and fixed outcomes; queries, bodies, titles, provenance and keys are excluded. Den definitions retain the user's category access policy and ordinary Assistant configuration, but no imported UCML body or provenance is copied into their revisions.

This is **UCML field encryption**, not whole-database or whole-disk encryption. Ordinary non-UCML records, Chat history, app settings and existing Den documents are not transformed. The original protected ownership/handle/path mechanisms continue to enforce storage ownership and are not themselves encryption. Explicit plaintext `.ucml` exports and source files remain plaintext at the user's chosen export destination. A model can also quote approved context in its reply, which is then ordinary conversation content.

Existing plaintext UCML rows are refused by the encrypted canonical reader; there is no silent migration or plaintext fallback. A reviewed migration must preserve the original source and key recovery plan before re-importing through the current encrypted path. Encrypting a new copy cannot erase historical plaintext WAL pages, revisions, exports or backups. No unsafe whole-database rewrite or claim of historical erasure is made.

Sealed headers reveal owner/scope IDs and document ID/revision. Decryption authenticates those bindings and checks their agreement with the inner UCML metadata. It does not enforce retention, revocation or expiry alone: a still-authorized local holder of a root key can open an older ciphertext. Such policy checks belong to the current authenticated context owner, not file metadata. Restoring an older valid ciphertext is possible; the canonical owner must enforce its current revision when importing.

Parsing rejects unsupported versions, unknown/duplicate JSON fields, oversized input, invalid encodings, malformed key metadata, wrong owner and authentication failure. Neither original secret bytes nor plaintext appear in error messages. The envelope also underlies the canonical encrypted field representation; plain `.ucml` remains readable Markdown with structured metadata.

## Verification

Run `dotnet test "9to1 Models/Dulche Alpha/Context.Tests/NineToOne.Dulche.Context.Tests.csproj"` from the repository root. Tests cover real encryption roundtrip, randomized ciphertext, daily derivation with older decryptability, wrong-owner refusal, authenticated metadata/ciphertext/nonce/tag tampering, missing/corrupt keys without replacement, bounds/version/duplicate handling, cancellation, and actual Linux credential storage/restart/decrypt with deletion refusal. The actual Linux test also exercises the architecture-correct ARM64 `O_DIRECTORY`/`O_TMPFILE` flags.

Canonical integration tests in `Assistants/Memory/Tests/AssistantUcmlEncryptionTests.cs` scan every file under the actual Linux-backed fixture (including live database/WAL, Home audit, Den revisions and retained credentials) for distinct private body/title/provenance values across import, correction, restart and rejection. They also exercise routing/tag/owner tampering, missing retained keys without regeneration, and refusal of legacy plaintext.

The cryptographic primitives follow the standard .NET APIs: [HKDF](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.hkdf.derivekey?view=net-10.0) and [AES-GCM](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.aesgcm.encrypt?view=net-10.0). These tests establish the stated library/host behavior; they are not a full SPUI-199.I product acceptance claim.
