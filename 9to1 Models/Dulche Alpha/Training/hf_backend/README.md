# Local Hugging Face adapter — bounded second unit

The adapter takes a sealed local model bundle, a reviewed dataset manifest and an explicit purpose. `LocalSession` performs the update and the checkpoint/restore code preserves the optimizer, model and input identity used to reproduce it. Use the controls below to distinguish a software-only fixture, a real admitted input and a durable resume result. [Local session](adapter.py) · [Restore contract](restore.py)

## Original input, training and checkpoint contract

1. Root registers reviewed dependency roots/source bundle; this package never modifies import paths or installs dependencies. Import alone must not initialize CUDA. Software-only tests construct a tiny random Llama and fixed token arrays to check software differentiation, never a real training dataset or selection signal.
2. Model loading requires an explicit caller purpose matching the custody `DatasetManifest`, its verified local bytes, and an exact local model bundle whose files match sealed `ArtifactRef` records. Software fixtures retain `software_test_only` purpose and cannot run NF4 or pass as real training. Real training requires genuine admitted data and a verified immutable checkpoint publisher. Only an ordinary Llama causal LM with Safetensors is admitted initially. No remote code, network model lookup, arbitrary architecture or pickle weights.
3. Load model weights with `local_files_only=True`, `trust_remote_code=False` and `use_safetensors=True`. Tokenizer construction bypasses AutoTokenizer/from_pretrained: deserialize only reverified sealed tokenizer.json bytes into a tokenizers object and wrap it in the known PreTrainedTokenizerFast implementation. Tokenizer config accepts a bounded allowlist of literal special tokens, context/direction/cleanup settings and generic tokenizer class names. Reject all path redirects, auto_map, unknown classes/fields, conflicting special-token declarations, extra bundle files and unsupported architecture/quantization. Keep original files unchanged. Architecture-specific tokenizer semantics outside this initial generic adapter are unsupported until separately reviewed.
4. Conventional CPU training and PEFT LoRA use the actual transformers/PEFT modules. Tests compare loss/gradients with an independent shifted-token cross-entropy reference, compare frozen-base low-rank gradients with an explicit algebraic reference, and record trainable/nonzero parameter coverage. No HF recomputation equivalence is claimed: buffers, RNG replay, shared parameters and general architectures need separate work.
5. Actual training batches come only from a reverified manifest file in the train split; validation/final-held-out files cannot enter the update method. Pre-tokenized JSON must contain only input_ids, attention_mask and labels, with exact bounded shapes and integer ranges. Source manifests must cover preprocessing/labels; an admission parser alone cannot prove the origin assertion true.
6. The optional NF4 construction path uses actual Transformers BitsAndBytesConfig + PEFT preparation, requires an explicit supervisor admission for an allowlisted GPU, and is not exercised here. No CPU substitution or fake 4-bit claim. GPU execution remains unavailable until root independently verifies device admission and executes a bounded test.
7. `step_file` checks cancellation before batch read/forward/backward/update, rejects nonfinite gradients and post-update model/optimizer state, and clears gradient buffers on exit. Its checkpoint callback receives owned detached CPU copies plus metrics after each completed update. Callback/post-update failure stops the session so callers cannot blindly repeat an already-applied update. Snapshot includes actual purpose, base artifact hashes, dataset hash, full model/optimizer state, CPU RNG and LoRA configuration.

Real-training admission requires a concrete `VerifiedCheckpointPublisher` belonging to the same store and execution purpose. A callable callback alone does not qualify. It writes and verifies both the immutable snapshot and linked evidence record before acknowledging publication. Optional `on_update(snapshot, record)` and `on_failed_update(snapshot, record)` callbacks are observers; they cannot substitute for durable real-training publication. After a partial/nonfinite optimizer update, gradient cleanup failure or failed successful publication, the exact failed model/optimizer state is published once with attempted/completed update counts and the failure phase. The optimizer is never retried. If failure preservation also fails, every original/cleanup/publication cause remains in the exception group and the session stays stopped. No durable preservation is claimed after a storage/publication failure until an artifact is verified. Abrupt process loss still requires the supervisor's last sealed checkpoint and interruption record.

Each supervised dataset file requires explicit examples and labels lineage. Each sample digest binds one actual row, including input IDs, attention mask and labels: SHA-256 of the ASCII JSON object with sorted keys, separators `(',', ':')`, and no extra whitespace. File sample order must match batch row order. All three splits are reverified before loading model weights, and the training file is checked again before each update. Equal canonical rows therefore cannot hide across splits behind whitespace or invented sample hashes. These checks verify declared byte relationships; independent provenance and licensing still require trusted admission.

A nonblocking per-session update lock rejects concurrent and callback-reentrant updates before invoking cancellation predicates. Snapshot reads are permitted between updates and on the publishing thread; concurrent reads fail instead of exposing a partially updated model. Cleanup errors join the update error path before publication, rather than replacing its exception from a finalizer.

`restore_checkpoint(publication)` resumes a completed CPU software-test checkpoint in a fresh full or LoRA session. Its destination publisher belongs to a separate attempt in the same run with both verified source references in `resume_from`. It validates model and dataset custody, dependency versions, trainable parameter order and ties, and CPU model, Adam and generator state before applying them. Optimizer and counters commit after model, mode and RNG readback. Uncertain rollback stops the destination and retains a failed-state artifact and linked evidence when storage permits. Earlier archive schemas remain readable as retained evidence. Resume uses the explicit compatibility metadata and the isolated worker's process CPU RNG.

The adapter is a library, not a standalone job launcher or public endpoint. The supervisor owns telemetry, limits, pause, dependency registration and immutable checkpoint publication. Model/data fingerprints, strategy, trainable counts and step metrics are returned for that integration. Real datasets/models are not bundled. CPU correctness does not establish quality, throughput, VRAM ratio or practical-scale readiness.

## CPU execution guard and current evidence

CPU software workers must set and assert `CUDA_VISIBLE_DEVICES=-1` before imports, install a throwing refusal at `torch._C._cuda_init` before importing HF/PEFT, set the torch default device explicitly to CPU, and retain pre/post CUDA-initialization checks. Package exports are lazy so `hf_backend.cpu_guard.install()` can precede adapter imports. This is fail-fast library refusal inside a controlled worker, not an OS GPU security boundary. Production workers use the common custody bootstrap; the local guard supports the isolated software tests.

The initial five-test run with an empty CUDA visibility value failed two checks because CUDA became initialized. The numerical assertions passed but that run remains a safety failure, recorded by the coordinator; no QLoRA readiness follows. Following explicit root authorization, the corrected tests require child mask `'-1'`, pre/post `cuda_initialized=False` and `guard_calls=0`. Every fixture verifies parameters, buffers and inputs are CPU before forwards/updates.

This includes actual local tiny random Llama/tokenizer loading, full/LoRA software-only updates, custody publication/decoding of immutable checkpoints, source/data tampering, unexpected bundle files, remote architecture/quantized-base refusals, held-out denial, pre-update cancellation and failed publication/nonfinite-update stopping. ## Native RTX + legacy VM V100 preflight

`custody.topology.preflight_heterogeneous_training` validates an operator's exact rank order (native RTX 5080 at rank 0, legacy VM Tesla V100 PCIe 16 GB at rank 1) against trusted lane-owner observations, including a fresh caller-minted attempt identity, device and runtime identity, distinct exclusive ownership, optimizer participation capability, verified cooling, mentor GPU release, protected work status and identical per-device limits (not a pooled budget). It neither authenticates the owners nor opens a lease, enumerates GPUs, or starts a worker. Never construct observations from a user request or inference endpoint response.

Both current local executors reject a supplied `training_topology` before claiming an attempt or reading a model or dataset. The current single-GPU path (including the V100 cooling hold) is unchanged. Cross-host execution still needs authenticated rank owners with renewable leases and ongoing telemetry, a compatible runtime/model strategy and an update protocol with all-rank failure handling and one verified checkpoint publisher. An inference service does not satisfy that contract.

### Two-rank checkpoint visibility

`custody.rank_checkpoint.TwoRankCheckpoint` accepts two ordered trusted owner receipts linked to the same attempt, step and previous checkpoint. Stage fragments out of place as sealed `segment_checkpoint` artifacts that name the step base as their sole input; they are not resumable results. Step 1 requires the base to be the attempt’s sole declared resume reference, of kind `checkpoint` or `segment_checkpoint`. A new attempt may instead declare a prior joint `evidence` artifact, but only with the exact committed pointer in its source attempt. Subsequent steps must use the immediately preceding committed joint result. The coordinator verifies both fragments, durably claims the step, writes one sealed joint manifest of kind `evidence` (never a model checkpoint) and atomically commits a fixed pointer. Only a verified `committed()` result may advance the trainer's progress. Steps are consecutive within an attempt, starting at 1; a resumed attempt starts a new local sequence.

For the separately deployed v8 SFT worker, this seam replaces the single-device optimizer/evidence/progress handoff after gradient accumulation. Neither existing local checkpoint publication nor a staged fragment may advance two-rank progress. After an uncertain publication, read the fixed record; if absent, stop and restore the previous committed base in a new attempt. Never retry that optimizer update blindly. A rank failure before publication leaves the prior base unchanged, but does not undo any optimizer side effects in the ranks; discard their live processes unless their runtime can independently prove rollback. This module neither authenticates owners nor provides a rank launcher, transport, autograd, or model-specific restore.

### Activation and boundary-gradient frames

`custody.rank_stream` sends contiguous little-endian float32, float16 or bfloat16 tensor bytes between already-owned binary streams. Schedule each rank-3 frame explicitly: rank 0 sends an activation, rank 1 returns a gradient for the same fresh attempt, step, microbatch, shape and dtype. Each receiver compares the exact expected fixed header before reading any payload. Keep control/log traffic off the binary stream, impose deadlines and teardown at the owner, and retire both streams after any framing or I/O failure; do not resynchronize or replay. The caller authenticates the ranks and owns tensor serialization, finite-value checks, timeout and cancellation. The module does not open a listener, run autograd, or publish optimizer results.

### PyTorch boundary call pattern

`custody.rank_autograd.AutogradBoundary` pairs the existing rank-stream activation and gradient headers. It imports PyTorch only when tensor operations are requested. At the eventual v8 split, the early rank passes its original graph-connected hidden tensor to `early_backward`, which sends the activation, receives the exact returned gradient and feeds it into that graph. The tail calls `tail_forward` for a fresh detached leaf, runs the existing downstream blocks and loss, performs its existing scaled backward exactly once, then calls `tail_backward` to return that leaf's gradient. The boundary does not divide, unscale or step an optimizer. Keep the adapter outside regions that autograd checkpointing may replay; stop the attempt and retire both streams on failure. This is a tensor boundary, not a Qwen layer partitioner or deployed runner.

### Qwen3.5 native text layer ranges

`custody.qwen35_range.Qwen35TextRange` adapts only the reviewed Transformers 5.20.1 eager, text-only no-cache ABI with default RoPE. It preserves the original indexed layers, asks the installed library for both native mask families and rotary embeddings, embeds solely on the early side, and normalizes solely on the tail. In v8, the split would replace the full `core(...).last_hidden_state` call: early `forward(input_ids=...)` supplies the stream adapter's graph-connected tensor; tail `forward(hidden=...)` consumes the detached boundary leaf and supplies the existing masked frozen-head loss. Caller-provided masks, positions, caches and other attention implementations are not admitted. No installed worker, model, optimizer or data path is modified.
