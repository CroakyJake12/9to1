# Efficient training core: first correctness boundary

This is a CPU-only reference/prototype, not the complete training engine or an LLM trainer. It implements the first software correctness slice of ETR-03/04/06/17, while all other requirements in the coordinator's continuous Dulche rubric remain active. No model downloads or GPU execution occur here.

## Running the reference comparison

The core accepts an already constructed dense CPU model, an explicit partition and an objective. Its tests compare the actual update under the supported optimizer and replay assumptions. Retain the model, objective, split and seed when comparing a change, so a different setup cannot account for the observed result. ## Original required input and update flow

1. The caller supplies an already constructed CPU dense sequential model, exact block partition, optimizer/configuration, and an independently admitted data purpose. Software tests supply arithmetic fixtures labelled `software_test_only`; they are never model-training datasets, selection signals, rewards or evaluation data.
2. Validate supported modules, CPU tensors, finite scalar settings, parameter coverage and no shared parameters or mutable buffers. Reject unsupported models, quantization, QLoRA and custom stochastic/stateful modules rather than silently approximating them.
3. For conventional mode, perform one full forward/backward and optimizer update. For block-coordinate mode, freeze other parameters, retain the autograd path through the frozen tail, compute a block gradient and update that block before advancing. The latter is a distinct algorithm, not full-gradient equivalence and not an implementation of the BAdam paper.
4. For recompute-equivalent mode, repeat the full forward/backward for each block at unchanged weights, replay the same CPU torch RNG for Dropout, use activation checkpointing with RNG preservation, and retain each block's gradients on CPU. Do not update any parameter until every block gradient has been collected. Clip the complete gradient globally, then apply one conventional optimizer step. All model/gradient/state storage is CPU in this first boundary; it does not demonstrate GPU/RAM savings or disk streaming.
5. Record selected parameters, parameters with gradients, and parameters with nonzero gradients separately. A complete schedule does not imply useful gradient coverage. Check finite loss/gradients before updates. For coordinate mode the clipping norm is explicitly active-block-only, not a full-model gradient norm.
6. At each completed update, emit a detached immutable-by-ownership snapshot and measurement through a callback. The core writes no files and cannot delete or overwrite models. Artifact publication, provenance admission, resource admission and real-job lifecycle belong to the supervisor. If publication fails, propagate the error and stop: the in-memory update already happened and must not be retried as if absent.
7. A saved configuration/model/optimizer/RNG/update cursor can initialize the same explicitly constructed architecture and resume deterministically. Restore validates the complete schema, strict scalar types, progress consistency, module modes, CPU RNG state and optimizer groups/moments before touching the live model. Per-parameter update counts distinguish a legitimately absent Adam state from a missing saved slot. Optimizer construction/load is staged; unexpected model-copy failure rolls back, and uncertain rollback stops the executor. No executable pickle loader is provided. Actual artifact encoding/atomic publication/reload integrity is supplied by the artifact store.

## Semantics and limitations

`recompute_equivalent` is equivalent within tested numerical tolerances only for the supported stateless CPU modules, unchanged inputs/objective/weights, standard SGD/Adam, and replayed torch CPU randomness. Arbitrary loss callbacks, distributed execution, GPU, AMP, custom generators, stateful buffers, hooks, tied weights, quantized frozen layers and fused update hooks are outside this boundary. Coordinate mode retains optimizer states per parameter; it is not a low-state BAdam adapter. LoRA is an explicit frozen dense base plus trainable A/B matrices, not QLoRA. Higher-order derivatives and differentiable optimizers are not supported.

The configuration uses a fixed built-in MSE or cross-entropy objective to avoid a callback changing random state or external data between recomputations. Gradient-equivalent recomputation advances the caller's CPU RNG once per logical step, matching conventional execution. No `no_grad` wrapper is placed around a frozen tail. Full gradients are retained until global clipping/update, which has a CPU memory cost and extra full-model passes.

Tests use small fixed arrays, CPU float64, bounded iterations and one torch compute thread. They establish software behavior only, not model quality, practical throughput, GPU ratios, 27B/Flash feasibility or real data-training permission.
