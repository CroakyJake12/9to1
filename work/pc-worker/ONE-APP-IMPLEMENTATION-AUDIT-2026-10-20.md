## Findings that control the merge order

1. **Unified Haven currently registers only Files and Spaces.** `9to1 Workspace/shared/src/Haven.Desktop/App.UnifiedWorkspaceHost.cs:258–262` passes exactly those two bindings to `NativeAppContentRegistry`. `Services/NativeAppContentRegistry.cs:49–58` refuses a missing binding before acquiring an owner. Existing Automations/Dev/productivity route-policy names and MainView launch methods do not establish unified same-tab embedding.
2. **There are genuinely separate product paths, but not every standalone directory is a newer app.** Write and Present standalone hosts construct the same shared Desktop pages as legacy MainView. Data Native also wraps the existing DataPage and explicitly distinguishes the separate Calc/UNO workflow. Promoting wrappers by their names would not consolidate anything.
3. **There are useful newer domain/CUI candidates to merge or prefer.** Canvas Rnote/Files, Data Calc/DuckDB, Stacks source collaboration, Sites authoring and canonical Dev/Automations ownership add concrete capabilities. None inspected is a verified complete replacement app. Boards standalone has a proven parallel schema/store and a forbidden FluentTheme load; it cannot be preferred whole.
4. **One shared app owner is the target; changing a route or wrapping a legacy page is not acceptance.** Preserve canonical object IDs, storage, borrowed Home services, original initialization/close custody and host-aware chrome while consolidating behavior. Header mode may differ by host; app functionality must not fork.

## Entry-point distinction
