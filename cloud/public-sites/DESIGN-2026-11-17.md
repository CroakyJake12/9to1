# Public website redesign — 17 November 2026

## Owner request and scope

Jacob requested that cakemods.com and 9to1.uk lose their generic generated-site
appearance, then explicitly requested a pop-up explaining that each website is
a very early scaffold, is missing significant functionality and is in preview.
This is work on the existing public website Worker, not a native-app release.
The current cloud website request supersedes historical cloud-authoring holds
for this scope. The existing private-testing account gate remains in place.

Starting source: `a1cdd5638db60648896dcc9b5d11a29739d5129a`, clean `main`.
Work uses disjoint file ownership in one checkout: CakeMods owns `cake.mjs` and
`cake.css`; 9to1 owns `nine.mjs` and `nine.css`; root owns shared shell, preview
behaviour, build wiring, release identity, focused checks and integration.
No native SDK, installed application or model service is involved. The local
native coordinator and its machine-specific state are not present in this
cloud checkout and are not recreated or represented as recovered.

## Required journeys (pinned before implementation)

1. A visitor opens any public website page. A labelled modal explains the early
   preview/scaffold and missing functionality. Its initial focus is on
   **Continue to preview**; background content is inert while it is open.
2. The visitor dismisses it using that button, the close control or Escape.
   The page becomes usable, focus returns to the visible Preview trigger and
   a tab-session preference records the dismissal for that origin only.
3. Navigation or reload in the same tab does not repeatedly open the modal.
   The persistent **Preview** trigger opens it again at any time. Storage
   denial must not make the page unusable. With JavaScript disabled, a native
   disclosure still provides the complete preview warning.
4. CakeMods visitors can see eight real communities, search and filter by topic
   and platform, follow a direct Reddit/Discord destination, or open an existing
   details route for moderator guidance. Projects remain a distinct section.
5. 9to1 visitors can understand the intended app family, browse the existing
   catalogue and read current development/account availability. Planned product
   scope must not be presented as already working functionality.
6. The same journeys remain readable and operable at 320, 390, 768 and 1440px,
   with keyboard focus, adequate contrast and reduced motion respected.

## Visual direction

- CakeMods: compact community directory, white surfaces, a restrained violet
  accent, strong headings, ruled lists and meaningful platform/topic metadata.
  Remove decorative letter logos, arbitrary pastel panels and repeated sections.
- 9to1: precise software catalogue, white/cool-grey surfaces, navy type and the
  established blue. Clear app purpose and current status; no fabricated product
  screenshots, users, metrics, release dates or testimonials.
- Preserve genuine owner logos, self-hosted Montserrat and all existing routes.
  Shared navigation is quieter, with Account secondary to public content.

## Validation and delivery

Run the existing package build and tests, inspect the changed source, then use
real Chromium renders for desktop/mobile, modal focus/session behaviour,
directory filtering and navigation. Retain genuine failures and distinguish
local render evidence from public deployed checks. Publish only the website
Worker, preserving its live settings, bindings, secrets, account admission and
Files service. Verify the new release identity and behaviours on both domains.
Native app/package acceptance is outside this website task and is not implied.

## Implementation and validation observed

- Both brand modules and styles were rewritten, with the shared shell and
  `preview.mjs` providing the preview disclosure. Existing brand assets/fonts,
  community destinations, account admission and Files routing are preserved.
- The previously separate Dev, Stacks and Sites catalogue entries are now one
  Build entry, following the canonical product ownership. Their coding,
  website and source-collaboration capabilities remain described.
- `npm run build`, all 27 existing `npm test` checks, and `git diff --check`
  passed on the integrated candidate. The two page modules and client strings
  also passed syntax checks and route/heading/ID checks.
- Chromium rendering through Cloudflare Browser Rendering exercised the actual
  server-rendered page content, bundled CSS and client code. The render fixtures
  inlined the unchanged Montserrat files to avoid cross-origin font failures.
  Both homepages were checked at desktop/mobile widths; additional checks
  covered 320, 390, 768, 820 and 1440px, community details, projects, the app
  catalogue and Dulche. No horizontal document overflow was found. The modal
  also remained usable at 320×700.
- Browser checks observed initial dialog focus, dismissal, focus restoration,
  reopening, and directory search/platform/topic/reset/empty-state behaviour.
  Expected counts: 8 total; Fortnite 3; Discord 2; Discord + Life & support 1.
  A first focus assertion ran before the native asynchronous `close` event;
  waiting for the real event confirmed correct restoration. No code was
  weakened to pass that check.
- Local Chromium could not start because this executor denies its process
  singleton socket. This failure is retained as an environment limitation;
  the supported Cloudflare renderer supplied actual rendered evidence.
- Public-domain navigation, keyboard Escape/Tab and session persistence are
  checked after deployment, separately from static render-fixture evidence.
