# Native installed identity

The Linux verifier is a discovery-only boundary. It never grants resource operations, approval decisions or arbitrary Home calls. Those require the freshly authenticated actor, owning service ACL and Home approval independently. Native peer and session-host identity require both installed-package evidence and a separate trusted controlled-launch authority. This authoring environment configures `UnavailableHomeNativeControlledLaunchAuthority`, so neither installed peer identity nor host identity is admitted.

The installer supplies `/var/lib/9to1/home/installed-receipts/*.9to1-install`, signed by an issuer explicitly pinned in `/etc/9to1/identity/publishers.json`. Both files, their parents and every installed payload file must be root-owned, non-writable by group/others and opened without following links. The verifier never writes these paths, imports user keys, generates trusted development certificates or accepts an unsigned build inventory.

Schema 1 envelopes contain `schemaVersion`, `issuerKeyId`, exact base64 `payload`, and base64 RSA-PSS/SHA256 `signature`. Issuer policy contains `keyId`, base64 DER `subjectPublicKeyInfo`, and explicit `allowedAppIds`, `allowedServiceIds`, `allowedRoles`. RSA keys must be 3072–8192 bits. Payload schema 1 binds app ID, receipt revision, provider and OS application/entrypoint, installation root, executable, system desktop-entry path/digest, complete relative-path/size/SHA256 inventory, service IDs and roles. Only `/usr/lib/9to1/apps/` and `/opt/9to1/apps/` qualify. Unknown schemas, duplicate identities, extra/missing files, symlinks and mutable evidence deny.

The verifier observes the real kernel peer PID/principal, `/proc` effective UID, process start time and mapped executable digest before and after verification. The signed entrypoint must resolve uniquely through the ambient profile's canonical Home installed-app registry, with current accessibility, provider, entrypoint and desktop-entry digest. Receipt and Home registry revisions are retained in the identity. A shared `dotnet` executable or mutable workspace output cannot satisfy installed-package checks.

Bounded runtime checks also require a declared self-contained .NET runtime, no shared framework or additional probing paths, exact signed CLR/host library mappings, root-owned system library mappings and `DOTNET_EnableDiagnostics=0`. Other DOTNET/COMPlus/CORECLR/COR/LD/Mono loader or profiler overrides deny, including `DOTNET_STARTUP_HOOKS`, `DOTNET_ROOT`, `CORECLR_PROFILER_PATH` and `LD_PRELOAD`. These checks establish observed package/runtime evidence only. They cannot prove controlled launch, distinguish arbitrary same-UID/JIT/debug memory injection, or attest all executing memory.

`LinuxControlledLaunchGate` therefore additionally invokes the mandatory `IHomeNativeControlledLaunchAuthority` for the app and each requested signed role. It supplies fresh actual PID/principal/start/executable observations, current Home profile and the identity of the actually held process-lifetime Home lease; it rechecks process/profile/lease after the authority answers. The lease identity and routing endpoint epoch are context, never launch attestations or bearer grants. No authority is inferred from a clean environment, a receipt, a process-local registration or a test double. Missing actual platform authority denies.

The pinned Linux host is `os.shell`, with OS application ID `desktop:9to1-os-shell.desktop` and issuer-authorized `home.session-host`. Both roles and mandatory controlled launch are rechecked by the host verifier. A service allowlist alone cannot establish this role. The listener exposes bounded discovery only; locator documents are routing information, and clients must independently attest the connected host before trusting readiness.

## Positive installation acceptance recipe (not provisioned)

1. Build the actual OS shell as a self-contained Linux package with diagnostics disabled at controlled launch. Generate a complete unsigned build inventory, then use the metadata-owned receipt producer with an explicitly approved external signing key. Independently verify the complete payload and exact signed bytes. The public-only test issuer fixture is never a production trust root.
2. On an isolated test OS, use its trusted installer to provision the immutable root-owned payload, system desktop entry, approved issuer policy and receipt. Resolve the resulting platform entrypoint through Home's canonical installed-app registry; do not assign a parallel application GUID.
3. Integrate a concrete trusted platform bootstrap/launch authority and its process isolation policy before admitting identity. It must record the real controlled process creation, bind and revalidate PID/start identity/executable/current profile/actually held Home lease, reject arbitrary apphost invocations, and address loader overrides and same-UID debugger/process-memory injection. An app-written launch marker, receipt, clean `/proc` snapshot or signed package alone does not implement this authority. No such production authority is implemented or provisioned here.
4. Exercise both sides of a real socket: approved controlled host/client identity succeeds; unsigned launch, altered payload, revoked issuer, desktop-entry replacement, missing authority, stale PID/start/lease/profile and injected loader/profiler overrides deny. Verify crash/restart gets a fresh lease, old endpoints are removed, and no resource or approval endpoint is exposed. Record the actual installation, isolation and process evidence rather than claiming success from a mock authority.

Current tests prove real producer/signature interoperability, tamper/issuer-scope rejection, actual environment override negatives, current lease/profile gate behaviour, unsigned workspace peer denial and real Unix listener denial/cleanup. The gate recording fixture proves port wiring only. No root-owned positive installed-package authentication or production controlled-bootstrap acceptance is claimed.
